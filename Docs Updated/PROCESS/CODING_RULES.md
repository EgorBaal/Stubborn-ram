# CODING_RULES.md

# Правила разработки проекта Stubborn Ram

Версия: 1.1  
Статус: целевая архитектура после миграции backend-инфраструктуры  
Дата обновления: сентябрь 2026

---

# 1. Назначение документа

Этот документ определяет правила написания и организации кода Stubborn Ram.

Главный принцип:

> Код должен оставаться простым, предсказуемым, модульным и соответствовать архитектурной документации.

Документация проекта является источником истины для архитектурных решений.

Если изменение кода требует изменения архитектуры, сначала обновляется и согласовывается соответствующая документация.

---

# 2. Главные правила

Перед реализацией новой функциональности необходимо:

1. определить модуль;
2. проверить соответствующую документацию;
3. определить ответственность каждого файла;
4. определить, какие данные и сервисы используются;
5. только после этого писать код.

Не следует заранее усложнять архитектуру ради функций, которые еще не нужны.

Приоритет:

1. корректность;
2. стабильность;
3. безопасность;
4. расширяемость;
5. скорость разработки.

---

# 3. Архитектурный принцип доступа к данным

Все обращения к серверной части выполняются через слой Services.

В целевой архитектуре:

```text
Component
    ↓
Service
    ↓
Backend API
    ↓
PostgreSQL / Object Storage / External Service
```

Компонент интерфейса не должен самостоятельно:

- выполнять SQL;
- обращаться к PostgreSQL;
- обращаться к Object Storage;
- вызывать секретные внешние API;
- содержать бизнес-логику доступа.

---

# 4. Backend API

Backend API является единой серверной точкой входа для приложения.

Backend отвечает за:

- authentication;
- authorization;
- permissions;
- бизнес-логику;
- работу с PostgreSQL;
- работу с Object Storage;
- работу чата;
- Email;
- AI/OCR;
- платежи;
- audit log;
- rate limiting.

Frontend не должен дублировать серверные проверки как источник истины.

Frontend может скрывать недоступные действия для удобства пользователя, но безопасность всегда обеспечивается backend.

---

# 5. Services

Services являются клиентским слоем доступа к backend.

Например:

```text
authService
profileService
trainingService
foodService
reportService
chatService
mediaService
weightService
activityService
paymentService
```

Названия выбираются по бизнес-модулю.

Service должен:

- отправить запрос;
- передать необходимые параметры;
- обработать ожидаемый ответ;
- вернуть данные компоненту.

Service не должен содержать UI.

---

# 6. Внешние сервисы

Любая внешняя интеграция подключается через отдельный server-side service/adapter.

Например:

```text
Email Service
AI Service
Payment Service
Storage Service
```

Запрещается напрямую вызывать внешние сервисы из React-компонентов, если для этого требуются:

- секретные ключи;
- privileged access;
- server-side credentials;
- обработка персональных данных.

Цель — возможность заменить поставщика без переписывания бизнес-модулей.

---

# 7. Работа с данными

Бизнес-логика должна быть отделена от отображения.

Например:

```text
Questionnaire
    ↓
validation
    ↓
questionnaireService
    ↓
Backend API
    ↓
PostgreSQL
```

Компонент отвечает за:

- отображение;
- пользовательский ввод;
- локальное UI-состояние.

Service/backend отвечают за:

- сохранение;
- получение;
- изменение;
- проверки;
- бизнес-правила.

---

# 8. Валидация

Валидация выполняется на двух уровнях.

## Frontend

Используется для удобства пользователя:

- обязательные поля;
- формат Email;
- допустимые значения;
- длина текста;
- предварительная проверка файлов.

## Backend

Является обязательной.

Backend повторно проверяет:

- типы;
- размеры;
- обязательные поля;
- permissions;
- ownership;
- состояние объекта;
- ограничения бизнеса.

Frontend validation никогда не считается механизмом безопасности.

---

# 9. Работа с авторизацией

Компоненты не должны самостоятельно реализовывать authentication flow.

Для авторизации используется централизованный authService / auth layer.

Он отвечает за:

- login;
- registration;
- logout;
- session;
- email verification;
- password recovery;
- смену Email;
- получение текущего пользователя.

Защита маршрутов выполняется через общий механизм приложения.

---

# 10. Permissions

Проверка разрешений выполняется централизованно.

Не следует создавать в отдельных компонентах собственные независимые системы:

```text
if (isCoach)
if (isAdmin)
if (hasSubscription)
```

если речь идет о разрешении конкретного действия.

Используется общая permission-модель.

Пример:

```text
can(user, "training.update", training)
```

Конкретный API и названия функций определяются при реализации permission layer.

Серверная проверка обязательна.

---

# 11. Работа с файлами

Фото и видео не должны храниться в исходном коде приложения.

Пользовательские файлы хранятся в Object Storage.

Frontend работает через media/storage service.

Схема:

```text
Frontend
    ↓
mediaService
    ↓
Backend
    ↓
permission check
    ↓
Object Storage
```

Постоянные публичные ссылки на пользовательские файлы не используются.

---

# 12. Загрузка файлов

Каждая загрузка должна проверяться.

Минимально проверяются:

- размер;
- MIME/type;
- расширение;
- допустимость файла для конкретного модуля;
- принадлежность пользователю;
- лимиты объекта.

Размерные ограничения определяются документацией соответствующего модуля.

Для видео применяется серверная обработка.

---

# 13. Видео

Видео обрабатывается на backend/worker стороне.

Frontend не должен самостоятельно отвечать за production-конвертацию видео.

Целевая схема:

```text
Upload
   ↓
Object Storage
   ↓
Backend / Worker
   ↓
FFmpeg
   ↓
Processed Video
```

Исходный файл удаляется после успешной обработки, если он больше не требуется по бизнес-правилам.

Для Training действуют утвержденные ограничения:

- до 8 видео на тренировку;
- до 45 секунд каждое;
- сжатие;
- удаление оригинала после успешной обработки.

---

# 14. Chat

Chat является самостоятельным модулем.

UI не должен напрямую работать с базой данных.

Используется:

```text
Chat UI
   ↓
chatService
   ↓
Backend API / WebSocket
   ↓
PostgreSQL + Object Storage
```

Одна coach-client связь имеет один основной чат согласно архитектуре Chat.

Медиа чата хранится отдельно от текстовых сообщений.

---

# 15. Real-time

Real-time функциональность не должна быть жестко привязана к конкретному внешнему поставщику.

Целевой механизм:

```text
Backend
    ↓
WebSocket
    ↓
Client
```

Клиентский код взаимодействует с abstraction/service layer, а не с конкретной реализацией realtime-инфраструктуры.

---

# 16. Email

Email отправляется только с backend.

Frontend не содержит:

- SMTP password;
- Email API key;
- provider secret.

Схема:

```text
Frontend
    ↓
Backend API
    ↓
emailService
    ↓
Email Provider
```

Статус отправки и ошибки обрабатываются на сервере.

---

# 17. AI / OCR

AI и OCR вызываются только через backend.

Frontend не получает AI provider secret.

Схема:

```text
Food UI
    ↓
foodService
    ↓
Backend
    ↓
AI/OCR adapter
    ↓
AI Provider
```

AI provider должен быть заменяемым.

Не следует помещать provider-specific код в Food-компоненты.

---

# 18. Payments

Платежи реализуются через paymentService.

Frontend не хранит secret payment keys.

Схема:

```text
Frontend
    ↓
paymentService
    ↓
Backend
    ↓
Payment Provider
```

Платежные карточные данные не должны сохраняться в Stubborn Ram.

---

# 19. Работа с PostgreSQL

Frontend не подключается к PostgreSQL напрямую.

Backend использует PostgreSQL через серверный data/repository layer.

Database schema является отдельным архитектурным документом.

Изменение структуры базы требует:

1. архитектурного решения;
2. обновления DATABASE_SCHEMA.md;
3. согласования;
4. миграции;
5. проверки.

Нельзя создавать production-таблицы «на лету» только потому, что это быстрее.

---

# 20. SQL и миграции

SQL должен быть воспроизводимым.

Изменения базы оформляются миграциями.

Каждая миграция должна быть:

- понятной;
- последовательной;
- повторяемой в предусмотренном режиме;
- совместимой с текущим этапом проекта.

Перед опасными миграциями выполняется backup.

---

# 21. Никаких секретов во frontend

Запрещено помещать во frontend:

- database passwords;
- private API keys;
- S3 secret keys;
- payment secrets;
- AI secrets;
- Email secrets;
- admin secrets;
- service account credentials.

Публичные значения, необходимые браузеру, должны быть явно классифицированы как public.

---

# 22. Environment Variables

Локальные секреты хранятся в `.env.local` или другом согласованном локальном env-файле.

Секретные env-файлы не коммитятся в Git.

Перед commit необходимо убедиться, что секреты не попали:

- в код;
- в JSON;
- в конфигурацию;
- в логи;
- в тестовые данные.

---

# 23. React-компоненты

Компонент должен иметь одну понятную ответственность.

Не следует превращать одну страницу в файл, который одновременно:

- рисует UI;
- выполняет API requests;
- содержит SQL;
- считает бизнес-правила;
- управляет authentication;
- отправляет Email.

Такой код должен быть разделен по слоям.

---

# 24. Структура модулей

Модули являются независимыми.

Предпочтительная структура:

```text
src/modules/<module>/

    Page.jsx
    Page.css
    components/
    hooks/
    services/
```

Конкретная структура может отличаться, если это оправдано модулем.

Общий shell приложения не должен изменяться из-за требований одного модуля.

---

# 25. CSS

Каждый крупный компонент/модуль имеет собственный CSS-файл.

Не создавать один огромный CSS-файл со стилями всех страниц.

Общие значения могут использоваться через CSS variables:

```css
--accent
--background
--card
```

Стили одного модуля не должны случайно влиять на другой.

Избегать чрезмерного использования глобальных selectors.

---

# 26. Именование файлов

## React-компоненты

PascalCase:

```text
Hero.jsx
QuestionCard.jsx
SupportCarousel.jsx
TrainingPage.jsx
```

## Вспомогательные файлы

camelCase:

```text
validation.js
helpers.js
calculateCalories.js
```

## Services

camelCase:

```text
authService.js
trainingService.js
chatService.js
```

---

# 27. Именование переменных

Использовать понятные английские названия.

Плохо:

```text
a
b
temp
data2
```

Хорошо:

```text
currentQuestion
clientWeight
dailyCalories
proteinTarget
```

Названия должны отражать смысл значения.

---

# 28. Props и состояние

Не передавать через props данные, которые можно получить из соответствующего hook/service без нарушения архитектуры.

Не хранить в локальном UI state данные, являющиеся canonical source в backend, если для этого нет конкретной причины.

Следует различать:

- server state;
- UI state;
- temporary form state.

---

# 29. Hooks

Hooks используются для повторяемого React-поведения.

Например:

```text
useAuth
useTraining
useReport
useWindowSize
```

Hook не должен превращаться в скрытый слой доступа к базе данных.

Если hook работает с backend, он должен использовать соответствующий service.

---

# 30. Утилиты

Utils предназначены для небольших переиспользуемых функций.

Не помещать туда бизнес-модули целиком.

Плохой пример:

```text
utils/trainingEverything.js
```

Лучше разделять функции по назначению.

---

# 31. Обработка ошибок

Ошибки должны обрабатываться предсказуемо.

Пользователю показывается понятное сообщение.

Внутренние детали сервера не должны попадать в UI:

- stack trace;
- database credentials;
- SQL;
- provider secrets;
- внутренние пути.

Технические детали остаются в server logs.

---

# 32. Loading

Для загрузки использовать существующую систему loading UI проекта.

Не создавать в каждом компоненте собственную несовместимую систему загрузки без необходимости.

Loading должен корректно работать:

- при первом запросе;
- при повторном запросе;
- при сохранении;
- при загрузке файла;
- при ошибке;
- при отмене/повторе операции.

---

# 33. Dependencies

Новые npm-пакеты добавляются только при реальной необходимости.

Перед добавлением необходимо проверить:

- нельзя ли решить задачу существующими средствами;
- размер зависимости;
- поддержку;
- совместимость с Vite/React;
- безопасность;
- влияние на bundle;
- необходимость dependency в production.

Не добавлять библиотеку ради одной небольшой функции без необходимости.

---

# 34. Git

Каждый законченный этап является отдельным логическим изменением.

После крупного этапа:

1. проверить код;
2. обновить документацию;
3. сделать backup при необходимости;
4. выполнить build;
5. сделать commit;
6. отправить изменения в GitHub.

Commit должен отражать понятную единицу работы.

---

# 35. Build и проверка

После значимых изменений необходимо по возможности выполнять:

```text
npm run build
```

До commit необходимо проверить:

- отсутствие очевидных runtime ошибок;
- отсутствие новых console errors;
- корректность маршрутов;
- корректность mobile layout;
- отсутствие случайного удаления существующей функциональности.

---

# 36. Документация

Документация является частью проекта.

После архитектурно значимых изменений проверяются:

```text
PROJECT_CONTEXT.md
ARCHITECTURE.md
DATABASE_SCHEMA.md
PERMISSIONS_ARCHITECTURE.md
SECURITY.md
ROADMAP.md
CHANGELOG.md
CODING_RULES.md
```

Документация должна отражать фактическое состояние проекта.

Запрещено оставлять в документации старую архитектуру после окончательного перехода на новую.

---

# 37. Работа с архитектурными изменениями

Если задача требует:

- нового внешнего сервиса;
- новой базы;
- новой таблицы;
- изменения ownership;
- нового permission;
- изменения authentication;
- изменения storage;
- изменения способа передачи данных;

нельзя сразу начинать кодирование.

Сначала:

```text
Idea
↓
Discussion
↓
Documentation
↓
Approval
↓
Implementation
↓
Verification
↓
Documentation update
↓
Commit
```

Если обнаружено противоречие между документами — разработка останавливается до принятия решения.

---

# 38. Что запрещено

Запрещается:

- обращаться к PostgreSQL из React;
- хранить секреты во frontend;
- обходить permission layer;
- дублировать бизнес-логику по компонентам;
- создавать произвольные таблицы без обновления schema documentation;
- подключать внешние сервисы напрямую из UI;
- создавать глобальные CSS-хаки ради одной страницы;
- менять AppLayout из отдельного модуля;
- добавлять зависимости без необходимости;
- переписывать рабочую архитектуру без согласования;
- оставлять устаревшую архитектуру в документации.

---

# 39. Целевая архитектура после миграции

Цепочка приложения:

```text
React / PWA
      ↓
Services
      ↓
Backend API
      ↓
┌───────────────┬───────────────┐
│ PostgreSQL    │ Object Storage│
└───────────────┴───────────────┘
      ↓
Server-side Services
      ↓
Email / AI / Payments
```

Для Chat:

```text
Chat UI
   ↓
chatService
   ↓
Backend / WebSocket
   ↓
PostgreSQL + Object Storage
```

Для видео:

```text
Upload
   ↓
Object Storage
   ↓
Worker / FFmpeg
   ↓
Processed Media
```

---

# 40. Принцип минимального усложнения

На старте не добавлять:

- Kubernetes;
- Redis;
- отдельный message broker;
- микросервисную архитектуру;
- отдельные серверы для каждого модуля;
- сложную event-driven инфраструктуру,

если текущая нагрузка этого не требует.

Backend должен начинаться как единое приложение с четкими внутренними service/module boundaries.

При росте нагрузки отдельные части можно вынести без изменения frontend-контрактов.

---

# 41. Definition of Done

Кодовая задача считается завершенной, когда:

- функциональность соответствует документации;
- данные проходят через правильный service layer;
- backend выполняет обязательные проверки;
- секреты отсутствуют во frontend;
- нет лишней зависимости;
- CSS не создает нежелательных глобальных эффектов;
- mobile UI проверен;
- build проходит;
- документация обновлена, если архитектура изменилась;
- изменения логически отделены в Git.

---

# 42. Главное правило для дальнейшей разработки

Если можно реализовать задачу проще, не нарушая архитектуру, выбирается более простой вариант.

Если простое решение создает технический долг или вынуждает повторно мигрировать инфраструктуру в будущем — сначала пересматривается архитектура.

Цель проекта:

> один раз выбрать устойчивую основу, затем спокойно развивать продукт поверх нее без постоянных переносов.
