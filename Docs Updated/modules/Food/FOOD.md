# FOOD

**Статус документа:** CANONICAL MODULE DOCUMENT  
**Версия:** 1.0  
**Текущее runtime-состояние:** NOT IMPLEMENTED / PLACEHOLDER

## 1. Назначение

Food предназначен для хранения, контроля и последующего анализа питания пользователя.

Stubborn Ram не обязан заменять FatSecret, Yazio и аналогичные приложения. Пользователь может вести питание удобным для себя способом, а платформа должна уметь принять, сохранить и использовать canonical result.

Все food data принадлежат пользователю.

## 2. Текущее состояние

В runtime подтверждено:

- маршрут `/app/nutrition`;
- `NutritionPlaceholderPage`;
- навигационный вход из Home.

Не подтверждены:

- day-based nutrition persistence;
- Food backend;
- plan/fact lifecycle;
- FatSecret integration;
- AI/OCR integration;
- dedicated food API;
- production food schema.

Food остается target-domain, а не текущей реализованной системой.

## 3. Главный продуктовый принцип

Основная модель:

```text
ПЛАН ↔ ФАКТ
```

Для любого выбранного дня пользователь видит:

- назначенный план;
- фактические значения.

Не должна существовать логика, где пользователь видит только факт без контекста плана, если план для этого дня существует.

## 4. Структура экрана

Целевая структура:

```text
Календарь
↓
Цель периода
↓
План на сегодня (если существует)
↓
КБЖУ + Вода + Соль
↓
Добавить данные
↓
Данные питания
↓
Tab Bar
```

Единый screen model используется и для текущего дня, и для истории.

Отдельные разделы «Сегодня» и «История» не требуются.

## 5. Календарь

- показывается неделя с выбранной датой;
- нажатие на любую дату открывает именно этот день;
- структура экрана одинакова для любого выбранного дня;
- история реализуется через calendar navigation.

## 6. Цель периода

Под календарем отображается активный этап питания.

Примеры:

- набор массы;
- снижение веса;
- восстановление;
- подготовка к соревнованиям.

Карточка может содержать:

- название;
- сроки;
- описание;
- задачи;
- рекомендации;
- комментарии;
- кнопку «Подробнее».

## 7. План на сегодня

Карточка появляется только при наличии специальных назначений для выбранной даты.

Возможные назначения:

- комментарий;
- специальные указания;
- изменение КБЖУ;
- изменение воды;
- читмил;
- рефид;
- углеводная загрузка;
- изменение соли;
- иные индивидуальные указания.

При отсутствии назначения карточка скрывается. Карточка должна визуально выделяться среди остальных элементов интерфейса.

## 8. Основные показатели

Основные показатели:

- калории;
- белки;
- жиры;
- углеводы;
- вода;
- соль.

Отображение:

```text
Факт / План
```

Цветовая индикация должна учитывать отклонение от плана.

Точные thresholds требуют отдельного product decision и не считаются утвержденными runtime-правилами.

## 9. Соль

Соль является полноценной nutrition metric.

Для нее действует та же модель plan/fact.

Правила:

- соль имеет plan и fact;
- может назначаться пользователем или тренером в соответствии с access/permission model;
- может действовать постоянно или на отдельную дату;
- участвует в analytics;
- доступна тренеру в допустимом context;
- должна сохраняться в history дня;
- должна входить в report/export сценарии, если эти сценарии включают Food data.

При импорте, если источник не содержит соли, отображается `Не указано`.

Нельзя вычислять отсутствующую соль без отдельного подтвержденного источника данных.

## 10. Добавление данных

Целевые способы:

### 10.1. Вручную

Вводятся:

- калории;
- белки;
- жиры;
- углеводы;
- вода;
- соль.

### 10.2. FatSecret

При наличии отдельной integration implementation данные могут поступать автоматически.

### 10.3. AI/OCR

Концептуально разрешен импорт из скриншотов дневника питания. Пользователь может выбрать до четырех скриншотов дневника питания.

Ожидаемый flow:

```text
screenshots
↓
AI/OCR processing
↓
preview / confirmation
↓
food data persistence
```

После успешной обработки исходные изображения автоматически удаляются. В системе сохраняется текстовая/структурированная информация, полученная после подтверждения пользователем.

## 11. Данные питания

Дополнительный раскрываемый блок может показывать:

- завтрак;
- обед;
- ужин;
- перекусы;
- список продуктов;
- граммовки.

По умолчанию блок может быть свернут.

## 12. История и редактирование

Любой выбранный день должен использовать тот же интерфейс, что и текущий.

Целевой пользовательский flow позволяет:

- изменять КБЖУ;
- изменять воду;
- изменять соль;
- повторно импортировать данные;
- изменять продукты;
- добавлять комментарий.

История не должна теряться из-за редактирования последующих дней.

## 13. План питания

План питания — самостоятельный object.

Минимально содержит:

- author;
- название периода;
- дату начала;
- дату окончания, если есть;
- КБЖУ;
- воду;
- соль;
- описание;
- рекомендации;
- комментарии.

Основная архитектурная модель:

> Нет отдельного mutable объекта «текущий план питания».

При открытии дня система определяет план, действовавший на эту дату.

Это сохраняет историческую корректность.

## 14. Индивидуальные дни

Поверх основного плана могут существовать назначения на конкретную дату:

- читмил;
- рефид;
- загрузка углеводами;
- слив воды;
- изменение КБЖУ;
- изменение воды;
- изменение соли;
- специальные комментарии.

После окончания даты дневное исключение не должно автоматически изменять основной план периода.

## 15. Самостоятельный пользователь и тренер

Целевой принцип:

- без тренера пользователь управляет своими планами;
- с тренером тренер получает право создавать/изменять планы в рамках permissions.

Ownership остается у пользователя.

## 16. Canonical source

Food является каноническим источником nutrition data для:

- Analytics;
- Reports;
- допустимого coach access;
- будущего feedback;
- cross-period comparison.

Другие модули не создают независимые копии Food data.

## 17. Аналитика

Целевая аналитика может включать:

- средние калории;
- средний белок;
- средний жир;
- средние углеводы;
- среднюю воду;
- среднюю соль;
- динамику plan/fact;
- сравнение периодов.

## 18. MVP и deferred

Актуальный CURRENT MVP прямо исключает полноценный Food module, FatSecret и AI nutrition analysis из обязательного MVP scope.

Поэтому эти возможности являются post-MVP target и не должны быть записаны как current runtime.

## 19. Архитектурные требования

- unique ID у food records/plans;
- historical data сохранены;
- no duplicate source of truth;
- backend является окончательной точкой контроля;
- provider integrations подключаются через отдельные service/adapter boundaries;
- расширение nutrition metrics не должно ломать существующие записи;
- для каждого day record сохраняются source и время последнего изменения;
- если дата окончания основного плана не задана, он считается действующим до появления следующего плана.
