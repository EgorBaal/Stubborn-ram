# PHOTO_AND_MEASUREMENTS

**Статус документа:** CANONICAL MODULE DOCUMENT  
**Версия:** 1.0  
**Текущее runtime-состояние:** PARTIALLY IMPLEMENTED

## 1. Назначение

Photo & Measurements предназначен для периодического объективного контроля изменения формы тела.

Главная единица домена:

> КОНТРОЛЬНАЯ ТОЧКА

Фотография или отдельный замер сами по себе не должны становиться единственной aggregate unit для progress tracking.

## 2. Текущее состояние

Подтверждено:

- route `/app/photos`;
- `PhotosPlaceholderPage`;
- `PhotoUploader`;
- использование общего `mediaService`;
- upload/complete/read/delete media flow.

Не подтверждены как отдельный domain:

- measurements backend;
- контрольные точки persistence;
- сравнение контрольных точек;
- dedicated photo domain tables;
- полноценный production lifecycle.

## 3. Целевая частота

Модуль предназначен для периодического контроля:

- раз в неделю;
- раз в две недели;
- раз в месяц;
- по тренерскому расписанию.

Точная частота может задаваться policy/coach plan.

## 4. Целевая структура экрана

```text
Календарь
↓
Цель периода
↓
План на сегодня (если существует)
↓
Последняя контрольная точка
↓
Создать контрольную точку
↓
История контрольных точек
↓
Tab Bar
```

## 5. Календарь

Дни, в которые создана контрольная точка, могут отмечаться отдельным indicator.

Нажатие на дату открывает контрольную точку выбранного дня.

История не должна требовать отдельного duplicate history screen.

## 6. Цель периода

Целевая карточка может содержать:

- название периода;
- сроки;
- описание;
- комментарии;
- рекомендации;
- задачи.

Режим назначения зависит от coach/access/permission context.

## 7. План на сегодня

Показывается только при наличии специальных задач, например:

- выполнить контрольную точку;
- сделать обязательные фото;
- сделать дополнительные фото;
- выполнить назначенные замеры;
- добавить комментарий.

При отсутствии задач карточка скрывается. При наличии задача должна визуально выделяться.

## 8. Последняя контрольная точка

Целевая summary card:

- дата;
- количество фотографий;
- количество замеров;
- вес;
- наличие комментария;
- наличие видео.

Вес не должен копироваться в Photo domain: он приходит из canonical Weight record.

## 9. Создание контрольной точки

Контрольную точку можно заполнять постепенно.

Целевой flow:

- вес;
- фото;
- замеры;
- необязательное видео;
- комментарий.

Не требуется заполнять все поля одновременно.

Можно:

- начать;
- выйти;
- вернуться;
- продолжить.

Не требуется искусственный progress percentage, если продукт не примет его отдельным решением.

## 10. Вес

Вес является canonical data Weight domain.

Photo & Measurements не хранит вторую копию веса.

Если веса за соответствующий день нет, UI должен сообщить об этом и предложить перейти в Weight.

## 11. Базовые фотографии

Целевые фиксированные containers:

- Фронт расслаблен;
- Правый бок;
- Спина;
- Левый бок.

Каждый container имеет постоянный внутренний ID.

Это позволяет сопоставлять одну и ту же позу между контрольными точками.

## 12. Дополнительные фотографии

Пользователь может добавлять дополнительные photo containers.

Примеры:

- двойной бицепс спереди;
- двойной бицепс сзади;
- Side Chest;
- Side Triceps;
- пресс;
- вакуум;
- собственные позы.

Дополнительные containers также имеют собственные IDs.

## 13. Стандарт съемки

Через `ⓘ` можно показывать рекомендации:

- одинаковый свет;
- одинаковое расстояние;
- одинаковая одежда;
- одинаковая поза;
- одинаковая высота камеры;
- отсутствие пампа, если это требуется для сравнения.

## 14. Скрытие лица

Целевой продуктовый flow:

1. Пользователь выбирает «Скрыть лицо».
2. Открывается простой встроенный редактор.
3. Пользователь включает скрытие.
4. Перемещает область.
5. Изменяет размер.
6. Подтверждает.

Используется обычное blur/masking behavior без AI requirement.

Это target UX, а не подтвержденная текущая runtime capability.

## 15. Видео

К контрольной точке может быть привязано одно необязательное видео.

Назначение:

- позирование;
- форма в движении;
- обязательные позы;
- оценка пластики.

Видео принадлежит контрольной точке и использует общий Media layer.

## 16. Замеры

Целевой стандартный список может включать:

- шея;
- грудь;
- талия;
- таз;
- бедро;
- голень;
- плечо;
- предплечье.

Для каждого доступного измерения может быть `ⓘ` с:

- схемой;
- местом измерения;
- инструкцией.

Без coach context пользователь выбирает необходимые замеры.

При coach context обязательный/рекомендуемый набор может назначаться тренером. Пользователю отображаются только выбранные/назначенные показатели.

## 17. Комментарий

Контрольная точка может содержать comment, например:

- завершение этапа;
- после болезни;
- после соревнований;
- особенности подготовки;
- личные заметки.

## 18. История контрольных точек

История отображает даты и наличие:

- фото;
- замеров;
- веса;
- видео;
- комментария.

Нажатие открывает полную контрольную точку.

## 19. Сравнение

Любую контрольную точку можно сравнить со второй.

Целевой comparison mode показывает:

- две даты;
- одинаковые базовые фотографии напротив друг друга;
- одинаковые дополнительные фотографии;
- замеры рядом;
- вес;
- комментарии.

Сопоставление фотографий выполняется по стабильным container IDs.

## 20. Ownership и coach access

Пользователь остается владельцем своих данных.

Тренер получает доступ через relationship/permissions.

Архитектурно:

```text
User ownership
↓
Control point
↓
coach read/feedback access
```

Текущий relationship runtime еще не реализован полностью.

## 21. Analytics и Reports

Canonical data контрольных точек в дальнейшем используется:

- Analytics;
- Reports;
- comparison;
- coach review.

Дублирование фотографий/веса/замеров между модулями запрещено как принцип.

## 22. Media integration

Текущий runtime использует общий media subsystem.

Целевой поток:

```text
Photo/Video UI
↓
mediaService
↓
apiClient
↓
Media API
↓
Private Object Storage
```
