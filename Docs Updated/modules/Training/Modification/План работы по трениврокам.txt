ТЕКУЩАЯ ТОЧКА РАБОТЫ ПО TRAINING

На 07.10.2026 основная техническая часть Exercise Info реализована, а
унификация exercises.category для системных и личных упражнений выполнена
локально и проверена.

В текущем цикле отдельно прорабатывается архитектура сохранения Workout и
материалов во время ведения тренировки. Принято продуктовое решение: тренировка
создаётся в БД сразу при начале новой тренировки и далее автоматически
сохраняется по мере изменений. Пользователь не должен видеть отдельный статус
«незавершённая тренировка».

Для клиента тренировка должна восприниматься как одна постоянно сохраняемая
сущность: упражнения, подходы, параметры, суперсеты, комментарии и другие
изменения автоматически сохраняются. Фото, видео и голосовые материалы также
должны загружаться и связываться с реальными сохранёнными Workout/WorkoutSet
по мере их добавления.

Кнопка «Завершить» не должна быть единственным моментом сохранения. Её
пользовательский смысл — закончить работу с текущей тренировкой и выйти из неё;
к этому моменту данные уже должны быть сохранены. Если приложение закрыто,
смахнуто, телефон выключен или произошёл сбой, ранее успешно сохранённые
данные не должны теряться. Для дополнительной надёжности предусматривается
локальная страховка состояния и синхронизация после восстановления связи.

Основной механизм autosave должен быть событийным с коротким debounce, а не
обязательным запросом каждые 5–10 секунд после каждого изменения. Дополнительно
может использоваться периодический страховочный autosave. Это решение принято
для снижения лишних API/DB операций без ухудшения UX.

При этом полная реализация данного lifecycle ещё не выполнена и не считается
закрытой задачей. До реализации необходимо отдельно спроектировать и
проверить создание Workout/WorkoutSet в БД сразу при начале тренировки,
autosave, восстановление после закрытия/сбоя, локальную страховку и
синхронизацию.

Также в ходе сквозной проверки материалов Training выявлены две независимые
проблемы, которые пока не исправлены:
1) текущий frontend может обращаться к материалам с временным setId, которого
ещё нет в workout_sets PostgreSQL;
2) отдельная загрузка media в Object Storage/S3 сейчас имеет ошибку на этапе
signed upload URL (PUT, 404/ERR_ABORTED).

Это означает, что текущая frontend-стабилизация lifecycle материалов не
считается полностью принятой до устранения/проверки этих проблем. Backend/API/
DB/media architecture в ходе диагностики не изменялись.

Следующие незавершённые задачи: завершить Media для Exercise, INFO-вход из
TrainingExerciseCard, возврат в исходный контекст, Progress, спроектировать и
реализовать новый autosave lifecycle Workout, затем перейти к полноценной
реализации Templates и выполнить сквозные проверки.

Это уточнение не закрывает T8/T9/T25/T26/T27/T28/T29/T31: они остаются частично
выполненными до прохождения соответствующих сквозных проверок.

======================================================================
5. ЗАФИКСИРОВАННЫЕ РЕШЕНИЯ ПО TRAINING
======================================================================

Этот раздел содержит принятые архитектурные и продуктовые решения. Он
является рабочей фиксацией решений, а не новым альтернативным планом.

  -------------------------------------
  5.1. КАНОНИЧЕСКАЯ МОДЕЛЬ ТРЕНИРОВКИ
  -------------------------------------

Каноническая модель:

Workout → WorkoutExercise → WorkoutSet

WorkoutExercise ссылается на Exercise через exercise_id.

Название упражнения не является идентификатором связи.

  ------------------------------------
  5.2. СИСТЕМНЫЕ И ЛИЧНЫЕ УПРАЖНЕНИЯ
  ------------------------------------

Используется одна таблица exercises.

Системное упражнение: user_id = NULL

Личное упражнение: user_id = UUID текущего пользователя

Пользователь видит: - все системные упражнения; - только свои личные
упражнения.

Чужие личные упражнения пользователю не выдаются.

  --------------------------------------------------
  5.3. EXERCISE INFO — ОДНА СУЩНОСТЬ, РАЗНЫЕ ДВЕРИ
  --------------------------------------------------

Exercise Info является одной страницей и одной сущностью:

/app/training/exercises/:id

К ней ведут разные точки входа.

Дверь №1: Каталог упражнений → клик по упражнению → Exercise Info

Дверь №2: TrainingExerciseCard → кнопка INFO / i → тот же Exercise Info

Не создаются две отдельные страницы информации об упражнении.

Кнопка закрытия/назад должна возвращать пользователя в исходный
контекст: - из каталога → обратно в каталог; - из тренировки → обратно в
ту же тренировку.

  ------------------------------
  5.4. СТРУКТУРА EXERCISE INFO
  ------------------------------

Целевая минимальная структура страницы:

1.  Название упражнения.
2.  Кнопка закрытия.
3.  Большое горизонтальное видео.
4.  Категория.
5.  Основные мышцы.
6.  Дополнительные мышцы.
7.  Описание упражнения.
8.  Кнопка Progress.

Категория и основные/дополнительные мышцы отображаются как выделенные плитки.
Если массив мышц пустой, соответствующие пустые значения не выводятся.

Страница не должна превращаться в перегруженную энциклопедию упражнения.

  ----------------------------------
  5.5. РАСШИРЕННАЯ МОДЕЛЬ EXERCISE
  ----------------------------------

В exercises добавлены nullable-поля:

description TEXT NULL primary_muscles TEXT NULL secondary_muscles TEXT
NULL

Существующие системные упражнения пока не заполняются массово. Сначала
готовится техническая инфраструктура, затем выполняется наполнение.

  -----------------------------------------
  5.6. ЛИЧНОЕ УПРАЖНЕНИЕ — РЕДАКТИРОВАНИЕ
  -----------------------------------------

Личное упражнение не должно оставаться навсегда пустым.

Системное упражнение: только просмотр.

Личное упражнение владельца: просмотр + редактирование.

Редактируемые данные личного упражнения: - название; - основная мышечная
группа; - дополнительные мышечные группы; - описание; - видео.

Редактирование должно выполняться через Backend API и обязательно
проверять ownership.

Системные упражнения нельзя редактировать обычному пользователю. Чужие
личные упражнения нельзя редактировать.

  -------------------------
  5.7. MEDIA ДЛЯ EXERCISE
  -------------------------

Видео упражнения не хранится как файл внутри React и не должно
превращать таблицу exercises в хранилище бинарных данных.

Используется существующая Media Architecture:

Exercise → Media relation → Media API → Object Storage / S3

Бинарный файл хранится в Object Storage.

PostgreSQL хранит метаданные и связи.

Целевой пользовательский сценарий: добавить видео → загрузить/связать
через Media API → сохранить связь с Exercise → отображать видео в
Exercise Info.

В качестве дальнейшего расширения допускается поддержка внешней ссылки
на видео, но она не должна ломать основную Media Architecture.

  ---------------
  5.8. PROGRESS
  ---------------

Progress не хранится как отдельное статическое поле Exercise.

Прогресс рассчитывается по истории выполнения упражнения:

Exercise → WorkoutExercise → Workout → WorkoutSet

Кнопка Progress является входом в отдельный экран/раздел прогресса
упражнения.

Сам экран Progress реализуется отдельным этапом после базового Exercise
Info.

  -----------------------------------
  5.9. ШАБЛОНЫ — ОТДЕЛЬНАЯ СУЩНОСТЬ
  -----------------------------------

Template является сохранённым blueprint тренировки.

Template не является Workout и не является записью History.

Целевая отдельная структура:

users → training_templates → training_template_exercises →
training_template_sets

Workout и Template не должны делить одну и ту же запись состояния.

Выбор шаблона создаёт независимую новую тренировку.

Изменение новой тренировки не меняет исходный шаблон.

Один шаблон можно использовать повторно.

  -------------------------------
  5.10. ДАТА И ВРЕМЯ ТРЕНИРОВКИ
  -------------------------------

В Workout используются отдельные значения:

training_date start_time end_time

Время хранится как TIME, дата — как DATE.

Для существующей истории не должны автоматически появляться текущие часы
у старых тренировок.

Текущее время устройства используется только при создании новой
тренировки, если это предусмотрено UI.

  --------------------------------
  5.11. TRAINING UI И СОХРАНЕНИЕ
  --------------------------------

Training History показывает сохранённые Workout из БД.

Training Builder создаёт/редактирует Workout.

Training Templates будут работать через отдельную сущность Template.

Exercise Picker выбирает существующее Exercise или создаёт личное
Exercise.

Свободный ввод названия упражнения в карточке тренировки не
используется: упражнение выбирается через каталог/Exercise Picker.

  -----------------------------------------------
  5.12. АВТОСОХРАНЕНИЕ ТЕКУЩЕЙ ТРЕНИРОВКИ
  -----------------------------------------------

Принято продуктовое решение: Workout создаётся в PostgreSQL сразу после
создания новой тренировки. Пользователь не должен ждать кнопки «Завершить» для
первичного сохранения данных.

Workout и его WorkoutSet должны существовать в БД до добавления к ним
фотографий, видео, голосовых и других материалов. Это устраняет ситуацию,
когда frontend использует UUID подхода, которого ещё нет в workout_sets.

Во время тренировки изменения автоматически синхронизируются с Backend:
- добавление/удаление упражнения;
- добавление/удаление подхода;
- изменение веса, повторений, времени и других параметров;
- суперсеты и другие связи, предусмотренные моделью;
- комментарии;
- другие данные текущего Workout.

Основной механизм сохранения: изменение → короткий debounce → сохранение.
Периодический autosave может использоваться как дополнительная страховка, но
не должен превращаться в постоянную отправку одного и того же состояния
каждые 5–10 секунд.

Для защиты от кратковременной потери сети/сбоя предусматривается локальная
копия текущего состояния и последующая синхронизация после восстановления
соединения.

Для пользователя не вводится отдельная сущность/экран «Незавершённая
тренировка». Workout остаётся обычной тренировкой. Если пользователь просто
закрыл/смахнул приложение или выключил телефон, ранее сохранённое состояние
остаётся доступным. Кнопка «Завершить» является действием выхода из текущей
тренировки, а не единственной операцией сохранения.

После начала тренировки медиа могут привязываться непосредственно к уже
существующим Workout/WorkoutSet. Фото, видео и голосовые загружаются через
существующую Media Architecture, а PostgreSQL хранит метаданные и связи.

Точная реализация autosave, локальной страховки, восстановления после сбоя и
правил синхронизации ещё не реализована и требует отдельного технического
этапа. Это решение не разрешает менять API/DB без отдельного проектирования и
проверки.

  ---------------------------------
  5.13. FRONTEND API ARCHITECTURE
  ---------------------------------

Frontend не обращается к Backend напрямую из компонентов.

Каноническая цепочка:

Component / Page → соответствующий service → общий apiClient → Backend
API → Fastify → PostgreSQL / Media / Object Storage

Для Training используется trainingService.

Для Media используется mediaService.

Прямые fetch к Backend внутри Training UI не используются.

  --------------------------
  5.14. LOCAL / PRODUCTION
  --------------------------

Development и Production используют разные API endpoints через .env.

Development: локальный Backend.

Production: https://api.stubbornram.ru/api

Архитектура приложения при этом не меняется.
