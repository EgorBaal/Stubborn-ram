# ACTIVITY --- текущая прототипная версия и состояние модуля

**Дата фиксации:** 2026-10-01\
**Статус:** FRONTEND UI PROTOTYPE / БОЛВАНКА\
**Важно:** это НЕ конечная production-версия Activity. Это промежуточный
визуальный и UX-образец, созданный для того, чтобы было от чего
отталкиваться при дальнейшем проектировании.

## 1. Источник требований

Канонический документ: - `ACTIVITY.md`.

Целевой Activity domain включает: - steps; - cardio; - extra activity; -
daily goals; - period goals; - Apple Health; - Health Connect; - manual
input.

Текущая frontend-болванка реализует только локальный UI и локальные
состояния.

## 2. Что было сделано

Созданы/изменены только файлы внутри Activity: -
`src/modules/activity/ActivityPage.jsx`; -
`src/modules/activity/ActivityPage.css`; -
`src/modules/activity/ActivityPlaceholderPage.jsx`.

Route `/app/activity` уже существовал, поэтому Router не менялся.

Training, Weight, Nutrition, AppLayout, Home, backend и другие модули в
этой итерации не изменялись.

## 3. Визуальная основа

Для Activity использовался предоставленный визуальный референс.

Референс задавал: - календарь; - цель периода; - план на сегодня; -
шаги; - кардио; - дополнительную активность; - кнопку добавления
активности; - centered detail/add overlays.

При этом: - существующий shell Stubborn Ram сохраняется; - существующий
нижний Tab Bar не дублируется; - данные из референса не используются как
реальные пользовательские данные.

## 4. Основной экран

Текущая композиция:

1.  Header «Активность».
2.  Календарь.
3.  Цель периода.
4.  План на сегодня --- только если существует назначение.
5.  Шаги.
6.  Кардио.
7.  Дополнительная активность.
8.  `+ Добавить активность`.
9.  Существующий Tab Bar приложения.

Selected date является центральным состоянием экрана.

## 5. Календарь

В Activity есть: - компактный календарь; - выбор даты; - month picker; -
выбранный день.

Выбор даты должен менять все данные экрана на выбранный день.

Календарь сделан локально внутри Activity.

Training использовался как UX/architecture reference, но Training не
изменялся.

## 6. Empty state

Стартовое состояние специально очищено.

Сейчас: - Цель периода: `Не задана`; - План на сегодня: полностью скрыт,
потому что назначений нет; - Шаги: `0`; - цель шагов: не задана; -
источник: `Не подключён`; - прогресс: `0%`; - Кардио: `0 мин`,
`План не задан`; - Дополнительная активность: `0 мин`, `Нет записей`; -
кнопка: `+ Добавить активность`.

Fake/seed данные не добавлялись.

В частности, значения из визуального референса не переносились в
приложение.

## 7. Локальная data model

В текущем прототипе локально разделены: - `selectedDateKey`; -
`periodGoal`; - `dailyPlans`; - `steps`; - `cardio`; -
`extraActivities`; - UI state для modal/picker/add forms.

Все данные по умолчанию пустые.

Это прототипная модель. Она НЕ является финальной backend/data model.

## 8. Goal

Есть локальная цель периода.

Empty state: - `Не задана`.

В UI предусмотрена работа с goal через modal.

Точная production-связь с trainer assignments, permissions и backend ещё
не реализована.

Canonical Activity предусматривает period goals, но текущий UI не
следует считать окончательной моделью прав и назначений.

## 9. Daily plan

План на конкретный день существует как отдельная концепция.

Основной экран: - ищет plan для selected date; - показывает карточку
только при наличии назначения; - при наличии плана использует
alert-визуализацию.

В empty state plan скрыт.

Нельзя считать текущую локальную модель production implementation of
trainer assignments.

## 10. Steps

Текущий UI предусматривает: - фактические шаги; - цель шагов; - процент
выполнения; - источник данных.

Empty state: - `0`; - цель не задана; - источник не подключён; - `0%`.

В canonical Activity предусмотрены источники: - Apple Health; - Health
Connect; - manual input.

Реальные интеграции в прототипе НЕ реализованы.

## 11. Cardio

В UI есть отдельный блок Cardio.

В пустом состоянии: - `0 мин`; - `План не задан`.

Референс предусматривает: - план; - факт; - тип кардио; -
длительность; - комментарий; - недельное планирование.

Текущий прототип не следует считать завершённой production cardio model.

## 12. Extra Activity

В UI есть: - дополнительная активность; - суммарная длительность; -
количество записей; - добавление активности через modal.

Empty state: - `0 мин`; - `Нет записей`.

Реальные записи в стартовом состоянии отсутствуют.

## 13. Add Activity

Предусмотрена кнопка: - `+ Добавить активность`.

Есть centered modal для добавления.

Это локальный frontend сценарий.

Backend persistence и production data flow не реализованы.

## 14. Scroll architecture

Это обязательная часть текущего прототипа.

Activity построен по принципу Training Builder:

``` text
фиксированный shell
↓
fixed top area
↓
.activity-content
↓
внутренний scroll
↓
фиксированный Tab Bar
```

Основной scroll-контейнер: - `.activity-content`.

Используются: - `flex: 1`; - `min-height: 0`; - `overflow-y: auto`.

Проверено: - body не должен скроллиться; - document не должен
скроллиться; - scroll должен происходить внутри Activity.

## 15. Важная история с нижней геометрией

В процессе разработки была обнаружена проблема:

сначала между последним блоком и Tab Bar появлялось слишком большое
пустое пространство.

Первый фикс прижал кнопку «Добавить активность» вниз, но создал другой
визуальный недостаток: слишком большой gap между «Дополнительная
активность» и кнопкой.

После этого была поставлена отдельная задача на перераспределение
свободного пространства.

Это важно сохранить как контекст: текущая геометрия Activity была
несколько раз корректирована и НЕ должна автоматически считаться
окончательной.

При возвращении нужно снова посмотреть реальный экран и CSS, а не
полагаться только на старый отчёт.

## 16. Centered overlays

В прототипе проверены centered overlays для: - цели периода; -
добавления активности; - выбора даты.

Bottom sheet не использовался.

## 17. Русский язык / UTF-8

## 18. Build

Это подтверждает только сборку текущего прототипа, а не production
readiness.

болванка.

Она нужна для: - проверки будущей композиции; - проверки календаря; -
проверки selected date; - проверки empty state; - проверки внутреннего
scroll; - проверки базовых карточек; - проверки modal UX.
