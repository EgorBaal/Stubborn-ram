# ACTIVITY

**Статус документа:** CANONICAL MODULE DOCUMENT  
**Версия:** 1.0  
**Актуальность runtime:** по состоянию на 19.09.2026  
**Текущее состояние:** PLACEHOLDER / FRONTEND-ONLY

## 1. Назначение

Модуль Activity предназначен для учета общей физической активности пользователя вне и вокруг тренировочного процесса.

Основные задачи домена:

- учитывать ежедневное движение;
- учитывать шаги;
- учитывать кардио;
- учитывать дополнительную активность;
- использовать данные активности для последующей аналитики;
- в будущем давать тренеру основу для корректировки тренировочного объема и питания.

Activity не является заменой Apple Health, Google Fit, Garmin и аналогичных систем. Внешние health-источники могут использоваться как источники данных, но Stubborn Ram хранит только данные, необходимые для собственного продукта и coaching-flow.

## 2. Текущее состояние

В текущем runtime подтверждено:

- маршрут `/app/activity`;
- `ActivityPlaceholderPage`;
- переход в модуль из Home.

Не подтверждено и не реализовано как самостоятельный backend domain:

- календарная история активности;
- persistence Activity;
- отдельные сущности шагов/кардио/дополнительной активности;
- backend API Activity;
- тренерские назначения Activity;
- activity analytics.

Следовательно, наличие маршрута и экран-заглушки не считается реализацией домена.

## 3. Целевая структура экрана

Целевой экран Activity:

```text
Календарь
↓
Цель периода
↓
План на сегодня (если существует)
↓
Шаги
↓
Кардио
↓
Дополнительная активность
↓
Добавить активность
↓
Tab Bar
```

Отдельной страницы «История активности» не требуется: история строится через календарь и выбор конкретного дня.

## 4. Календарь

Для любого выбранного дня используется один и тот же экран дня активности.

Правила:

- любой день открывается нажатием;
- сегодняшний, вчерашний и прошлые дни имеют одну и ту же структуру;
- данные не должны зависеть от того, открыт ли «сегодня» или исторический день;
- календарь является основным способом просмотра истории Activity.

## 5. Цель периода

Под календарем может отображаться текущая цель периода.

Примеры:

- повседневная активность;
- повышенная активность;
- снижение активности;
- подготовка к соревнованиям;
- восстановительный период.

Карточка цели содержит:

- название периода;
- даты действия или признак бессрочного периода;
- кнопку «Подробнее».

В раскрытой части могут отображаться:

- описание этапа;
- рекомендуемый диапазон шагов;
- рекомендации по кардио;
- комментарии пользователя;
- комментарии тренера.

Право назначения должно определяться общей access/permission model, а не UI.

## 6. План на сегодня

Карточка отображается только при наличии специальных назначений для выбранного дня.

Примеры:

- увеличить количество шагов;
- добавить кардио;
- уменьшить активность;
- исключить кардио;
- добавить специальный комментарий.

При отсутствии индивидуальных назначений карточка скрывается. При наличии она должна визуально выделяться среди обычных блоков.

## 7. Шаги

Шаги являются главным показателем Activity.

Целевой UI должен отображать:

- фактическое количество шагов;
- назначенное количество;
- отношение факт / план;
- визуальный индикатор выполнения;
- источник данных.

Пример:

```text
8742 / 10000
```

Поддерживаемые источники в целевой концепции:

- Apple Health;
- Health Connect (Android);
- ручной ввод.

При отсутствии автоматической синхронизации пользователь должен иметь возможность внести значение вручную.

## 8. Кардио

Кардио является отдельной сущностью/типом активности и не смешивается со шагами.

Целевой сценарий:

- кардио может быть назначено пользователем или тренером;
- назначения могут быть привязаны к дням;
- на главном экране отображается краткий итог;
- при открытии дня отображаются план и факт.

План содержит:

- вид кардио;
- назначенную длительность;
- комментарии.

Факт содержит:

- фактический вид кардио;
- фактическую длительность.

Дополнительное кардио сверх плана не должно теряться.

Пример:

```text
План: 30 минут
Факт: 45 минут
```

## 9. Дополнительная активность

Используется для учета любой активности вне тренировок и отдельного cardio-flow.

Примеры:

- футбол;
- баскетбол;
- теннис;
- поход;
- прогулка в горах;
- переезд;
- физическая работа;
- другая энергозатратная деятельность.

Для каждой записи:

- название;
- длительность;
- необязательный комментарий.

На основном экране достаточно показывать суммарную длительность, а внутри дня — список записей.

Добавление выполняется вручную.

## 10. Добавление активности

При действии «Добавить активность» пользователь выбирает:

- Кардио;
- Дополнительная активность.

Для кардио:

- тип;
- длительность;
- комментарий.

Для дополнительной активности:

- свободное название;
- длительность;
- комментарий.

## 11. Пользователь и тренер

Архитектурный принцип:

```text
Самостоятельный пользователь ↔ Пользователь с тренером
```

Целевой режим без тренера:

- пользователь сам задает целевые значения;
- пользователь сам создает записи;
- пользователь редактирует собственные назначения.

Целевой режим с тренером:

- тренер создает назначения;
- пользователь видит назначения;
- пользователь вносит фактические данные;
- редактирование тренерских назначений пользователем запрещается, если это не разрешено отдельным permission.

Эта модель является TARGET и не должна интерпретироваться как текущий runtime relationship engine.

## 12. Данные и persistence

Каждая самостоятельная запись Activity должна иметь уникальный внутренний ID.

История должна сохраняться бессрочно в рамках действующей lifecycle policy.

Прошлые записи не изменяются автоматически из-за появления более новых данных.

Данные должны быть пригодны для аналитики и отчетов без создания второго независимого источника истины.

Целевая модель должна оставаться расширяемой.

## 13. Расширяемость кардио

Минимальный первоначальный набор:

- тип кардио;
- длительность.

Структура должна допускать последующее добавление:

- дистанции;
- темпа;
- пульса;
- дополнительных параметров;
- комментариев.

Расширение не должно ломать существующие записи.

## 14. Аналитика и уведомления

Activity должен предоставлять canonical data для аналитики.

Целевые показатели:

- среднее количество шагов;
- выполнение плана шагов;
- число кардио;
- длительность кардио;
- количество дополнительной активности;
- суммарная длительность активности;
- динамика за выбранный период.

Целевые in-app сигналы могут включать:

- осталось пройти заданное количество шагов;
- кардио еще не выполнено;
- план активности выполнен.

На текущем этапе отдельного backend-driven notification flow нет.

## 15. Интеграции
