# WEIGHT --- текущая прототипная версия и состояние модуля

**Дата фиксации:** 2026-10-01\
**Статус:** FRONTEND UI PROTOTYPE / БОЛВАНКА\
**Важно:** это НЕ конечная production-версия Weight. Этот файл нужен как
временная точка возврата: он описывает то, что было сделано в текущем
прототипе, какие решения были приняты визуально и технически, и что
обязательно нужно перепроверить перед дальнейшей разработкой.

## 1. Источник требований

Канонический документ модуля --- `WEIGHT.md` / актуальная версия
документа Weight.

По документу Weight предусматривает: - календарь; - несколько измерений
в день; - primary measurement rule; - историю; - графики; - цели; -
аналитику; - дальнейшую интеграцию с другими progress-модулями.

Канонический Weight является источником данных о массе тела для
связанных доменов.

Важно: canonical-документ и текущая frontend-болванка --- не одно и то
же. Документ описывает целевую модель, а текущая реализация является
только локальным UI-прототипом.

## 2. Что реально было сделано в текущей болванке

Создан/изменён локальный Weight UI: -
`src/modules/weight/WeightPage.jsx` -
`src/modules/weight/WeightPage.css` - `WeightPlaceholderPage.jsx`
использовался как вход в страницу в процессе работы.

Текущая болванка работает frontend-only.

Backend, API, PostgreSQL, persistence и service layer для Weight в этой
работе не подключались.

## 3. Текущая структура экрана

Основной экран Weight был собран как компактный dashboard:

1.  Верхняя часть с названием «Вес» и action-кнопкой.
2.  Компактный календарь.
3.  Цель периода.
4.  План на выбранный день.
5.  Главный показатель текущего веса.
6.  Записи выбранного дня.
7.  Динамика веса.
8.  История изменений.

Календарь является центральной точкой выбора даты.

## 4. Календарь

В прототипе: - показывается компактная неделя; - выбранная дата влияет
на содержимое Weight; - заголовок месяца открывает отдельный календарный
modal; - точки под датами были убраны; - month picker сделан локально
внутри Weight.

В качестве UX-референса использовался календарь Training, но
Training-файлы не изменялись.

## 5. Measurements --- основная локальная модель

В текущем прототипе `measurements` является единым локальным источником
для связанных блоков Weight.

Одна запись измерения содержит, по текущей реализации: - дату; -
время; - вес; - комментарий; - идентификатор/локальную сущность записи.

Из этого одного набора должны получать данные: - Today / записи
выбранного дня; - Current Weight; - History; - Graph.

Это важное решение: эти блоки НЕ должны в дальнейшем получать данные из
независимых fake/mock-массивов.

## 6. Несколько измерений в один день

В прототипе сохранено поведение: - несколько измерений в один день не
перезаписывают друг друга; - каждая запись отображается отдельно; -
запись можно открыть; - запись можно удалить.

## 7. Primary measurement rule

В текущей версии сохранялась логика canonical Weight: - сначала
используется первое измерение типа `Утром натощак`; - если такого
измерения нет, используется первое измерение дня.

Это обязательно перепроверить при следующем возвращении к Weight, потому
что текущая UI-болванка не является production data implementation.

## 8. Current Weight

На главном экране текущий вес сделан главным визуальным показателем.

В пустом состоянии: - `— кг`.

При наличии локальных измерений значение рассчитывается из текущего
локального набора данных.

Отдельно проверить при возвращении: - поведение для выбранной даты; -
что происходит, если в выбранный день нет записи; - использование
последнего известного веса; - соответствие primary measurement rule; -
границы между «вес за день» и «последний известный вес».

## 9. Goal

В UI предусмотрена цель периода.

Модель прототипа содержит: - название; - комментарий; - дату начала; -
дату окончания либо бессрочный режим.

На главном экране цель представлена компактной кликабельной ячейкой.

Пустое состояние: - `Не задана`.

Подробности открываются в centered modal.

Это пока только локальная frontend-модель и не является production goal
system.

## 10. Plans

В UI предусмотрены планы, привязанные к конкретным датам.

Основной экран получает план для selected date.

Если план существует, он визуально выделяется alert-состоянием.

Планы предусматривают: - дату; - комментарий; - создание; -
редактирование; - удаление.

План на сегодня/выбранную дату не является отдельной независимой
сущностью экрана --- он должен вычисляться из набора планов по дате.

В пустом состоянии: - план отсутствует.

## 11. Добавление измерения

Предусмотрено centered modal: - поле веса; - точность 0.01 кг; -
необязательный комментарий; - timestamp при сохранении.

После сохранения одна и та же локальная measurement record должна
обновлять: - текущий день; - Current Weight; - History; - Graph.

Записи можно удалять.

## 12. Graph

В прототипе предусмотрен блок «Динамика веса».

Есть отдельный detail modal с периодами: - Неделя; - Месяц; - Год.

График: - строится только из measurements; - не содержит fake points; -
имеет X/Y axes; - имеет точки и соединяющую линию; - Y-axis динамически
масштабируется вокруг фактических данных.

В исходной реализации использовалась логика диапазона вокруг min/max с
запасом примерно ±10 кг и защитой от слишком узкого диапазона.

Обязательно перепроверить график при возвращении: - агрегирование
нескольких измерений одного дня; - отображение всех дат; - отсутствие
искажений при одном/двух измерениях; - Week/Month/Year semantics; -
empty state; - timezone/date boundaries.

## 13. History

Главный экран содержит компактную кнопку/ячейку «История изменений».

По нажатию открывается большой centered modal.

История: - прокручиваемая; - содержит каждое измерение отдельно; -
несколько записей одного дня не объединяются визуально в одну запись.

Важно: в ходе разработки была обнаружена проблема, когда Graph видел
measurements, а History использовал отдельный источник и показывал
`Нет записей`. Это было исправлено концептуально: History должен
использовать тот же `measurements` state.

При следующем возвращении обязательно проверить это ещё раз.

## 14. Empty state

Стартовые fake/seed данные были удалены.

Пустое состояние текущей болванки: - Current Weight: `— кг`; - Goal:
`Не задана`; - Plan: отсутствует/пустой; - Today: `Нет записей`; -
Graph: `Нет данных для построения графика`; - History: `Нет записей`.

Никаких демонстрационных значений вроде 102 кг, 95 кг и т. п. в
стартовом состоянии быть не должно.

## 15. Scroll architecture

Это один из обязательных пунктов для повторной проверки.

Weight использует внутренний scroll-контейнер: - `.weight-scroll`; -
`overflow-y: auto`.

Принцип: - внешний app shell остаётся статичным; - верхняя часть
остаётся на месте; - нижний Tab Bar остаётся на месте; - прокручивается
только внутренняя рабочая область Weight.

В ходе проверки было подтверждено: - document не является длинным
scroll-контейнером; - body не должен скроллиться; - Weight content
скроллится внутри `.weight-scroll`.

В качестве архитектурного референса использовался Training Builder,
особенно `training-builder-content`.

## 16. Overlays

В Weight используются centered modal overlays, а не bottom sheets.

Проверенные сценарии: - Add Record; - Goal detail; - Plan detail; - Day
details; - Graph detail; - History.

Если контента в overlay станет много, сам overlay может иметь внутренний
scroll.

## 17. Важное ограничение текущей версии

Эта версия НЕ является production Weight.

Не считать реализованными только на основании этого прототипа: - backend
persistence; - API; - database model; - authorization; - permissions; -
coach assignments; - analytics; - notifications; - cross-module
integrations; - lifecycle/retention; - production data migration.

Canonical `WEIGHT.md` описывает гораздо более широкий целевой домен.

## 18. Что обязательно проверить при возвращении к Weight

Перед дальнейшей разработкой нужно заново:

1.  Прочитать актуальный `WEIGHT.md`.
2.  Проверить актуальный `SYSTEM_STATE`.
3.  Проверить фактические Weight-файлы в репозитории.
4.  Проверить route.
5.  Проверить, какие изменения появились после этой болванки.
6.  Не считать текущий JSX/CSS окончательной архитектурой.
7.  Проверить data flow.
8.  Проверить selected date.
9.  Проверить primary measurement rule.
10. Проверить current weight.
11. Проверить History ↔ measurements.
12. Проверить Graph ↔ measurements.
13. Проверить goal/plan model.
14. Проверить modal architecture.
15. Проверить внутренний scroll.
16. Проверить empty state.
17. Проверить русский текст/UTF-8.
18. Проверить отсутствие fake data.
19. Проверить build.
20. Только после этого продолжать production implementation.

## 19. Что считать текущим результатом

Текущий Weight --- это **визуальная и UX-болванка для дальнейшего
проектирования**, а не готовый модуль.

Её задача была: - показать будущую композицию; - проверить календарь; -
проверить взаимодействие с датой; - проверить базовые модальные окна; -
проверить локальную модель measurements; - проверить внутренний
scroll; - показать empty state.

Все существующие решения можно пересматривать при следующем этапе, если
они не соответствуют canonical-документам.
