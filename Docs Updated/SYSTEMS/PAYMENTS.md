**Статус документа:** CANONICAL / CURRENT  
**Актуальность фактов:** 19.09.2026  
**Назначение:** единое описание payment/access-source архитектуры Stubborn Ram с жёстким разделением между утверждённой target-моделью и фактически реализованным runtime.

> Payment subsystem в текущем production runtime **не реализован**.

# 3. Основной архитектурный принцип

Платёж не является самим правом доступа.

Платёж подтверждает экономическое событие и создаёт или продлевает соответствующий источник доступа.

Фактическое право пользователя выполнять конкретное действие должно определяться общей системой Access/Permissions.

Целевая цепочка:

```text
Payment
   ↓
Subscription / Payment Record
   ↓
Access Source
   ↓
Access Decision
   ↓
Permission Check
   ↓
Allowed / Denied
```

Критическое правило:

**Frontend не является источником истины по платежу, подписке или полному доступу.**

Frontend не должен самостоятельно решать:

- был ли платёж успешным;
- активна ли подписка;
- закончился ли оплаченный период;
- выполнен ли возврат;
- есть ли у пользователя полный доступ.

---

# 4. Источники полного доступа

Целевая модель предусматривает три независимых источника полного доступа:

```text
Trial
Personal Subscription
Coach-related Access
```

Если хотя бы один соответствующий источник активен, пользователь должен получать полный доступ в рамках общей Access-модели.

Приоритет между источниками не требуется.

Источники должны существовать независимо.

Например:

```text
Personal Subscription ACTIVE
        +
Coach-related Access ACTIVE

=> оба источника сохраняются независимо
```

Отключение одного источника не должно автоматически удалять или изменять другой.

> Это утверждённое правило target-модели, а не подтверждённое текущее runtime-поведение.

---

# 5. Trial

## 5.1 Целевая модель

Trial является бесплатным источником полного доступа.

Целевые правила:

- Trial предоставляется один раз на аккаунт;
- длительность — 10 календарных дней;
- стартует после подтверждения Email и создания профиля;
- автоматически не продлевается;
- не запускается повторно из-за смены устройства;
- не запускается повторно из-за повторного входа.

Факт выдачи Trial должен храниться на сервере и быть привязан к конкретному аккаунту.

## 5.2 Текущий runtime

В текущем runtime полноценная Trial subsystem не подтверждена как реализованная.

Поэтому:

```text
10-day Trial = TARGET RULE
Trial runtime lifecycle = NOT IMPLEMENTED / NOT VERIFIED
```

---

# 6. Личная подписка пользователя

## 6.1 Целевая модель

Personal Subscription предоставляет пользователю самостоятельный полный доступ.

Целевая базовая модель:

- подписка оплачивается пользователем;
- оплачивается отдельный период;
- базовый срок — один календарный месяц;
- автоматического продления в MVP нет;
- после окончания оплаченного периода доступ пересчитывается.

При одновременном наличии личной подписки и coach-related access оба источника существуют независимо.

## 6.2 Данные подписки

Целевая система должна сохранять как минимум:

- пользователя;
- идентификатор подписки;
- тариф;
- дату/время начала;
- дату/время окончания;
- статус;
- связанный платёж;
- сумму;
- валюту.

Расчёт окончания периода должен выполняться на Backend единообразно.

Frontend не вычисляет окончание подписки как источник истины.

---

# 7. Подписка тренера

## 7.1 Целевая модель

Coach Subscription является свойством аккаунта тренера, а не клиента.

Целевая цепочка:

```text
Coach Subscription
        ↓
Active Coach Relationship
        ↓
Client-related Access
```

При наличии действующей подписки тренера и активной связи Coach → Client клиент может получать соответствующий источник полного доступа согласно общей Access-модели.

## 7.2 Границы сущностей

Подписка тренера и связь тренер-клиент — разные сущности.

Подписка тренера не должна быть записана как свойство клиента.

Целевая логика:

```text
Coach
 ├── Coach Subscription
 └── Coach → Client Relationship
                    ↓
               Client Access
```

## 7.3 Сохранение данных

Окончание подписки тренера не должно удалять:

- профиль тренера;
- профиль клиента;
- историю тренировок;
- отчёты;
- переписку;
- медиа;
- другие пользовательские данные.

Данные и история являются отдельным от платежа слоем.

---

# 8. Grace Period тренера

Целевая модель предусматривает grace period для сопровождения тренером:

**72 часа после окончания оплаченного периода тренера.**

Во время grace period существующие активные coach-client relationships продолжают предоставлять соответствующий доступ.

После окончания grace period без продления:

- новые операции, требующие действующей coach subscription, блокируются;
- существующие клиентские данные сохраняются;
- история сохраняется;
- аккаунты не удаляются;
- дальнейший доступ определяется общей Access-моделью.

Grace period относится к целевой бизнес-логике и не является реализованной production feature на текущем этапе.

---

# 9. Календарный месяц

Целевая личная подписка имеет срок действия один календарный месяц.

При создании подписки Backend должен фиксировать:

- дату и время начала;
- дату и время окончания;
- идентификатор платежа;
- идентификатор подписки;
- пользователя;
- тариф;
- сумму;
- валюту;
- статус.

Точное правило вычисления периода должно быть единым на Backend.

Запрещено использовать разную логику расчёта срока на разных frontend-экранах.

---

# 10. Отсутствие автоматического продления в MVP

Целевая MVP-модель:

```text
Active
  ↓
Expired
  ↓
Access Recalculation
```

Автоматическое recurring-поведение не входит в текущую реализацию.

Пользователь должен самостоятельно оформить следующий период.

При этом архитектура должна быть расширяема так, чтобы позднее можно было добавить:

- recurring payments;
- сохранённый платёжный метод у провайдера;
- автоматическое списание;
- retry;
- уведомления;
- отмену автопродления;
- отдельный recurring lifecycle.

---

# 11. Платёжный провайдер

Провайдер не должен быть жёстко встроен в бизнес-логику приложения.

Целевая архитектура:

```text
Payment Service
      ↓
Payment Provider Adapter
      ↓
Provider
```

Такой слой нужен для:

- изоляции provider API;
- унификации внутренних payment contracts;
- снижения связности пользовательских модулей;
- возможности сменить провайдера без переписывания Training/Food/Reports/Chat и других доменов.

В старой утверждённой target-модели для российского рынка рассматривались:

- YooKassa;
- T-Bank acquiring.

Окончательный провайдер должен определяться отдельно перед реализацией с учётом:

- договора;
- комиссии;
- API;
- webhook-механизма;
- возвратов;
- юридических требований;
- требований к хранению и обработке платёжных данных.

На текущем этапе конкретный провайдер не считается интегрированным.

---

# 12. Backend как источник истины

Все критические payment/subscription состояния должны определяться Backend.

Backend является источником истины для:

- результата платежа;
- состояния подписки;
- периода действия;
- возврата;
- изменения access source.

Frontend получает состояние, а не вычисляет его заново.

Целевая модель:

```text
Provider Event
      ↓
Backend
      ↓
Payment State
      ↓
Subscription State
      ↓
Access Source
      ↓
Permission Decision
```

---

# 13. Webhook

После подключения провайдера Backend должен принимать серверные уведомления о событиях платежной системы.

Типовые события:

- успешная оплата;
- отмена;
- failed payment;
- возврат;
- истечение;
- изменение состояния платежа;
- другие события выбранного провайдера.

Webhook должен проходить:

1. проверку подлинности;
2. проверку структуры;
3. идемпотентную обработку;
4. фиксацию события;
5. обновление payment/subscription state;
6. последующий пересчёт access source.

Повторная доставка одного webhook не должна:

- создавать вторую подписку;
- повторно зачислять один платёж;
- повторно выполнять одно и то же бизнес-изменение.

Webhook processing относится к PLANNED implementation.

---

# 14. Идемпотентность

Платёжные операции должны быть идемпотентными.

Система должна иметь уникальный идентификатор или комбинацию идентификаторов, позволяющую определить, что событие уже обработано.

Особенно важно для:

- webhook;
- повторных payment requests;
- сетевых ошибок;
- refresh страницы;
- повторной отправки запроса;
- повторной доставки provider events.

Идемпотентность должна быть обеспечена Backend, а не frontend-логикой.

---

# 15. Статусы платежа

Payment и Subscription — разные сущности.

Пример целевого lifecycle платежа:

```text
Created
  ↓
Pending
  ↓
Succeeded
  ↓
Refunded
```

Альтернативная ветка:

```text
Created
  ↓
Failed / Canceled
```

Статус платежа не должен непосредственно использоваться frontend как универсальное право доступа.

Backend должен преобразовывать payment state в состояние subscription/access source.

---

# 16. Статусы подписки

Подписка должна иметь собственный lifecycle.

Минимальная целевая модель:

```text
Pending
Active
Expired
Canceled
```

При необходимости могут использоваться дополнительные технические состояния.

Изменение subscription state выполняется на Backend.

---

# 17. Возвраты

Старая утверждённая target-модель предусматривала возможность возврата в течение:

**7 календарных дней.**

Возврат должен выполняться через payment mechanism выбранного провайдера.

После подтверждённого возврата Backend должен:

1. зафиксировать возврат;
2. связать его с исходным платежом;
3. обновить subscription state;
4. пересчитать access source;
5. при необходимости перевести пользователя в ограниченный доступ.

История платежа и возврата не должна удаляться.

> Правило «7 дней» относится к утверждённой target-модели. Это не реализованная production payment feature на текущем этапе.

---

# 18. Частичные возвраты

Целевая data model должна позволять хранить:

- полную сумму платежа;
- сумму возврата;
- дату возврата;
- причину;
- внешний идентификатор операции.

Поддержка частичных возвратов может быть добавлена отдельно, если её потребуют выбранный provider и бизнес-модель.

---

# 19. Что происходит после окончания личной подписки

Целевая Access-логика:

```text
Personal Subscription expired
        ↓
Check other access sources
```

Затем:

```text
Trial active
        → Full Access
```

```text
Coach-related access active
        → Full Access
```

```text
No active source
        → Restricted Access
```

Окончание подписки само по себе не удаляет пользовательские данные.

---

# 20. Ограниченный доступ

Целевая модель предусматривает возможность входа пользователя даже без полного доступа.

В качестве базовых разрешённых действий определены:

- вход в аккаунт;
- просмотр истории;
- просмотр сохранённых данных;
- настройки аккаунта;
- оформление новой подписки.

Создание новых данных и другие операции, требующие полного доступа, должны блокироваться через Access/Permissions.

Важно:

```text
Restricted Access rules = TARGET
Current runtime permission engine = PARTIAL / NOT FULLY IMPLEMENTED
```

Текущая production authorization model в основном опирается на authentication и ownership checks; полноценная payment-derived Access/Permissions engine ещё не реализована.

---

# 21. Отмена подписки

Поскольку target-MVP не использует автоматическое продление:

- отдельная отмена автопродления не требуется;
- пользователь просто не оформляет следующий период;
- текущая подписка завершается в установленную дату.

При будущем recurring billing необходимо отдельно определить:

- отмену автопродления;
- дату окончания текущего оплаченного периода;
- retry failed charges;
- grace period;
- уведомления;
- переходы subscription states.

---

# 22. Уведомления

Целевая система должна поддерживать транзакционные уведомления:

- платёж создан;
- платёж успешно завершён;
- платёж не завершён;
- подписка скоро заканчивается;
- подписка закончилась;
- возврат выполнен.

Email отправляется через серверный Email Service.

Payment module не должен напрямую обращаться к внешнему Email API.

---

# 23. Безопасность платёжных данных

Stubborn Ram не должен хранить данные банковской карты пользователя как собственную payment credential storage.

Целевая модель:

```text
Card Data
   ↓
Payment Provider
```

В Stubborn Ram должны храниться только необходимые данные бизнес-операции, например:

- пользователь;
- сумма;
- валюта;
- статус;
- дата;
- внешний идентификатор;
- тариф;
- данные возврата;
- технические метаданные.

Секретные ключи payment provider:

- хранятся только на Backend/серверной инфраструктуре;
- не передаются во frontend;
- не должны попадать в Git.

---

# 24. Связь с Permissions

Payment Service не должен непосредственно выдавать разрешение на конкретное действие.

Целевая цепочка:

```text
Payment succeeded
       ↓
Subscription active
       ↓
Access source active
       ↓
Access decision
       ↓
Permission decision
```

Например:

```text
Subscription active
       ↓
Full access
       ↓
Permission: training.create
       ↓
Allowed
```

Payment subsystem является upstream-источником информации для Access-модели, но не заменяет Permission layer.

---

# 25. Связь с Coach-Client Relationship

Coach Subscription принадлежит тренеру.

Client access через тренера требует одновременно:

```text
Coach Subscription Active
        +
Coach → Client Relationship Active
```

Если relationship архивирована, старая связь не должна автоматически продолжать предоставлять новый access source.

Исторические данные клиента сохраняются независимо от состояния платежа тренера.

Полный runtime relationship subsystem сейчас не реализован; поэтому описанная схема является target-моделью.

---

# 26. Целевая модель данных

Базовая логическая модель:

```text
User
 │
 ├── Payment
 │      └── Provider Payment ID
 │
 ├── Personal Subscription
 │
 ├── Trial
 │
 └── Coach Relationship
          │
          └── Coach Subscription
```

Payment и Subscription должны иметь собственные записи.

Недопустимо использовать только:

```text
is_paid = true
```

как единственный источник истины.

Необходимо сохранять историю payment/subscription state changes.

Целевая schema должна предусматривать как минимум зоны:

- payment records;
- subscription records;
- payment → access-source linkage;
- refund data;
- status/event history;
- idempotency information.

Эта schema в текущем production database не реализована.

---

# 27. Аудит платежных операций

Критические операции должны быть журналируемыми.

Минимальная трассировка должна позволять определить:

- кто совершил действие;
- какой платёж затронут;
- какой внешний идентификатор использован;
- состояние до операции;
- состояние после операции;
- время изменения;
- каким серверным событием оно вызвано.

Это необходимо для:

- расследования payment errors;
- спорных операций;
- восстановления истории;
- анализа webhook duplicates;
- поддержки и operational diagnostics.

Audit capability является целевым требованием, а не текущим готовым payment subsystem.

---

# 28. Независимость пользовательских модулей от provider API

Модули не должны напрямую знать API конкретного payment provider.

Это относится к:

- Training;
- Food;
- Activity;
- Reports;
- Photos;
- Measurements;
- Weight;
- Chat;
- Analytics;
- другим feature-модулям.

Целевая цепочка:

```text
Feature Module
      ↓
Access / Permission Decision
      ↓
Subscription / Trial / Coach-related Source
      ↓
Payment subsystem
```

А не:

```text
Training
   ↓
YooKassa API
```

Такое разделение позволяет менять provider без переписывания доменной логики feature-модулей.

---

# 29. Минимальный MVP payment subsystem

Целевая MVP-реализация должна включать:

1. личный тариф;
2. создание платежа;
3. переход пользователя на payment page провайдера;
4. приём webhook;
5. идемпотентную обработку;
6. создание/продление личной подписки;
7. расчёт срока в один календарный месяц;
8. возврат в пределах утверждённого правила;
9. связь subscription с access source;
10. транзакционные уведомления;
11. журналирование payment events.

Не входят в MVP:

- автоматическое продление;
- промокоды;
- рассрочки;
- marketplace;
- сложная product catalog модель;
- multi-provider runtime beyond the required adapter boundary.

---

# 30. Подготовка к масштабированию

Target-архитектура должна позволять добавить:

- несколько тарифов;
- разные типы подписок;
- разные валюты;
- несколько providers;
- корпоративные тарифы;
- marketplace;
- несколько специалистов;
- recurring billing.

Расширение payment layer не должно требовать перестройки базовой authentication model или переписывания feature-модулей.

# 34. Итоговая модель

```text
                         ┌─────────────────────┐
                         │     User / Coach    │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │   Payment Service   │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Provider Adapter    │
                         └──────────┬──────────┘
                                    │
                                    ▼
                             Payment Provider
                                    │
                                  Webhook
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │  Payment State      │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Subscription State  │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │   Access Source     │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Permission Decision │
                         └──────────┬──────────┘
                                    │
                              Allow / Deny
```

Главное правило:

**Платёж подтверждает экономическое событие. Подписка формирует источник доступа. Access-модель определяет наличие соответствующего доступа. Permission-модель определяет, разрешено ли конкретное действие.**

В текущем runtime Stubborn Ram этот payment layer пока остаётся target/planned subsystem и не должен представляться как уже работающая production-функция.
