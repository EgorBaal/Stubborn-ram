# Stubborn Ram — CURRENT MVP

Версия: 1.0
Дата: 05.09.2026
Статус: УТВЕРЖДЕНО ДЛЯ РЕАЛИЗАЦИИ

## 1. Цель текущего этапа

На текущем этапе Stubborn Ram не пытается реализовать всю запланированную платформу.

Главная задача — как можно быстрее получить рабочую систему для первых платных клиентов онлайн-тренера.

MVP должен позволять:

1. клиенту зарегистрироваться и войти;
2. тренеру видеть своих клиентов;
3. тренеру и клиенту общаться в чате;
4. клиенту создавать недельный отчёт;
5. прикреплять к отчёту фотографии, скриншоты и видео;
6. добавлять текстовый комментарий;
7. отправлять отчёт тренеру;
8. тренеру открывать отчёт, просматривать все материалы и текст;
9. тренеру писать обратную связь;
10. клиенту открывать ответ тренера и видеть его материалы;
11. хранить отправленные данные постоянно, без автоматического удаления;
12. использовать уже созданный модуль тренировок, когда его data layer будет подключён.

## 2. Что НЕ входит в MVP

До отдельного решения НЕ реализуются:

- питание как отдельный полноценный модуль;
- FatSecret;
- AI-анализ питания;
- аналитика;
- библиотека;
- Activity;
- Weight;
- Photos & Measurements как отдельный самостоятельный модуль;
- сложная система уведомлений;
- платежи;
- подписки и автопродление;
- маркетплейс тренеров;
- сложная система ролей специалистов;
- Redis;
- Kubernetes;
- отдельные микросервисы;
- сторонний SaaS для чата;
- стороннее файловое хранилище;
- иностранный AI;
- иностранный email-провайдер без отдельного согласования.

Эти функции не удаляются из общего Roadmap. Они просто переносятся после MVP.

## 3. Главные модули MVP

### 3.1 Auth

Регистрация, подтверждение email, вход, восстановление пароля, сессия.

### 3.2 Coach / Client relationship

Один пользователь может быть клиентом тренера.
Связь между пользователями хранится отдельно от самих данных.

Данные клиента принадлежат клиенту.
Тренер получает доступ к данным только через активную связь coach-client.

### 3.3 Chat

Один чат на одну пару тренер-клиент.

Поддерживаемые типы сообщений MVP:

- текст;
- фотография;
- видео;
- документ при необходимости.

История чата хранится постоянно.

### 3.4 Reports

Недельный отчёт является отдельной сущностью.

Отчёт содержит:

- client_id;
- период/дату отчёта;
- текст клиента;
- прикреплённые media;
- статус;
- дату отправки;
- обратную связь тренера;
- прикреплённые материалы тренера, если они нужны.

После отправки отчёт не удаляется автоматически.

### 3.5 Media

Все пользовательские фото и видео хранятся в российском S3-совместимом объектном хранилище.

В PostgreSQL хранится только метаинформация о файле и его принадлежность.

Файлы не должны быть публичными.

Доступ выдаётся через сервер и временные signed URLs.

## 4. Постоянное хранение

Фраза «хранить до бесконечности» в проекте трактуется как:

- нет автоматического удаления пользовательских отчётов;
- нет автоматического удаления файлов отчётов;
- нет автоматического удаления истории чата;
- нет lifecycle policy, которая удаляет эти данные по возрасту;
- удаление возможно только отдельным административным/пользовательским процессом, если такой процесс будет позже утверждён.

Резервные копии являются отдельным механизмом и не заменяют основное хранилище.

## 5. Тренировки

Training UI уже существует и считается ценным активом проекта.

На MVP:

- не переписывать Training UI без необходимости;
- подключить его к новой backend/data layer после создания базовой инфраструктуры;
- сохранить архитектуру Workout → WorkoutExercise → WorkoutSet;
- использовать exercise_id, а не название упражнения как идентификатор;
- медиа тренировок хранить через общий Media слой;
- отчёты и чат должны ссылаться на существующие объекты, а не копировать их.

## 6. Архитектурное правило

Новый backend должен быть независимым от конкретного поставщика.

Frontend не должен напрямую зависеть от PostgreSQL/S3/конкретного email-провайдера.

Схема:

Frontend
→ Services
→ Backend API
→ PostgreSQL / Object Storage / Workers

Это необходимо, чтобы в будущем не пришлось переписывать UI при смене инфраструктуры.

## 7. Инфраструктура MVP

Базовый поставщик инфраструктуры: Selectel.

Используются только необходимые сейчас компоненты:

1. Cloud Server — backend API + WebSocket + первоначальный worker;
2. Managed PostgreSQL — основная БД;
3. S3 — постоянное хранение фото/видео/файлов;
4. DNS — при необходимости перенести управление DNS;
5. CDN — подключать только когда реальный объём/нагрузка оправдает его.

Не оплачивать заранее сервисы, которые MVP не использует.

## 8. Email

Email нужен для:

- подтверждения регистрации;
- восстановления пароля;
- критических системных уведомлений.

Email должен быть изолирован через emailService.

Предварительный кандидат: Unisender Go, но перед production необходимо проверить актуальные условия обработки данных и договорные документы.

## 9. AI

AI не является частью MVP.

Если позже потребуется импорт данных из скриншотов питания, использовать российский AI/OCR через отдельный aiService.

До появления этой функции AI-инфраструктуру не оплачивать.

## 10. Платежи

Платежи не являются частью MVP.

Когда появится необходимость принимать оплату внутри платформы, использовать российский эквайринг через paymentService.

## 11. Аналитика

Внутренняя аналитика не является частью MVP.

Не подключать стороннюю аналитику ради MVP.

## 12. Уведомления

Для первой версии не требуется сложная push-система.

В первую очередь достаточно:

- состояния непрочитанных сообщений;
- состояния новых отчётов;
- визуальных индикаторов внутри приложения.

Push добавляется позже отдельным этапом.

## 13. Безопасность

Обязательные требования MVP:

- все пользовательские данные хранятся в российской инфраструктуре;
- пароли хранятся только в виде безопасных хэшей;
- секреты не попадают во frontend;
- пользовательские файлы не являются публичными;
- сервер проверяет права доступа к каждому объекту;
- coach не может получить данные чужого клиента;
- клиент не может получить данные другого клиента;
- все критические операции проверяются на сервере;
- доступ к файлам выдаётся только после проверки прав;
- логирование не должно содержать пароли и токены.

## 14. Миграция с Supabase

Supabase не отключать до полного завершения миграции.

Порядок:

1. резервная копия;
2. развёртывание новой инфраструктуры;
3. создание новой БД;
4. создание backend API;
5. создание object storage;
6. перенос необходимых данных;
7. перенос auth;
8. подключение frontend через новый service layer;
9. тестирование;
10. production switch;
11. наблюдение и rollback window;
12. только после этого удаление старой инфраструктуры.

## 15. Приоритет

Порядок разработки:

P0 — Auth + backend foundation
P0 — Coach/client relationship
P0 — Media storage
P0 — Chat
P0 — Reports
P0 — Coach cabinet
P0 — Client report flow
P1 — Training persistence
P2 — остальные модули Roadmap

Главный критерий MVP:

Тренер должен реально провести одного клиента через Stubborn Ram от общения до получения недельного отчёта и отправки обратной связи.
