# Архитектура системы разрешений Stubborn Ram

Версия документа:

1.0

Статус:

Проектирование

---

# Назначение документа

PERMISSIONS_ARCHITECTURE.md описывает архитектуру системы разрешений платформы Stubborn Ram.

Документ определяет:

- принципы предоставления разрешений;
- правила проверки доступа;
- взаимосвязь пользовательских статусов и разрешений;
- влияние полного доступа на выполнение действий;
- принципы взаимодействия системы разрешений с модулями платформы;
- единый механизм проверки разрешений.

Документ является основой для реализации системы контроля доступа платформы, серверных проверок и политик безопасности.

---

# Принципы архитектуры

Архитектура системы разрешений Stubborn Ram проектируется как единая долгосрочная инфраструктура контроля доступа.

Все решения должны обеспечивать:

- единые правила проверки разрешений;
- минимальное количество специальных сценариев;
- безопасность выполнения действий;
- масштабируемость платформы;
- простоту сопровождения системы.

Основные принципы системы разрешений описаны ниже.

---

## 1. Разрешение является правом на выполнение действия

Основной единицей системы является разрешение на выполнение конкретного действия.

Разрешение определяет возможность выполнить одно определенное действие над объектом платформы.

Например:

- создать тренировку;

- изменить программу;

- удалить фотографию;

- просмотреть отчет;

- отправить сообщение.

Архитектура платформы предоставляет разрешения не пользователям и не ролям, а конкретным действиям.

Все проверки доступа выполняются исключительно относительно действия, которое пользователь пытается выполнить.

---

## 2. Пользовательские статусы не являются разрешениями

Статусы использования платформы:

- Самостоятельный пользователь;

- Клиент;

- Тренер;

не являются разрешениями сами по себе.

Статусы определяют сценарий использования платформы и участвуют в формировании итогового набора разрешений.

Конкретные права пользователя определяются системой после проверки всех применимых архитектурных условий.

---

## 3. Системные уровни доступа не являются пользовательскими разрешениями

Системные уровни доступа:

- User;

- Admin;

не заменяют пользовательские разрешения.

Административный уровень доступа предоставляет отдельный набор системных возможностей, предназначенных исключительно для обслуживания платформы.

Получение уровня доступа Admin не означает автоматическое получение всех пользовательских разрешений.

Права администратора определяются отдельными архитектурными правилами безопасности.

---

## 4. Проверка разрешений выполняется перед каждым действием

Любое действие, изменяющее данные платформы либо предоставляющее доступ к защищенной функциональности, должно сопровождаться проверкой соответствующего разрешения.

Отсутствие необходимого разрешения делает выполнение действия невозможным независимо от состояния пользовательского интерфейса.

Проверка разрешений должна выполняться на стороне сервера.

Проверки пользовательского интерфейса используются исключительно для повышения удобства работы и не являются механизмом обеспечения безопасности.

---

## 5. Разрешения формируются совокупностью условий

Ни один отдельный признак аккаунта сам по себе не предоставляет и не ограничивает возможность выполнения действий.

Итоговое разрешение формируется системой на основании совокупности нескольких независимых условий.

Разрешение не предоставляет доступ к данным напрямую. Оно определяет только возможность выполнения конкретного действия над объектом платформы.

На текущем этапе учитываются следующие условия.

### 5.1. Статусы использования платформы

Статусы использования определяют общий сценарий работы пользователя.

Например:

- Самостоятельный пользователь;

- Клиент;

- Тренер.

Статусы сами по себе не являются разрешениями, но участвуют в формировании итогового набора доступных действий.

---

### 5.2. Наличие полного доступа

Перед выполнением действий, требующих полного доступа, система проверяет наличие хотя бы одного активного источника полного доступа.

Источниками полного доступа являются:

- Trial;

- личная подписка;

- сопровождение тренером, имеющим действующую подписку.

При отсутствии полного доступа действия, требующие полного доступа, становятся недоступными независимо от остальных условий.

---

### 5.3. Активные связи пользователя

Для ряда действий система учитывает наличие активной связи между пользователем и другими участниками платформы.

На текущем этапе учитываются:

- активное сопровождение тренером;

- архивное сотрудничество;

- отсутствие активной связи.

Наличие или отсутствие связи влияет только на действия, связанные с совместной работой, и не изменяет остальные пользовательские права.

---

### 5.4. Системный уровень доступа

Системный уровень доступа определяет возможность выполнения административных действий.

На текущем этапе используются:

- User;

- Admin.

Системный уровень доступа не изменяет пользовательские сценарии работы платформы и используется исключительно для выполнения административных функций.

---

### 5.5. Состояние объекта

При необходимости система дополнительно учитывает состояние объекта, над которым выполняется действие.

Например:

- активный объект;

- архивный объект;

- помеченный как удаленный объект;

- заблокированный объект.

Даже при наличии всех остальных разрешений выполнение действия может быть запрещено состоянием самого объекта.

---

Только после проверки всех применимых условий система принимает итоговое решение о возможности выполнения действия.

---

## 6. Единый механизм проверки разрешений

Все действия платформы используют единый механизм проверки разрешений.

Отдельные модули платформы не реализуют собственную независимую систему проверки прав доступа.

Любое действие пользователя сначала передается системе разрешений.

После проверки система принимает одно из двух решений:

- разрешить выполнение действия;

- запретить выполнение действия.

Только после получения положительного результата выполнение действия передается соответствующему модулю платформы.

Единый механизм проверки обеспечивает:

- одинаковое поведение всех модулей;

- централизованное изменение правил доступа;

- отсутствие дублирования логики проверки;

- упрощение сопровождения платформы.

---

## 7. Причина отказа

При отказе в выполнении действия система разрешений должна возвращать не только факт отказа, но и стандартизированную причину отказа.

Полученная причина используется пользовательским интерфейсом для отображения соответствующего сообщения.

В зависимости от причины отказа интерфейс может:

- объяснить пользователю причину ограничения;

- предложить оформить подписку;

- предложить подключиться к тренеру;

- сообщить о необходимости выполнения другого условия;

- предложить иной доступный способ получения необходимого разрешения.

Система разрешений отвечает исключительно за принятие решения и возврат причины отказа.

Пользовательский интерфейс самостоятельно определяет способ отображения полученной информации пользователю.

---

## 8. Принцип ранней проверки разрешений

Проверка разрешений выполняется до запуска бизнес-логики соответствующего модуля.

Если выполнение действия запрещено, управление не передается модулю платформы.

Это означает, что модуль не начинает выполнение своей внутренней логики и не выполняет дополнительных проверок, связанных с данным действием.

Например:

- при отсутствии полного доступа пользователь не может начать создание нового дневника питания;

- при сопровождении тренером пользователь не может начать редактирование тренировочной программы;

- при отсутствии разрешения невозможно начать создание нового отчета.

После отказа в выполнении действия пользователь получает причину отказа, а интерфейс отображает соответствующее сообщение или предлагает доступный способ получения необходимого разрешения.

Такой подход позволяет:

- выполнять предварительную проверку до запуска бизнес-логики;

- не дублировать проверки внутри каждого модуля;

- уменьшить сложность реализации;

- обеспечить единообразное поведение всей платформы;

- исключить выполнение бизнес-логики при отсутствии необходимых разрешений.

---

## 9. Обязательная серверная проверка

Ранняя проверка разрешений используется исключительно для управления пользовательскими сценариями и повышения удобства работы с платформой.

Перед любым действием, изменяющим данные платформы, сервер обязан повторно выполнить проверку соответствующего разрешения.

Проверка, выполняемая пользовательским интерфейсом, не считается механизмом обеспечения безопасности.

Даже если пользователь смог обойти ограничения пользовательского интерфейса, сервер не должен выполнять действие без успешной проверки разрешений.

Окончательное решение о возможности выполнения действия всегда принимает сервер.

---

## 10. Система разрешений не содержит бизнес-логики

Система разрешений не содержит бизнес-логику отдельных модулей платформы.

Единственной задачей системы разрешений является принятие решения о возможности выполнения конкретного действия.

После успешной проверки управление передается соответствующему модулю платформы.

Каждый модуль самостоятельно выполняет собственную бизнес-логику.

Изменение внутренней логики любого модуля не должно требовать изменения архитектуры системы разрешений.

---

## 11. Разрешения вычисляются, а не хранятся

Система не хранит индивидуальные разрешения пользователей в виде отдельных записей базы данных.

Разрешения вычисляются динамически на основании архитектурных правил платформы.

При вычислении используются сведения, уже существующие в системе.

Например:

- статусы использования платформы;

- наличие полного доступа;

- активные связи пользователя;

- системный уровень доступа;

- состояние объекта.

Такой подход исключает дублирование данных, упрощает сопровождение системы и обеспечивает возможность дальнейшего масштабирования платформы без изменения модели хранения данных.

---

## 12. Единый источник истины

Система разрешений является единственным источником принятия решений о возможности выполнения действий.

Ни один модуль платформы не должен реализовывать собственную независимую систему проверки разрешений.

Любой модуль обращается к системе разрешений и получает итоговое решение.

Такой подход обеспечивает:

- единые правила проверки доступа;

- одинаковое поведение всех модулей;

- отсутствие противоречий между различными разделами платформы;

- централизованное изменение архитектурных правил без изменения отдельных модулей.

---

## 13. Структура разрешений модулей

Настоящий документ определяет исключительно общую архитектуру системы разрешений.

Конкретные разрешения отдельных модулей не описываются в PERMISSIONS_ARCHITECTURE.md.

Каждый функциональный модуль платформы самостоятельно определяет перечень поддерживаемых действий в собственной архитектурной документации.

При этом все действия обязаны использовать архитектурные принципы настоящего документа.

Например:

- TRAINING_ARCHITECTURE.md;

- FOOD_ARCHITECTURE.md;

- REPORT_ARCHITECTURE.md;

- CHAT_ARCHITECTURE.md;

- PROFILE_ARCHITECTURE.md.

При проектировании новых модулей используется единый принцип описания действий.

Базовыми действиями являются:

- просмотр;

- создание;

- изменение;

- удаление.

При необходимости модуль может вводить дополнительные специализированные действия, соответствующие его назначению.

Все новые действия автоматически подчиняются архитектурным принципам настоящего документа.

Добавление нового модуля не должно требовать изменения архитектуры системы разрешений.

# Правило изменения документа

PERMISSIONS_ARCHITECTURE.md изменяется только после принятия нового архитектурного решения.

Любые изменения принципов предоставления разрешений, порядка проверки доступа, взаимодействия системы разрешений с другими компонентами платформы или иных элементов архитектуры сначала обсуждаются и утверждаются, после чего фиксируются в настоящем документе.

Изменение перечня действий отдельных модулей не является основанием для изменения PERMISSIONS_ARCHITECTURE.md и выполняется в архитектурной документации соответствующего модуля.

Только после обновления документа допускается реализация изменений в коде.
