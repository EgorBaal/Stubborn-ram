# Архитектура авторизации Stubborn Ram

Версия документа:

2.0

Статус:

Архитектурно утверждено для целевой инфраструктуры; реализация после миграции

---

# Назначение документа

AUTH_ARCHITECTURE.md описывает архитектуру системы авторизации платформы Stubborn Ram.

Документ определяет:

- жизненный цикл аккаунта;
- регистрацию пользователей;
- подтверждение Email;
- вход в систему;
- восстановление пароля;
- постоянные пользовательские сессии;
- Welcome Flow;
- пробный период (Trial);
- источники полного доступа;
- ограниченный доступ;
- защиту маршрутов приложения;
- административный доступ;
- требования безопасности, относящиеся к авторизации.

Документ является основой для реализации всей системы авторизации платформы.

Целевая архитектура не зависит от Supabase Authentication. После миграции авторизация предоставляется собственным Backend API Stubborn Ram с PostgreSQL и серверным управлением сессиями.

---

# Принципы авторизации

Система авторизации Stubborn Ram проектируется как долгосрочная инфраструктура платформы.

Все решения должны обеспечивать:

- безопасность учетных записей;
- сохранность пользовательских данных;
- масштабируемость;
- возможность дальнейшего развития без изменения архитектуры;
- отсутствие прямого доступа клиентского приложения к PostgreSQL;
- единое серверное управление аутентификацией и разрешениями.

---

## 1. Один аккаунт — один пользователь

Каждый человек использует один постоянный аккаунт.

Все данные платформы принадлежат именно этому аккаунту.

Создание нескольких аккаунтов для одного пользователя не является частью архитектуры платформы.

Аккаунт может изменять статусы использования платформы без создания нового профиля.

---

## 2. Разделение авторизации и пользовательских данных

Система авторизации отвечает исключительно за:

- регистрацию;
- вход;
- подтверждение Email;
- управление сессиями;
- восстановление доступа;
- смену пароля;
- смену Email.

Все пользовательские данные хранятся отдельно в профиле пользователя и связанных таблицах PostgreSQL.

Авторизация не используется для хранения бизнес-данных платформы.

Связь аккаунта с бизнес-данными выполняется через стабильный `user_id`.

---

## 3. Подтвержденный Email обязателен

Каждый аккаунт должен иметь подтвержденный адрес электронной почты.

До подтверждения Email пользователь не считается полностью зарегистрированным и не получает доступ к функциональности приложения.

Email-письма отправляются серверной частью через отдельный Email-провайдер/адаптер.

Текущий целевой провайдер транзакционной почты — Unisender Go, при условии завершения договорной и юридической проверки.

---

## 4. Создание профиля пользователя

После успешного подтверждения Email система создает полноценный профиль пользователя.

Создание профиля не откладывается до завершения Welcome Flow.

Профиль связан с аккаунтом через `user_id`.

После создания профиля система сохраняет:

- идентификатор аккаунта;
- имя;
- фамилию;
- дату создания профиля;
- дату начала Trial;
- дату окончания Trial;
- первоначальный статус использования платформы;
- статус завершения Welcome Flow.

Имя и фамилия запрашиваются в процессе регистрации.

Во всех элементах интерфейса и при взаимодействии с пользователем платформа использует только имя пользователя, если иное не требуется конкретным сценарием.

---

# 5. Welcome Flow

Welcome Flow является обязательной частью первого входа в приложение.

Пока Welcome Flow не завершен, пользователь не получает доступ к основным разделам платформы.

Система должна обеспечивать безопасное продолжение Welcome Flow после повторного входа, закрытия приложения или потери соединения.

Завершение Welcome Flow определяется полем:

`onboarding_completed`

Значения:

- `false` — Welcome Flow не завершен;
- `true` — Welcome Flow завершен.

### Состав Welcome Flow

Welcome Flow состоит из трех последовательных экранов:

1. Приветствие пользователя.
2. Выбор первоначального статуса использования платформы.
3. Ознакомление с основными возможностями платформы и переход к главному экрану приложения.

После успешного завершения Welcome Flow пользователь попадает на главный экран.

---

# 6. Жизненный цикл нового пользователя

```text
Landing
   ↓
Регистрация
   ↓
Подтверждение Email
   ↓
Создание профиля
   ↓
Welcome Flow
   ↓
Главный экран приложения
   ↓
Использование платформы
```

---

# 7. Пользовательские маршруты

Лендинговая страница предназначена только для новых пользователей.

Если пользователь уже авторизован и его сессия действительна, при открытии сайта он автоматически перенаправляется в приложение.

Повторный показ лендинга авторизованному пользователю не производится.

Если Email не подтвержден, пользователь направляется в соответствующий сценарий подтверждения.

Если Welcome Flow не завершен, пользователь направляется на продолжение Welcome Flow.

Маршрутизация выполняется централизованно.

---

# 8. Постоянные пользовательские сессии

После успешного входа пользователь остается авторизованным.

Повторный ввод Email и пароля не требуется до момента:

- явного выхода;
- истечения/отзыва сессии;
- завершения сессии по причинам безопасности.

Каждое устройство хранит собственную независимую пользовательскую сессию.

Авторизация на одном устройстве не завершает активные сессии на других устройствах.

Сессионные данные и механизмы их продления контролируются Backend API.

Frontend не обращается напрямую к PostgreSQL и не получает учетные данные базы данных.

---

# 9. Биометрическая разблокировка

После успешной авторизации пользователь может использовать биометрические возможности устройства (Face ID, Touch ID и аналогичные).

Биометрическая разблокировка не является самостоятельным способом авторизации.

Она используется исключительно для быстрого открытия ранее авторизованной пользовательской сессии.

При отсутствии действующей пользовательской сессии биометрическая разблокировка не используется.

Реализация биометрической разблокировки является отдельным будущим этапом и не должна изменять базовую архитектуру аккаунта.

---

# 10. Восстановление пароля

Восстановление доступа осуществляется по подтвержденному адресу электронной почты пользователя.

При утрате пароля пользователь использует функцию «Забыли пароль?».

Backend создает одноразовый ограниченный по времени токен восстановления и передает его через Email-провайдера.

После успешного восстановления пользователь продолжает использовать тот же аккаунт.

Все пользовательские данные, история и настройки сохраняются.

Временные пароли архитектурой не предусматриваются.

---

# 11. Изменение адреса электронной почты

Каждый аккаунт использует один основной подтвержденный адрес электронной почты.

Изменение Email выполняется только авторизованным пользователем.

Для критического действия требуется повторное подтверждение личности в соответствии с SECURITY.md.

После ввода нового Email система отправляет письмо для подтверждения нового адреса.

До подтверждения новый Email не используется для входа в систему.

Текущий подтвержденный Email продолжает оставаться основным адресом аккаунта.

После успешного подтверждения новый Email становится основным.

Изменение Email не влияет на:

- пользовательский профиль;
- историю;
- подписки;
- идентификатор аккаунта;
- связанные пользовательские данные.

---

# 12. Пробный период (Trial)

Пробный период — бесплатный период полного доступа ко всем функциям платформы.

На текущем этапе принято решение:

- продолжительность Trial составляет 10 календарных дней.

Пробный период начинается автоматически в момент создания профиля пользователя после успешного подтверждения Email.

Пробный период не начинается:

- при регистрации без подтверждения Email;
- после повторной установки приложения;
- после повторного входа;
- после смены устройства.

Каждый аккаунт может получить Trial только один раз за всю историю существования.

Факт использования Trial должен быть надежно сохранен в PostgreSQL и не определяться только по данным frontend.

---

# 13. Источники полного доступа

Полный доступ к функциональности платформы может предоставляться несколькими независимыми способами.

Предусмотрены:

- активный Trial;
- личная оплаченная подписка;
- активное сопровождение тренером, имеющим действующую подписку.

Система не должна проверять каждый источник отдельно в различных разделах приложения.

Используется единый серверный механизм определения access state.

Перед выполнением действия, изменяющего данные платформы, Backend проверяет право пользователя на соответствующее действие.

---

# 14. Личная подписка

Пользователь может получить полный доступ к платформе путем оформления личной подписки.

Личная подписка является одним из независимых источников полного доступа.

При наличии активной личной подписки пользователь получает полный доступ независимо от наличия тренера.

Правила оплаты и жизненного цикла подписки определяются PAYMENT_ARCHITECTURE.md.

---

# 15. Подписка тренера

Тренер приобретает подписку, позволяющую сопровождать определенное количество клиентов.

Пока клиент связан с тренером, имеющим действующую подписку, клиент получает полный доступ к платформе без необходимости приобретать собственную подписку.

Полный доступ предоставляется автоматически.

При прекращении сопровождения или окончании подписки тренера система повторно вычисляет право доступа пользователя.

Правила связи тренера и клиента определяются COACH_CLIENT_RELATIONSHIP.md.

---

# 16. Приоритет источников полного доступа

При проверке права полного доступа система учитывает все возможные источники.

Если хотя бы один источник активен, пользователь получает полный доступ.

Приоритет между источниками не требуется.

Достаточно наличия хотя бы одного действующего основания.

---

# 17. Завершение Trial

После окончания Trial система автоматически проверяет наличие другого источника полного доступа.

Если существует:

- личная активная подписка;

или

- активное сопровождение тренером с действующей подпиской,

пользователь продолжает пользоваться платформой без ограничений.

Если других источников полного доступа нет, аккаунт автоматически переходит в режим ограниченного доступа.

---

# 18. Ограниченный доступ

После окончания Trial или прекращения действия всех источников полного доступа аккаунт не блокируется.

Пользователь сохраняет возможность:

- войти в аккаунт;
- просматривать всю историю тренировок;
- просматривать историю питания;
- просматривать историю веса;
- просматривать отчеты;
- просматривать аналитику;
- просматривать фотографии;
- просматривать переписку;
- управлять настройками учетной записи;
- изменить Email;
- изменить пароль;
- оформить личную подписку.

Создание новых данных становится недоступным.

К ограничениям относятся:

- создание новых тренировок;
- создание новых записей питания;
- создание новых записей веса;
- отправка новых отчетов;
- загрузка новых фотографий;
- отправка новых сообщений;
- создание любых новых пользовательских данных;
- изменение данных, требующих полного доступа.

Все ранее созданные данные остаются доступны для просмотра.

Удаление пользовательских данных по причине окончания Trial или подписки не допускается.

Ограниченный доступ определяется сервером и не может надежно реализовываться только через frontend.

---

# 19. Поведение интерфейса при ограниченном доступе

После перехода в режим ограниченного доступа приложение отображает постоянное информационное уведомление на главном экране.

Пользователь должен видеть понятную причину ограничения и доступный способ восстановления полного доступа.

Frontend может скрывать или отключать действия, недоступные пользователю, но окончательное разрешение на выполнение операции всегда принимает Backend.

---

# 20. Проверка доступа при изменении статуса пользователя

Статус пользователя сам по себе не является разрешением.

Право доступа вычисляется на основании:

- состояния аккаунта;
- подтверждения Email;
- завершения Welcome Flow;
- активных источников полного доступа;
- связи с тренером;
- состояния конкретного объекта;
- действия, которое пользователь пытается выполнить.

Единый механизм проверки используется всеми модулями.

Подробная action-based модель разрешений определяется PERMISSIONS_ARCHITECTURE.md.

---

# 21. Административный доступ

Административные возможности определяются системным уровнем доступа аккаунта.

Администратор использует ту же систему авторизации, что и остальные пользователи.

Наличие административных прав не изменяет жизненный цикл пользовательского аккаунта.

Административные проверки выполняются сервером.

Администратор не получает пароль пользователя и не должен иметь возможности просматривать секреты аутентификации.

Подробные правила административного доступа, безопасности и аудита определяются SECURITY.md.

---

# 22. Подготовка к двухфакторной аутентификации

На текущем этапе двухфакторная аутентификация не используется.

Архитектура должна обеспечивать возможность последующего добавления 2FA без изменения базовой структуры аккаунтов, пользовательских данных и бизнес-модулей.

Механизм 2FA должен быть подключаемым к существующему authentication service.

---

# 23. Выход из аккаунта

При выполнении команды «Выйти» пользователь завершает только текущую пользовательскую сессию.

Авторизация на остальных устройствах сохраняется.

Каждое устройство управляет своей пользовательской сессией независимо.

---

# 24. Удаление аккаунта

Пользователь может запросить удаление своего аккаунта.

Удаление аккаунта не приводит к немедленному физическому удалению пользовательских данных.

После подтвержденного запроса аккаунт переводится в архивное состояние.

Повторная регистрация нового аккаунта на Email, связанном с архивным аккаунтом, не допускается, пока действует соответствующая политика хранения/восстановления.

При попытке регистрации система должна предложить восстановить существующий архивный аккаунт, если такой сценарий разрешен политикой хранения.

Архив предназначен для защиты пользователя от случайной потери данных и возможности восстановления доступа в предусмотренных системой сценариях.

Окончательная политика хранения архивных данных определяется SECURITY.md и требованиями законодательства.

---

# 25. Смена пароля

Для смены пароля авторизованный пользователь должен пройти повторное подтверждение личности в соответствии с SECURITY.md.

После успешной смены пароля:

- текущая сессия сохраняется активной;
- все остальные активные пользовательские сессии автоматически завершаются.

При следующем открытии приложения на остальных устройствах требуется повторная авторизация с новым паролем.

При восстановлении пароля через Email все ранее активные сессии также завершаются.

---

# 26. Защита от подбора пароля

Защита от brute-force выполняется на стороне Backend.

Система должна применять:

- rate limiting для попыток входа;
- ограничение частоты восстановления пароля;
- безопасные сообщения об ошибках без раскрытия существования аккаунта;
- журналирование подозрительной активности;
- защиту критических authentication endpoints.

Автоматическая блокировка аккаунта только из-за нескольких неверных попыток не является обязательным механизмом.

Конкретные лимиты определяются SECURITY.md и эксплуатационными настройками Backend.

---

# 27. Архитектура компонентов авторизации

Целевая схема:

```text
React / PWA
     ↓
Backend API
     ↓
Authentication Service
     ↓
PostgreSQL
```

Дополнительные серверные интеграции:

```text
Backend API
 ├── Email Service → Unisender Go
 ├── Permission Service
 ├── Access Service
 └── Audit / Security logging
```

Frontend не обращается напрямую:

- к PostgreSQL;
- к Email API;
- к платежным API;
- к AI API;
- к внутренним секретам инфраструктуры.

Все такие операции выполняются сервером через соответствующие сервисы/адаптеры.

---

# 28. Сессии и безопасность

Сессионная модель должна обеспечивать:

- независимые сессии устройств;
- безопасное продление действующей сессии;
- отзыв отдельной сессии;
- отзыв всех сессий;
- автоматическое завершение сессий после смены пароля;
- отсутствие передачи секретов базы данных frontend-приложению.

Конкретная реализация session/token механизма является техническим решением Backend Foundation и не должна нарушать описанные поведенческие требования.

---

Документ не заменяет:

# 30. Правило изменения документа

AUTH_ARCHITECTURE.md изменяется только после принятия нового архитектурного решения.

Любое изменение системы:

- авторизации;
- регистрации;
- пользовательских сессий;
- Welcome Flow;
- Trial;
- подписок как источников доступа;
- ограниченного доступа;
- административной авторизации;
- жизненного цикла аккаунта

сначала обсуждается и утверждается, после чего фиксируется в настоящем документе.

Только после обновления документа допускается реализация изменений в коде.
