# Архитектура авторизации Stubborn Ram

Версия документа:

1.0

Статус:

Частично реализовано

---

# Назначение документа

AUTH_ARCHITECTURE.md описывает архитектуру системы авторизации платформы Stubborn Ram.

Документ определяет:

- жизненный цикл аккаунта;
- регистрацию пользователей;
- подтверждение Email;
- вход в систему;
- восстановление пароля;
- постоянные пользовательские сессии;
- Welcome Flow;
- пробный период (Trial);
- защиту маршрутов приложения;
- взаимодействие с Supabase Authentication;
- требования безопасности, относящиеся к авторизации.

Документ является основой для реализации всей системы авторизации платформы.

На текущем этапе в коде реализованы базовые сценарии регистрации, входа, восстановления пароля и проверки пользовательской сессии. Полные сценарии создания профиля пользователя, Welcome Flow, Trial и ограниченного доступа пока не реализованы.

---

# Принципы авторизации

Система авторизации Stubborn Ram проектируется как долгосрочная инфраструктура платформы.

Все решения должны обеспечивать:

- безопасность учетных записей;
- сохранность пользовательских данных;
- масштабируемость;
- возможность дальнейшего развития без изменения архитектуры.

Основные принципы авторизации описаны ниже.

---

## 1. Один аккаунт — один пользователь

Каждый человек использует один постоянный аккаунт.

Все данные платформы принадлежат именно этому аккаунту.

Создание нескольких аккаунтов для одного пользователя не является частью архитектуры платформы.

Аккаунт может изменять статусы использования платформы без создания нового профиля.

---

## 2. Разделение авторизации и пользовательских данных

Система авторизации отвечает исключительно за:

- регистрацию;
- вход;
- подтверждение Email;
- управление сессиями;
- восстановление доступа.

Все пользовательские данные хранятся отдельно в профиле пользователя и связанных таблицах базы данных.

Авторизация не должна использоваться для хранения бизнес-данных платформы.

---

## 3. Подтвержденный Email обязателен

Каждый аккаунт должен иметь подтвержденный адрес электронной почты.

До подтверждения Email пользователь не считается полностью зарегистрированным и не получает доступ к функциональности приложения.

---

## 4. Создание профиля пользователя

На текущем этапе автоматическое создание профиля пользователя в текущей реализации не выполнено. Этот сценарий считается планируемым и не реализован в существующем коде.

Создание профиля не откладывается до завершения Welcome Flow.

Это обеспечивает:

- наличие полноценного аккаунта сразу после подтверждения Email;
- отсутствие неподтвержденных профилей в базе данных;
- возможность безопасного продолжения Welcome Flow после закрытия приложения или потери соединения.

После создания профиля система сохраняет:

- идентификатор аккаунта (user_id);
- имя;
- фамилию;
- дату создания профиля;
- дату начала Trial;
- дату окончания Trial;
- первоначальный статус использования платформы;
- статус завершения Welcome Flow.

Имя и фамилия запрашиваются в процессе регистрации.

Во всех элементах интерфейса и при взаимодействии с пользователем платформа использует только имя пользователя, если иное не требуется в конкретном сценарии.

---

## 5. Welcome Flow

На текущем этапе Welcome Flow в текущей реализации не используется. В коде реализованы только базовые сценарии входа и регистрации.

Welcome Flow является обязательной частью первого входа в приложение.

Пока Welcome Flow не завершен, пользователь не получает доступ к основным разделам платформы.

Система должна обеспечивать возможность безопасного продолжения Welcome Flow после повторного входа в приложение.

Завершение Welcome Flow определяется полем:

onboarding_completed

Значения:

false — Welcome Flow не завершен.

true — Welcome Flow завершен.

### Состав Welcome Flow

Welcome Flow состоит из трех последовательных экранов.

1. Приветствие пользователя.

2. Выбор первоначального статуса использования платформы.

3. Ознакомление с основными возможностями платформы и переход к главному экрану приложения.

После успешного завершения Welcome Flow пользователь попадает на главный экран приложения.

## 7. Пользовательские маршруты

Лендинговая страница предназначена только для новых пользователей.

Если пользователь уже авторизован и его сессия действительна, при открытии сайта он автоматически перенаправляется на главный экран приложения.

Повторный показ лендинга авторизованному пользователю не производится.

---

## 8. Постоянные пользовательские сессии

После успешного входа пользователь остается авторизованным.

Повторный ввод Email и пароля не требуется до момента явного выхода из аккаунта либо завершения сессии по причинам безопасности.

Каждое устройство хранит собственную независимую пользовательскую сессию.

Авторизация на одном устройстве не завершает активные сессии на других устройствах.

Если пользователь уже авторизован, при открытии приложения он автоматически попадает на главный экран без повторного прохождения авторизации.

---

## 9. Биометрическая разблокировка

После успешной авторизации пользователь может использовать биометрические возможности устройства (Face ID, Touch ID и аналогичные).

Биометрическая разблокировка не является самостоятельным способом авторизации.

Она используется исключительно для быстрого открытия ранее авторизованной пользовательской сессии.

При отсутствии действующей пользовательской сессии биометрическая разблокировка не используется.

---

## 10. Восстановление пароля

Восстановление доступа осуществляется по адресу электронной почты пользователя.

После успешного восстановления пароля пользователь продолжает использовать тот же аккаунт.

Все пользовательские данные, история и настройки сохраняются.

---

## 11. Изменение адреса электронной почты

Каждый аккаунт использует один основной подтвержденный адрес электронной почты.

Изменение Email выполняется только авторизованным пользователем.

После ввода нового Email система отправляет письмо для подтверждения нового адреса.

До момента подтверждения новый Email не используется для входа в систему.

Текущий подтвержденный Email продолжает оставаться основным адресом аккаунта.

После успешного подтверждения новый Email становится основным.

Изменение Email не влияет на пользовательский профиль, историю, подписки, идентификатор аккаунта и другие пользовательские данные.

---

## 12. Пробный период (Trial)

Пробный период — это бесплатный период полного доступа ко всем функциям платформы.

Продолжительность пробного периода определяется настройками платформы.

На текущем этапе принято решение:

- продолжительность Trial составляет 10 календарных дней.

Пробный период начинается автоматически в момент создания профиля пользователя после успешного подтверждения Email.

Пробный период не начинается:

- при регистрации без подтверждения Email;
- после повторной установки приложения;
- после повторного входа в аккаунт;
- после смены устройства.

Каждый аккаунт может получить Trial только один раз за всю историю существования.

---

## 13. Источники полного доступа

Полный доступ к функциональности платформы может предоставляться несколькими независимыми способами.

На текущем этапе предусмотрены следующие источники полного доступа:

- активный Trial;
- личная оплаченная подписка;
- активное сопровождение тренером, имеющим действующую подписку.

Система не должна проверять каждый источник отдельно в различных разделах приложения.

Перед выполнением любого действия, изменяющего данные платформы, используется единый механизм проверки права полного доступа.

---

## 14. Личная подписка

Пользователь может получить полный доступ к платформе путем оформления личной подписки.

Личная подписка является одним из источников полного доступа.

При наличии активной личной подписки пользователь получает полный доступ независимо от наличия тренера.

---

## 15. Подписка тренера

Тренер приобретает подписку, позволяющую сопровождать определенное количество клиентов.

Пока клиент связан с тренером, имеющим действующую подписку, клиент получает полный доступ к платформе без необходимости приобретать собственную подписку.

Полный доступ предоставляется автоматически.

При прекращении сопровождения тренером система автоматически выполняет повторную проверку права полного доступа пользователя.

---

## 16 Приоритет источников полного доступа

При проверке права полного доступа система учитывает все возможные источники доступа.

Если хотя бы один источник является активным, пользователь получает полный доступ.

Приоритет между источниками не требуется.

Достаточно наличия хотя бы одного действующего основания.

---

## 17. Завершение Trial

После окончания Trial система автоматически проверяет наличие другого источника полного доступа.

Если существует:

- личная подписка;

или

- активное сопровождение тренером,

пользователь продолжает пользоваться платформой без ограничений.

Если других источников полного доступа нет, аккаунт автоматически переходит в режим ограниченного доступа.

---

## 18. Ограниченный доступ

После окончания Trial или прекращения действия всех источников полного доступа аккаунт не блокируется.

Пользователь сохраняет возможность:

- войти в аккаунт;
- просматривать всю историю тренировок;
- просматривать историю питания;
- просматривать историю веса;
- просматривать отчеты;
- просматривать аналитику;
- просматривать фотографии;
- просматривать переписку;
- управлять настройками учетной записи;
- изменить Email;
- изменить пароль;
- оформить личную подписку.

Создание новых данных становится недоступным.

К ограничениям относятся:

- создание новых тренировок;
- создание новых записей питания;
- создание новых записей веса;
- отправка новых отчетов;
- загрузка новых фотографий;
- отправка новых сообщений;
- создание любых новых пользовательских данных;
- изменение данных, требующих полного доступа.

Все ранее созданные данные остаются доступны для просмотра.
Удаление пользовательских данных по причине окончания Trial или подписки не допускается.

---

## 19. Поведение интерфейса при ограниченном доступе

После перехода в режим ограниченного доступа приложение отображает постоянное информационное уведомление на главном экране.

Уведомление информирует пользователя о завершении Trial или отсутствии активного источника полного доступа и предлагает оформить подписку.

При попытке выполнить действие, требующее полного доступа, система отображает модальное окно с предложением оформить подписку.

После оформления подписки все ограничения автоматически снимаются без потери пользовательских данных.

---

## 20. Прекращение сопровождения тренером

Если пользователь перестает быть клиентом тренера, система автоматически выполняет проверку права полного доступа.

Проверка выполняется в следующем порядке.

1. Проверяется наличие личной активной подписки.

Если личная подписка активна, пользователь продолжает пользоваться платформой без ограничений.

2. Если личной подписки нет, проверяется, использовался ли Trial ранее.

Если Trial еще не использовался, он запускается автоматически.

3. Если Trial уже был использован и личной подписки нет, аккаунт переводится в режим ограниченного доступа.

Повторное предоставление Trial одному и тому же аккаунту не допускается независимо от количества смен тренеров.

---

## 21. Административный доступ

Административные возможности определяются уровнем системного доступа аккаунта.

Администратор использует ту же систему авторизации, что и остальные пользователи.

Наличие административных прав не изменяет жизненный цикл пользовательского аккаунта.

Подробные правила административного доступа, безопасности и аудита действий определяются документом SECURITY.md.

---

## Подготовка к двухфакторной аутентификации

На текущем этапе двухфакторная аутентификация не используется.

Архитектура авторизации должна обеспечивать возможность последующего добавления двухфакторной аутентификации без изменения существующей структуры авторизации.

## 22. Выход из аккаунта

При выполнении команды «Выйти» пользователь завершает только текущую пользовательскую сессию.

Авторизация на остальных устройствах сохраняется.

Каждое устройство управляет своей пользовательской сессией независимо.

---

## 23. Удаление аккаунта

Пользователь может запросить удаление своего аккаунта.

Удаление аккаунта не приводит к немедленному физическому удалению пользовательских данных.

После удаления аккаунт переводится в архивное состояние.

Повторная регистрация нового аккаунта на адрес электронной почты, связанный с архивным аккаунтом, не допускается.

При попытке регистрации система предлагает пользователю восстановить существующий архивный аккаунт.

Архив предназначен для защиты пользователя от случайной потери данных и возможности восстановления доступа в предусмотренных системой сценариях.

Окончательная политика хранения архивных данных определяется документом SECURITY.md.

---

## 24. Смена пароля

После успешной смены пароля текущая пользовательская сессия сохраняется активной.

Все остальные активные пользовательские сессии автоматически завершаются.

При следующем открытии приложения на остальных устройствах требуется повторная авторизация с новым паролем.

# Правило изменения документа

AUTH_ARCHITECTURE.md изменяется только после принятия нового архитектурного решения.

Любое изменение системы авторизации, регистрации, пользовательских сессий, Welcome Flow, Trial, подписок, источников полного доступа или жизненного цикла аккаунта сначала обсуждается и утверждается, после чего фиксируется в настоящем документе.

Только после обновления документа допускается реализация изменений в коде.
