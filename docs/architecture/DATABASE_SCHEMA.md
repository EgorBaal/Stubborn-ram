# Принципы проектирования

База данных Stubborn Ram создается с учетом:

- долгосрочного развития продукта;
- безопасности пользовательских данных;
- разделения ролей пользователей;
- масштабирования функциональности;
- сохранения пользовательской истории.

## 1. Только подтвержденные решения

В DATABASE_SCHEMA.md фиксируются только решения, которые были согласованы.

Предположения, идеи и возможные будущие функции не должны становиться частью фактической схемы без отдельного решения.

---

## 2. Разделение ответственности

Каждая сущность базы данных должна отвечать за конкретную область данных.

Структура базы должна соответствовать структуре модулей приложения.

---

## 3. Владение данными

Каждая пользовательская информация должна иметь определенного владельца.

Система должна понимать:

- кто создал данные;
- кому принадлежат данные;
- кто имеет доступ;
- кто может изменять информацию.

---

## 4. Подготовка к масштабированию

Архитектура базы должна учитывать возможность дальнейшего развития:

- новые функции;
- новые роли;
- расширение количества пользователей;
- развитие платформы;
- несколько специалистов.

# Пользовательская модель

## Общий принцип

Stubborn Ram использует разделение между:

1. системой авторизации;
2. профилем пользователя;
3. дополнительными данными пользователя.

Авторизация не используется для хранения бизнес-данных приложения.

# auth / accounts

В целевой архитектуре учетная запись пользователя является частью собственной Auth-инфраструктуры Backend.

Она отвечает за:

- идентификацию аккаунта;
- Email;
- безопасное хранение учетных данных;
- управление сессиями.

Точная физическая структура auth-таблиц определяется при реализации AUTH-инфраструктуры.

Бизнес-таблицы не должны зависеть от Email как от внешнего ключа.

Основной идентификатор пользователя:

`user_id`

Он является постоянным идентификатором аккаунта.

# profiles

Назначение:

Основной профиль пользователя внутри Stubborn Ram.

Каждый авторизованный пользователь имеет профиль.

Предварительно определенные данные:

- идентификатор аккаунта (`user_id`);
- имя;
- фамилия;
- аватар;
- статусы использования платформы;
- системный уровень доступа;
- дата создания профиля;
- дата последнего изменения;
- дата начала Trial;
- дата окончания Trial;
- признак завершения Welcome Flow;
- статус аккаунта.

Каждый аккаунт может иметь только один профиль.

Все пользовательские данные платформы принадлежат аккаунту пользователя
и связываются с ним через постоянный user_id.

Профиль является представлением основных пользовательских данных,
но не является владельцем бизнес-сущностей вместо аккаунта.

---

## Принцип хранения данных

Данные пользователя принадлежат его аккаунту.

Все пользовательские данные проектируются как долгосрочные.

Удаление или изменение отдельных настроек аккаунта не должно приводить к потере истории тренировок, питания, фотографий, отчетов или других модулей без отдельного подтвержденного сценария.

Архитектура должна обеспечивать возможность хранения данных на протяжении многих лет.

---

## Принцип идентификации пользователя

Каждый аккаунт имеет единственный постоянный идентификатор (`user_id`).

Все данные платформы связываются именно с этим идентификатором.

Ни Email, ни имя пользователя, ни статусы использования платформы никогда не используются как связь между таблицами.

Изменение Email, имени или режима использования не должно влиять на целостность данных.

---

## Принцип неизменности идентификатора

После создания аккаунта его идентификатор (`user_id`) никогда не изменяется.

Все данные платформы проектируются таким образом, чтобы быть связаны исключительно с этим идентификатором.

---

## Принцип удаления данных

Удаление аккаунта не должно автоматически приводить к физическому удалению связанных данных из базы данных.

Политика окончательного удаления определяется отдельными правилами безопасности и хранения данных.

---

# Связь Client и Coach

## Общий принцип

Связь между клиентом и тренером является отдельной сущностью системы.

Она не должна храниться только внутри профиля пользователя.

Причины:

- история сотрудничества;
- изменение тренера;
- разные статусы взаимодействия;
- дальнейшее расширение до нескольких специалистов.

---

# coach_client_relationships

Назначение:

Хранение отношений между клиентом и тренером.

Уже согласовано:

- связь является самостоятельной сущностью;
- связь не удаляется физически;
- поддерживаются состояния `ACTIVE` и `ARCHIVED`;
- история сотрудничества сохраняется.

### Исторический доступ

- `ACTIVE` — текущее сотрудничество и основной доступ тренера к разрешенным модулям клиента.
- `ARCHIVED` — новые данные клиента тренеру не предоставляются, но сохраняется исторический доступ к данным периода собственного сотрудничества в соответствии с permissions и настройками доступа.
- Новый тренер по умолчанию получает только данные собственного периода сотрудничества.
- Клиент может явно открыть новому тренеру отдельные исторические периоды и/или модули.
- Клиент может расширять, ограничивать или отзывать такой исторический доступ.
- Архивирование не удаляет данные и не меняет их владельца.
- Одну и ту же связь можно реактивировать, сохраняя предыдущие периоды сотрудничества.

Структура конкретных полей и дополнительные статусы фиксируются перед созданием production schema.

# Авторство данных

Не каждая сущность обязана иметь одновременно owner_id и author_id.
Для каждой сущности, где ownership и авторство имеют смысл, они моделируются отдельно:

owner_id — пользователь, которому принадлежат данные;
author_id — пользователь, который создал или изменил конкретную запись/элемент.

Для данных пользователя владельцем является сам пользователь. Тренер не становится владельцем клиентских данных только потому, что создал план, цель, комментарий или другой объект в рамках сотрудничества.

Автор и владелец могут совпадать.

Например:

Программа:

Автор — тренер.

Владелец — пользователь.

Отчет:

Автор — пользователь.

Владелец — пользователь.

Комментарий:

Автор — тренер.

Владелец — пользователь.

Данный принцип является обязательным для всех новых таблиц базы данных, где авторство и владение имеют смысл для конкретной сущности.

## ПЛАНЫ И ЦЕЛИ

Планы и цели являются сущностями с периодом действия.

Для периода:

- `start_date` обязателен;
- `end_date` может быть `NULL`, если период продолжается;
- изменение плана или цели не перезаписывает историю, а завершает предыдущий период и создает новый;
- история предыдущих периодов сохраняется;
- ownership принадлежит пользователю;
- авторство хранится отдельно, когда оно имеет смысл.

Планы и цели, созданные активным тренером, автоматически завершаются при окончании сотрудничества и сохраняются в истории.

После окончания сотрудничества пользователь может продолжить, изменить или сбросить соответствующую цель/план в зависимости от конкретного модуля.

# Постоянное хранение MVP

Для Chat, Reports и их media не предусматривается автоматическое удаление по возрасту.

То есть:

- старые сообщения не удаляются автоматически;
- старые отчеты не удаляются автоматически;
- фотографии отчетов не удаляются автоматически;
- видео отчетов не удаляются автоматически;
- вложения чата не удаляются автоматически.

Резервное копирование является отдельным механизмом и не заменяет основное хранилище.

# PostgreSQL и Object Storage

PostgreSQL является источником истины для структурированных данных.

Object Storage является источником истины для самих пользовательских файлов.

Связь:

```text
PostgreSQL
│
├── user/profile data
├── relationships
├── chats
├── messages
├── reports
├── feedback
├── media metadata
└── training data

Object Storage
│
├── photos
├── screenshots
├── videos
└── documents
```

# Права доступа

Доступ к данным определяется не только наличием записи в базе.

Сервер определяет доступ на основании:

- аутентификации пользователя;
- ownership объекта;
- требуемого action/permission;
- контекста coach-client relationship;
- статуса связи (`ACTIVE` / `ARCHIVED`);
- правил исторического доступа и настроек пользователя.

Наличие или отсутствие активной связи само по себе не является единственным критерием доступа: после архивирования могут сохраняться разрешенные исторические действия.

Проверка permission выполняется на backend до выполнения действия. Frontend не является источником истины для прав доступа.
Правила разрешений описываются в:

`docs/architecture/PERMISSIONS_ARCHITECTURE.md`

## REPORT

Weekly Report является самостоятельным каноническим объектом и принадлежит пользователю-клиенту.

Связь с тренером используется для определения контекста сотрудничества и доступа, но не определяет ownership отчета.

Отчет должен поддерживать:

- `owner_id` — клиент;
- `relationship_id` — связь с тренером, в рамках которой отчет был создан/отправлен;
- период отчета (`period_start`, `period_end`);
- дату создания;
- дату отправки;
- дату проверки тренером;
- статус;
- ответы на questionnaire;
- список включенных модулей/элементов;
- данные канонических сущностей модулей за выбранный период;
- зафиксированное состояние данных на момент отправки;
- данные обратной связи тренера.

Жизненный цикл:

`DRAFT → SUBMITTED → REVIEWED`.

`DRAFT` можно изменять. После `SUBMITTED` отчет считается архивным снимком состояния на момент отправки и не редактируется задним числом.

При открытии исходной сущности после отправки отчета пользователь может видеть ее текущее состояние, но сам отчет сохраняет состояние, зафиксированное при отправке.

Если исходная сущность после отправки отчета была удалена или недоступна, в архивном отчете сохраняется ее место с соответствующей отметкой об удалении/недоступности.

### REPORT_FEEDBACK

`report_feedback`:

- имеет `author_id`;
- привязан к конкретному отчету и конкретному модулю/сущности/элементу на минимальном разумном уровне;
- может содержать текст до 500 символов;
- может содержать до 2 изображений и 1 видео через `media_links`;
- поддерживает soft delete;
- удаленная обратная связь тренера отображается как «Комментарий тренера удалён»;
- автор может редактировать и удалять собственную обратную связь.

Отчет и обратная связь являются данными PostgreSQL. Медиа хранятся через общую систему Media/Object Storage.

Сам отчет не является копией данных модулей: он агрегирует канонические данные и фиксирует состояние на момент отправки.

Отчеты не удаляются автоматически после окончания сотрудничества или архивирования связи.

# Правило обновления документа

DATABASE_SCHEMA.md обновляется только после согласования:

1. пользовательского сценария;
2. требований модуля;
3. структуры данных;
4. связей между сущностями.

Сначала проектируется логика использования.

После этого создается структура базы данных.

После утверждения структуры создаются SQL-миграции.

SQL-миграции должны соответствовать DATABASE_SCHEMA.md.

---

# Правило миграции

Целевая база данных создается в PostgreSQL новой backend-инфраструктуры.

Supabase не является целевой системой хранения.

Во время миграции:

1. существующие данные сохраняются;
2. создается целевая схема;
3. создаются таблицы и индексы;
4. создаются необходимые ограничения;
5. реализуются серверные проверки доступа;
6. выполняется перенос данных;
7. выполняется проверка целостности;
8. только после успешной проверки frontend переводится на новую систему.

Старая база не удаляется до завершения проверки миграции.

# Definition of Done для схемы MVP

Схема MVP считается готовой к реализации, когда согласованы:

- структура пользователей и профилей;
- coach-client relationship;
- chat;
- messages;
- reports;
- report feedback;
- media metadata;
- связи media с объектами;
- ownership;
- authorship;
- индексы для основных запросов;
- ограничения целостности;
- правила доступа;
- стратегия хранения.

После этого допускается создание production SQL-миграций.

# Главное правило базы данных

**Данные создаются один раз.**

**Данные сохраняются один раз.**

**Данные принадлежат пользователю.**

Все остальные модули получают доступ к тем же данным.

Тренировка является историческим объектом.

Отчет является самостоятельным объектом, агрегирующим канонические данные модулей за выбранный период и фиксирующим состояние данных на момент отправки.

Чат является каналом общения.

Media хранится отдельно от структурированных данных.

История пользователя не должна исчезать из-за смены тренера, окончания Trial или смены инфраструктурного provider.
