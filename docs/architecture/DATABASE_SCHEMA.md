# Назначение документа

DATABASE_SCHEMA.md описывает структуру данных платформы Stubborn Ram.

Документ определяет:

- основные сущности системы;
- связи между данными;
- правила владения данными;
- принципы хранения информации.

Этот документ является основой для дальнейшего проектирования базы данных Supabase/PostgreSQL.

На текущем этапе в репозитории уже присутствуют базовые SQL-скрипты для хранения лидов и настройки RLS: database/001_create_leads.sql и database/002_leads_rls.sql. Полная схема модулей приложения пока остается в стадии проектирования.

# Принципы проектирования

База данных Stubborn Ram создается с учетом:

- долгосрочного развития продукта;
- безопасности пользовательских данных;
- разделения ролей пользователей;
- масштабирования функциональности.

Основные принципы:

## 1. Только подтвержденные решения

В DATABASE_SCHEMA.md фиксируются только решения, которые были согласованы.

Предположения, идеи и возможные будущие функции не должны становиться частью схемы базы без отдельного решения.

---

## 2. Разделение ответственности

Каждая сущность базы данных должна отвечать за конкретную область данных.

Структура базы должна соответствовать структуре модулей приложения.

---

## 3. Владение данными

Каждая пользовательская информация должна иметь определенного владельца.

Система должна понимать:

- кто создал данные;
- кому принадлежат данные;
- кто имеет доступ;
- кто может изменять информацию.

---

## 4. Подготовка к масштабированию

Архитектура базы должна учитывать возможность дальнейшего развития:

- новые функции;
- новые роли;
- расширение количества пользователей;
- развитие платформы.

---

# Пользовательская модель

## Общий принцип

Stubborn Ram использует разделение между:

1. системой авторизации;
2. профилем пользователя;
3. дополнительными данными пользователя.

---

# auth.users

Источник:

Supabase Authentication.

Назначение:

Хранение учетных записей пользователей.

Отвечает за:

- регистрацию;
- авторизацию;
- управление сессией;
- безопасность учетной записи.

Бизнес-данные пользователя не должны храниться напрямую в auth.users.

---

# profiles

Назначение:

Основной профиль пользователя внутри Stubborn Ram.

Каждый авторизованный пользователь имеет профиль.

Предварительно определенные данные:

- идентификатор аккаунта (user_id);
- имя;
- фамилия;
- аватар;
- статусы использования платформы;
- системный уровень доступа;
- дата создания профиля;
- дата последнего изменения;
- дата начала Trial;
- дата окончания Trial;
- признак завершения Welcome Flow;
- статус аккаунта.

---

Каждый аккаунт может иметь только один профиль.

Создание нескольких профилей для одного аккаунта не допускается.

Все пользовательские данные платформы принадлежат именно этому профилю.

## Принцип хранения данных

Данные пользователя принадлежат его аккаунту.

Все пользовательские данные проектируются как долгосрочные.

Удаление или изменение отдельных настроек аккаунта не должно приводить к потере истории тренировок, питания, фотографий, отчетов или других модулей без отдельного подтвержденного сценария.

Архитектура должна обеспечивать возможность хранения данных на протяжении многих лет.

---

## Принцип идентификации пользователя

Каждый аккаунт имеет единственный постоянный идентификатор (user_id).

Все данные платформы связываются именно с этим идентификатором.

Ни Email, ни имя пользователя, ни статусы использования платформы никогда не используются как связь между таблицами.

Изменение Email, имени или режима использования не должно влиять на целостность данных.

---

## Принцип неизменности идентификатора

После создания аккаунта его идентификатор (user_id) никогда не изменяется.

Все данные платформы проектируются таким образом, чтобы быть связаны исключительно с этим идентификатором.

Это гарантирует сохранность связей между всеми модулями независимо от изменения Email, имени, режима использования аккаунта или других данных профиля.

---

## Принцип удаления данных

Удаление аккаунта не должно автоматически приводить к физическому удалению связанных данных из базы данных.

По умолчанию используется принцип мягкого удаления (Soft Delete) либо архивирования, если это соответствует пользовательскому сценарию и требованиям законодательства.

Физическое удаление данных допускается только в специально предусмотренных сценариях.

---

## Принцип целостности данных

Все таблицы платформы должны ссылаться на профиль пользователя исключительно через идентификатор аккаунта (user_id).

Создание дублирующих связей через Email, имя пользователя, номер телефона или другие изменяемые данные запрещается.

Каждая новая таблица должна сохранять ссылочную целостность с основным профилем пользователя.

---

# Статусы использования аккаунта

Stubborn Ram использует единый аккаунт пользователя.

Каждый аккаунт может одновременно обладать одним или несколькими статусами использования платформы.

Статус использования определяет, каким образом пользователь использует платформу.

Статусы использования не являются системными уровнями доступа.

---

## Принцип статусов

Статусы использования определяют только сценарии работы пользователя внутри платформы.

Они не являются системными ролями безопасности.

Один аккаунт может одновременно обладать несколькими статусами.

Например:

• Самостоятельный пользователь;

• Самостоятельный пользователь + Тренер;

• Клиент;

• Клиент + Тренер.

Пользователь может свободно переходить между статусами без создания нового аккаунта.

Все изменения выполняются путем изменения статусов аккаунта.

История пользователя, данные и подписки при этом полностью сохраняются.

## Самостоятельный пользователь

Пользователь использует платформу самостоятельно.

Самостоятельный пользователь использует платформу для ведения собственного прогресса.

Наличие данного статуса не ограничивает возможность одновременно обладать другими статусами использования.

Самостоятельный пользователь может в любой момент стать клиентом тренера или получить статус тренера без создания нового аккаунта.

---

## Клиент

Пользователь связан с тренером.

Связь с тренером определяется отдельной сущностью coach_client_relationships.

Клиент получает доступ к платформе в соответствии с правилами сопровождения тренером.

При прекращении сопровождения пользователь не теряет свой аккаунт и может продолжить использование платформы как самостоятельный пользователь.

---

## Тренер

Пользователь использует инструменты сопровождения клиентов.

Тренер может создавать назначения, сопровождать клиентов и использовать профессиональные функции платформы.

Получение статуса тренера не требует создания нового аккаунта.

---

Один аккаунт может одновременно обладать несколькими статусами использования.

Например:

- Самостоятельный пользователь + Тренер;
- Клиент + Тренер.

Все статусы относятся к одному и тому же аккаунту пользователя.

# Системные уровни доступа

Режим использования приложения не является системной ролью.

Для административных функций используются отдельные уровни доступа.

На текущем этапе предусмотрены:

## User

Обычный пользователь платформы.

## Admin

Системный администратор.

Используется только для обслуживания платформы и не влияет на пользовательские сценарии.

Системный уровень доступа определяет административные возможности аккаунта и не зависит от статусов использования платформы.

Например:

- тренер может иметь уровень доступа User;
- клиент может иметь уровень доступа User;
- самостоятельный пользователь может иметь уровень доступа User;
- любой из них при необходимости может обладать уровнем доступа Admin.

Уровень доступа и статусы использования являются независимыми характеристиками аккаунта.

## Независимость статусов и системных ролей

Статусы использования платформы и системные уровни доступа являются полностью независимыми.

Например:

Самостоятельный пользователь → User

Клиент → User

Тренер → User

Самостоятельный пользователь + Тренер → User

Любой из перечисленных аккаунтов при необходимости может обладать уровнем доступа Admin.

Получение административных полномочий не изменяет пользовательские статусы аккаунта.

Административный доступ предназначен исключительно для обслуживания платформы.

# Связь Client и Coach

## Общий принцип

Связь между клиентом и тренером является отдельной сущностью системы.

Она не должна храниться только внутри профиля пользователя.

Причина:

В будущем могут потребоваться:

- история сотрудничества;
- изменение тренера;
- разные статусы взаимодействия.

---

# coach_client_relationships

Предварительное назначение:

Хранение отношений между клиентом и тренером.

Статус:

Частично утверждено.

Подтверждено:

- связь является самостоятельной сущностью;
- связь никогда не удаляется физически;
- поддерживаются состояния ACTIVE и ARCHIVED;
- история сотрудничества сохраняется.

Требует дальнейшего проектирования:

- дополнительные статусы;
- структура таблицы;
- правила доступа;
- поддержка нескольких специалистов.

---

# Авторство данных

Каждая сущность платформы должна хранить сведения:

- владелец данных;
- автор данных.

Автор и владелец могут совпадать.

Например:

Программа:

Автор — тренер.

Владелец — пользователь.

Отчет:

Автор — пользователь.

Владелец — пользователь.

Комментарий:

Автор — тренер.

Владелец — пользователь.

Данный принцип является обязательным для всех новых таблиц базы данных.

---

# Принцип единственного экземпляра данных

Любая сущность платформы существует только в одном экземпляре.

Предоставление доступа к данным осуществляется путем изменения прав доступа, а не созданием копий объектов.

Дублирование пользовательских данных архитектурой платформы не допускается.
