# SECURITY.md

# Архитектура безопасности Stubborn Ram

Версия документа:

1.0

Статус:

Проектирование

---

# Назначение документа

SECURITY.md описывает архитектуру безопасности платформы Stubborn Ram.

Документ определяет:

- принципы безопасности платформы;
- административный доступ;
- защиту пользовательских данных;
- правила административного просмотра;
- журналирование действий;
- базовые требования к безопасности системы.

Документ является основой для проектирования механизмов безопасности платформы.

---

# Принципы безопасности

Архитектура безопасности Stubborn Ram проектируется как долгосрочная инфраструктура платформы.

Основными принципами являются:

- защита пользовательских данных;
- минимально необходимые права доступа;
- прозрачность административных действий;
- невозможность получения пользовательских паролей;
- возможность последующего аудита действий.

---

# 1. Принцип минимально необходимых привилегий

Каждый пользователь получает только те возможности, которые необходимы для выполнения его задач.

Дополнительные права предоставляются только при наличии соответствующего уровня доступа.

---

# 2. Системные уровни доступа

На текущем этапе используются два системных уровня доступа.

## User

Обычный пользователь платформы.

## Admin

Администратор платформы.

Уровень доступа Admin используется исключительно для обслуживания платформы.

---

# 3. Назначение администратора

Администратор существует исключительно для обеспечения работоспособности платформы.

Администратор может использовать административные инструменты только для:

- технической поддержки пользователей;
- решения проблем с авторизацией;
- решения проблем с подписками;
- решения проблем с оплатой;
- восстановления доступа;
- анализа ошибок платформы;
- обеспечения безопасности системы.

Административные полномочия не используются для обычного использования платформы.

---

# 4. Административный доступ

Администратор использует собственный аккаунт платформы.

Создание отдельного административного аккаунта не требуется.

Если аккаунт обладает уровнем доступа Admin, пользователю становятся доступны административные функции.

---

# 5. Режим администратора

Пользователь с уровнем доступа Admin получает возможность переключения в режим администратора.

Переключение выполняется только внутри собственного аккаунта.

Во время просмотра пользовательских данных система должна явно отображать, что используется административный режим.

---

## Переключение режима

Если аккаунт обладает системным уровнем доступа Admin, пользователь получает возможность переключения в режим администратора.

Переключение выполняется внутри собственного аккаунта и не требует повторной авторизации.

Переключатель режима администратора отображается только пользователям с уровнем доступа Admin.

Переход в режим администратора не изменяет учетную запись пользователя и не выполняет вход под учетной записью другого человека.

# 6. Просмотр пользовательских данных

Администратор имеет право просматривать пользовательские данные исключительно для выполнения задач технической поддержки и обслуживания платформы.

Пароль пользователя никогда не отображается и не может быть получен администратором.

Администратор не выполняет вход под учетной записью пользователя.

---

## Административный просмотр

Администратор не выполняет вход под учетной записью пользователя.

При открытии пользовательского профиля используется специальный режим административного просмотра.

Во время административного просмотра интерфейс должен явно отображать, что администратор просматривает чужой аккаунт.

Административный просмотр используется исключительно для технической поддержки пользователей, обеспечения безопасности платформы и исполнения пользовательского соглашения.

# 7. Поиск пользователей

Администратор может находить пользователей по:

- user_id;
- Email;
- имени;
- фамилии.

В дальнейшем список способов поиска может быть расширен без изменения общей архитектуры платформы.

---

# 8. Полномочия администратора

Администратор имеет право изменять только системные данные, необходимые для обслуживания платформы.

На текущем этапе к ним относятся:

- статус подписки;
- срок действия подписки;
- статус Trial;
- связь пользователя с тренером;
- системный статус аккаунта.

Изменение пользовательских тренировок, питания, фотографий, отчетов, сообщений и других пользовательских данных не входит в полномочия администратора без отдельного утвержденного сценария.

---

## Ограничения полномочий администратора

Администратор не имеет права изменять пользовательские данные без специально утвержденного архитектурного сценария.

К пользовательским данным относятся:

- тренировки;
- питание;
- фотографии;
- отчеты;
- переписка;
- аналитика;
- любые другие данные, созданные пользователем.

Администратор использует свои полномочия исключительно для устранения технических проблем, восстановления работоспособности платформы и обслуживания пользователей.

# Неизменяемые ограничения администратора

Даже при наличии системного уровня доступа Admin администратор не получает полного контроля над пользовательским аккаунтом.

Администратор не имеет права:

- выполнять вход под учетной записью пользователя;
- получать или просматривать пароль пользователя;
- изменять пароль пользователя;
- изменять адрес электронной почты пользователя;
- создавать пользовательские данные от имени пользователя;
- изменять пользовательские тренировки, питание, отчеты, фотографии, переписку и другие пользовательские данные без специально утвержденного архитектурного сценария.

Полномочия администратора ограничиваются исключительно обслуживанием платформы, восстановлением работоспособности системы и решением технических проблем пользователей.

---

# 9. Журнал административных действий

Все действия администратора подлежат обязательному журналированию.

Система должна сохранять:

- идентификатор администратора;
- дату и время действия;
- пользователя, в отношении которого выполнено действие;
- тип выполненного действия.

Журнал используется для обеспечения безопасности платформы и последующего аудита.

---

## Неизменяемость журнала

Журнал административных действий является неизменяемым.

После создания запись журнала не может быть изменена или удалена.

При необходимости фиксации новой информации создается новая запись журнала.

Журнал хранится в целях обеспечения безопасности платформы и проведения последующего аудита действий администратора.

## Хранение журнала безопасности

Журнал безопасности является частью системной истории платформы.

Записи журнала не подлежат изменению или удалению пользователями и администраторами.

Срок хранения журнала определяется политикой хранения данных платформы и может изменяться без изменения архитектуры системы.

При изменении политики хранения должна обеспечиваться целостность журнала и возможность проведения аудита за установленный период хранения.

---

# Архивирование аккаунтов

При удалении аккаунта пользовательские данные не удаляются физически.

Аккаунт переводится в архивное состояние.

Архивирование предназначено для защиты пользователя от случайной потери данных и возможности восстановления аккаунта.

Повторная регистрация нового аккаунта на адрес электронной почты, связанный с архивным аккаунтом, не допускается.

При попытке регистрации система предлагает пользователю восстановить существующий архивный аккаунт.

---

Восстановление архивного аккаунта может быть выполнено только владельцем аккаунта после подтверждения права владения подтвержденным адресом электронной почты.

Администратор не восстанавливает пользовательские аккаунты самостоятельно, за исключением случаев устранения технических ошибок платформы.

---

# Изменение адреса электронной почты

Каждый аккаунт использует один основной адрес электронной почты.

Изменение Email допускается только после подтверждения нового адреса.

До подтверждения нового Email текущий подтвержденный адрес остается активным.

После успешного подтверждения новый Email становится основным адресом аккаунта.

Изменение Email не влияет на пользовательские данные, историю, подписки и идентификатор аккаунта.

---

# Подтверждение критически важных действий

Для выполнения действий, влияющих на безопасность учетной записи, пользователь должен повторно подтвердить свою личность.

На текущем этапе повторное подтверждение выполняется путем ввода текущего пароля.

Повторное подтверждение требуется при выполнении следующих действий:

- изменение адреса электронной почты;
- смена пароля;
- удаление аккаунта.

После успешного подтверждения личности действие может быть выполнено.

Архитектура платформы должна обеспечивать возможность замены данного механизма на двухфакторную аутентификацию без изменения общей структуры безопасности.

---

# Смена пароля

После успешной смены пароля текущая пользовательская сессия остается активной.

Все остальные пользовательские сессии автоматически завершаются.

При следующем открытии приложения на остальных устройствах требуется повторная авторизация с использованием нового пароля.

---

# Восстановление доступа

Восстановление доступа осуществляется по подтвержденному адресу электронной почты пользователя.

При утрате пароля пользователь использует функцию «Забыли пароль?».

После ввода адреса электронной почты система отправляет ссылку для создания нового пароля.

Использование временных паролей архитектурой платформы не предусматривается.

После успешного создания нового пароля пользователь может выполнить вход в свой аккаунт.

Все ранее активные пользовательские сессии автоматически завершаются.

---

# Защита от подбора пароля

Аккаунт пользователя не блокируется автоматически при многократном вводе неверного пароля.

Защита от автоматического подбора паролей обеспечивается встроенными механизмами Supabase, включая ограничение частоты запросов (Rate Limiting) и другие средства защиты.

Пользователь, забывший пароль, восстанавливает доступ через стандартную процедуру восстановления пароля.

Административное вмешательство для восстановления доступа не требуется.

---

# Уведомления безопасности

При выполнении действий, влияющих на безопасность учетной записи или доступ к аккаунту, система отправляет уведомление на подтвержденный адрес электронной почты пользователя.

На текущем этапе уведомления отправляются при следующих событиях:

- изменение адреса электронной почты;
- изменение пароля;
- восстановление пароля;
- архивирование аккаунта;
- восстановление аккаунта из архива;
- административное действие, изменяющее состояние аккаунта пользователя.

Уведомления безопасности предназначены исключительно для информирования пользователя и не требуют дополнительных действий, если операция была выполнена самим пользователем.

---

# Выход из аккаунта

При выполнении команды «Выйти» завершается только текущая пользовательская сессия.

Авторизация на остальных устройствах сохраняется.

Каждое устройство управляет собственной пользовательской сессией независимо.

---

# Управление активными сессиями

Пользователь имеет возможность просматривать список своих активных пользовательских сессий.

Для каждой активной сессии отображается доступная техническая информация, необходимая для идентификации устройства.

Пользователь может:

- завершить отдельную пользовательскую сессию;
- завершить все пользовательские сессии одновременно.

При завершении текущей пользовательской сессии пользователь выходит только с текущего устройства.

При завершении всех пользовательских сессий авторизация сохраняется только на устройстве, с которого выполнялось действие.

---

# Двухфакторная аутентификация

На текущем этапе двухфакторная аутентификация не используется.

Архитектура платформы должна обеспечивать возможность последующего добавления двухфакторной аутентификации без изменения общей архитектуры безопасности.

# Правило обновления документа

SECURITY.md обновляется только после принятия нового архитектурного решения, относящегося к безопасности платформы.

Любые изменения административного доступа, пользовательских прав, механизмов защиты данных или других элементов безопасности сначала обсуждаются и утверждаются, после чего фиксируются в настоящем документе.

Только после обновления документа допускается реализация изменений в коде.
