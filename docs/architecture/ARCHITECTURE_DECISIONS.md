STUBBORN RAM
Архитектурные решения 1–45
Версия: сентябрь 2026

1. Владелец данных
Пользователь является единственным владельцем своих данных. Тренер владельцем данных не является.

2. Доступ тренера
Активный тренер получает доступ к основным фитнес-модулям пользователя в рамках действующего сотрудничества.

3. Архив сотрудничества
После завершения сотрудничества тренер сохраняет доступ к архиву данных периода своего сотрудничества. Новые данные после завершения сотрудничества ему недоступны.

4. Факты и планы
Пользователь фиксирует собственные факты. Активный тренер создаёт планы и цели. Если тренера нет, пользователь фактически ведёт себя как собственный тренер.

5. Цели при активном тренере
При активном тренере пользователь самостоятельно не создаёт цели в тех областях, которыми управляет тренер.

6. Привязка обратной связи
Обратная связь привязывается к конкретной сущности и, где это разумно, к максимально атомарному уровню.

7. Комментарии и чат
Комментарии к сущностям не являются чатом. Пользователь и тренер могут оставлять комментарии вокруг одной и той же сущности.

8. Медиа в обратной связи
Одна точка обратной связи: максимум 500 символов текста, 2 изображения и 1 видео.

9. Редактирование обратной связи
Каждый пользователь может редактировать и удалять собственные комментарии/обратную связь. Удаление — мягкое.

10. Обратная связь тренера без комментария клиента
Тренер может оставить обратную связь самостоятельно, даже если клиент не оставил собственного комментария, если для данной сущности предусмотрена обратная связь.

11. Архитектура отчёта
Отчёт состоит из анкеты/вопросов и автоматически подтягиваемых данных модулей. Отчёт является агрегатором канонических данных, а не копией всех данных.

12. Период отчёта
По умолчанию используется последние 7 дней. Пользователь может выбрать другой период или отдельные дни.

13. Состав отчёта
По умолчанию отчёт включает все основные модули. Пользователь может исключать отдельные элементы и добавлять необходимые.

14. Состояния отчёта
DRAFT можно редактировать. SUBMITTED становится архивной версией и задним числом не редактируется.

15. Снимок отчёта и актуальные данные
Открытый отправленный отчёт показывает состояние данных на момент отправки. При переходе в исходную сущность отображается её текущее состояние.

16. Удаление исходной сущности
Если исходная сущность была удалена после отправки отчёта, в архивном отчёте сохраняется её место с пометкой об удалении.

17. Удаление комментария тренера
Если комментарий тренера был удалён, в истории сохраняется маркер «Комментарий тренера удалён».

18. Планы и цели как периоды
У плана/цели есть обязательная start_date и необязательная end_date. При изменении плана старый период закрывается, новый начинается с указанной даты.

19. История целей и планов
Прошлые цели и планы не переписываются. Для исторической даты показывается действовавший тогда период; для текущей даты — актуальный.

20. Владелец и автор
owner_id определяет владельца, author_id — создателя/назначившего сущность. В режиме без тренера они совпадают. При работе с тренером owner_id = клиент, author_id = тренер для назначенных им целей/планов.

21. Переход от тренера к самостоятельному режиму
При завершении сотрудничества цели/планы тренера заканчиваются. Пользователю можно предложить по каждому модулю продолжить ту же цель уже от своего имени, изменить её или начать заново.

22. Подключение тренера
Клиент вводит публичный Trainer ID и отправляет запрос. До принятия тренер не видит данные клиента.

23. Принятие или отклонение
Тренер принимает запрос — связь становится ACTIVE. Тренер может отклонить запрос; причина отклонения необязательна.

24. История запросов
Каждый запрос сохраняется. Отклонённый запрос можно отправить повторно. Ожидающий запрос клиент может отменить, тренер получает уведомление.

25. Отключение тренера клиентом
Клиент может завершить сотрудничество. Связь переходит в ARCHIVED.

26. Завершение сотрудничества тренером
Тренер не завершает сотрудничество одной кнопкой. Он может инициировать завершение, но клиент должен подтвердить.

27. Поддержка
Клиент и тренер могут обращаться в поддержку. Администратор может расследовать ситуацию и применять необходимые меры.

28. Повторное подключение
Та же связь может перейти ARCHIVED → ACTIVE. История периодов активности сохраняется.

29. Отпуск тренера
Краткий отпуск не меняет статус связи. ARCHIVED означает завершение сотрудничества, а не временный перерыв.

30. Новый тренер
Новый тренер по умолчанию видит только данные собственного периода сотрудничества.

31. Передача старой истории
Клиент может явно открыть старые данные новому тренеру по периоду и модулям.

32. Настройки доступа к старой истории
Клиент может в любое время расширить, ограничить или отозвать доступ к старой истории и отдельным модулям.

33. Доступ к текущим модулям
Все основные фитнес-модули по умолчанию доступны активному тренеру. Клиент может отключить отдельные модули.

34. Переход от самостоятельного режима к тренеру
При начале сотрудничества собственные цели пользователя заканчиваются с даты начала сотрудничества. Новые цели создаёт тренер.

35. Будущие специалисты
Сейчас используется один активный тренер. Архитектура оставляет основу для будущих специалистов и направлений, но их реализация сейчас не требуется.

36. Авторство тренера
Цели, планы, комментарии и отправленные тренером медиа должны отображаться с атрибуцией тренера.

37. Имя и аватар тренера
Выбран вариант: исторические записи показывают текущее имя и текущий аватар тренера.

38. Удаление аккаунта тренера
История клиента сохраняется. В идеале сохраняются последнее имя и аватар тренера; если это невозможно — отображаются «Тренер» и стандартный аватар.

39. После завершения сотрудничества
Ничего из истории клиента не удаляется задним числом. Цели, планы, комментарии, медиа и другие данные сохраняются.

40. Режимы аккаунта
Один аккаунт может работать как клиент и как тренер. Тренерская подписка открывает переключение режима. В будущем возможен режим администратора.

41. Trainer ID
У тренера есть публичный уникальный Trainer ID для приглашений. Внутри системы связи используют стабильный user_id.

42. Оплата тренерских услуг
На данном этапе платформа не регулирует оплату между тренером и клиентом. Коммерческий слой будет добавлен позже.

43. Удаление аккаунта клиента
Аккаунт переводится в архив. Данные физически не удаляются, предусмотрена возможность восстановления.

44. Факты пользователя
Пользователь всегда может редактировать или удалять собственные факты. Это не изменяет уже отправленный архивный отчёт.

45. Цели после завершения сотрудничества
Цели и планы тренера автоматически завершаются при завершении сотрудничества и остаются в истории.

Ключевые принципы:
- Один пользователь — один аккаунт и один владелец собственных данных.
- Тренер получает доступ через связь с пользователем, а не через владение данными.
- ACTIVE/ARCHIVED определяют состояние сотрудничества; архив не уничтожает историю.
- Данные модулей являются каноническими; отчёт агрегирует их, а не дублирует.
- Исторические отчёты сохраняют отправленное состояние.
- Планы и цели моделируются периодами, а не перезаписью текущего значения.
- owner_id и author_id разделяют владение и авторство.
- Комментарии к сущностям и чат — разные механизмы.
- Доступ к старой истории управляется пользователем явно.
- Архитектура допускает будущих специалистов без реализации этой функции на текущем этапе.
