# Архитектурное состояние после миграции

Проект находится в состоянии модульной архитектуры с централизованной маршрутизацией и общим shell внутри приложения.

Основные принципы текущей структуры:

- модульные страницы живут в src/modules/\*;
- маршруты централизованы в src/app/router/appRoutes.jsx;
- общий shell приложения принадлежит AppLayout;
- BottomTabBar является общим компонентом shell и не должен использоваться напрямую внутри модулей;
- страницы legacy-папки src/pages/app используются только как временные placeholder и не являются основным местом разработки.

---

# Ключевые директории

## src/app

Назначение:

- корневая инфраструктура внутреннего приложения.

Содержит:

- layouts/ — общая оболочка приложения;
- router/ — маршруты приложения, включая внутренняя и auth/landing/questionnaire части.

Что важно:

- AppLayout является единственным владельцем общего shell;
- маршрутизация собрана в одном месте и не разбрасывается по модулям.

---

## src/modules

Назначение:

- основной слой модульных экранов приложения.

Текущие модули:

- activity
- analytics
- chat
- home
- library
- nutrition
- photos
- profile
- report
- training
- weight

Каждый модуль должен содержать собственную локальную структуру, включая:

- Page.jsx;
- Page.css;
- локальные компоненты;
- локальные hooks/services при необходимости.

Логика модулей не должна быть завязана на legacy-страницы или на общий page-shell.

---

## src/components

Назначение:

- переиспользуемые UI-элементы и общие интерфейсные блоки.

Содержит:

- app/
- auth/
- client/
- coach/
- common/
- home/
- landing/
- questionnaire/
- ui/

Важно:

- отдельные модули могут использовать общие компоненты, но не должны переносить свою специфичную логику в общий слой.
- общие UI-части не заменяют собственные локальные компоненты модуля.

---

## src/features

Назначение:

- доменная логика и функциональные области проекта.

Содержит обособленные зоны, например:

- auth
- chat
- fatsecret
- notifications
- nutrition
- programs
- progress
- questionnaire
- reports

Это слой, который помогает структурировать предметную область, но не должен смешиваться с layout-оболочкой или глобальными маршрутизаторами.

---

## src/loading

Назначение:

- единая инфраструктура runtime-загрузки внутри уже запущенного приложения.

Содержит:

- LoadingProvider;
- LoadingContext;
- useLoading;
- LoadingOverlay;
- LoadingScreen.

Важно:

- Startup Screen и Loading Overlay являются независимыми подсистемами;
- Loading Overlay не используется для холодного запуска;
- модули не должны создавать собственные полноэкранные loader-системы, если подходит общий Loading Overlay.

---

## src/pages

Назначение:

- резервный и временный слой страниц.

На текущем этапе:

- отдельные страницы остаются в src/pages/app как placeholder-файлы;
- основная разработка переведена в src/modules.

Не является основной структурой для новых экранов.

---

## src/services

Назначение:

- слой интеграций и серверных вызовов.

Содержит:

- auth/
- leadService.js
- supabaseService.js

Здесь находятся запросы к Supabase, внешним сервисам и сервисные операции уровня приложения.

---

## src/contexts

Назначение:

- глобальные контексты приложения.

Текущий пример:

- AuthContext.jsx

Не используется для хранения page-specific логики или модульных UI-правил.

---

## src/assets, src/data, src/styles, src/utils

Назначение:

- статические ресурсы, данные, общие стили и вспомогательные утилиты.

Эти директории не должны содержать:

- маршрутизацию;
- page-specific CSS;
- бизнес-логику конкретного модуля;
- зависимость от конкретного экрана приложения.

Роутинг является централизованным и не должен размазываться по отдельным модулям.

# Общий shell приложения

Внутреннее приложение работает через общий shell:

```text
AppLayout
└── Outlet
    └── BottomTabBar
```

Правило текущей архитектуры:

- AppLayout отвечает за общую оболочку приложения;
- BottomTabBar принадлежит shell, а не модулю;
- модульные страницы не должны напрямую импортировать и рендерить BottomTabBar;
- модуль не должен зависеть от другого модуля через общую оболочку.
- AppLayout не владеет вертикальной прокруткой модульных страниц.

Вертикальная прокрутка:

- Home фиксированная и не использует вертикальный scroll;
- обычные маршруты используют собственный экземпляр PageScroll;
- Chat использует специализированный scroll-контекст;
- scroll одного маршрута не должен влиять на другой маршрут.

# Ключевые правила текущей структуры

## 1. Модули и shell

Модули оформляются как локальные страницы внутри src/modules, а общий shell остаётся в AppLayout.

## 2. Центральный router

Все внутренние маршруты задаются в src/app/router/appRoutes.jsx.

## 3. Локальная изоляция

Каждый модуль должен быть изолирован по стилям и внутренней логике.

## 4. Legacy страницы не являются целевым состоянием

src/pages/app является временным слоем и не должен использоваться как основной путь разработки новых экранов.

## 5. Общий слой ограничен

Только AppLayout, нижняя навигация, общие UI-абстракции и базовые сервисы могут быть общими.

# Резюме

Текущая структура проекта соответствует модульному подходу с общей оболочкой и централизованной маршрутизацией. Основная разработка направлена в src/modules, а legacy-структуры постепенно оттесняются в роль временных заглушек и технических остатков миграции.

## Router

Ответственность:

- распределение маршрутов по лендингу, авторизации, анкете и внутреннему приложению.

Допустимые зависимости:

- Layout;
- Pages.

Запрещённые зависимости:

- прямые зависимости от UI-компонентов конкретной страницы.

---

## Layout

Ответственность:

- общая оболочка приложения и контейнер для контента.

Допустимые зависимости:

- Pages;
- общие компоненты.

Запрещённые зависимости:

- модульная логика конкретной страницы;
- page-specific CSS одного модуля.

---

## Pages

Ответственность:

- представление конкретной страницы и координация её контента.

Допустимые зависимости:

- Components;
- Hooks;
- Services.

Запрещённые зависимости:

- импорт другой Page;
- использование CSS другой страницы.

---

## Components

Ответственность:

- отображение интерфейса и составных частей страницы.

Допустимые зависимости:

- UI-компоненты;
- Hooks.

Запрещённые зависимости:

- импорт Page;
- прямой доступ к маршрутам уровня приложения.

---

## Hooks

Ответственность:

- повторно используемая логика состояния и эффектов.

Допустимые зависимости:

- Services.

Запрещённые зависимости:

- прямые зависимости от UI-компонентов страницы.

---

## Services

Ответственность:

- взаимодействие с внешними системами.

Допустимые зависимости:

- другие Services;
- низкоуровневые библиотеки и клиенты.

Запрещённые зависимости:

- UI-компоненты;
- Page-компоненты;
- CSS.

---

## Supabase

Ответственность:

- хранение данных и серверная интеграция.

Допустимые зависимости:

- только через Services.

Запрещённые зависимости:

- прямой доступ из UI или Pages.

---

# Правила зависимостей

| Слой      | Может зависеть от              | Запрещённые зависимости                                                             |
| --------- | ------------------------------ | ----------------------------------------------------------------------------------- |
| Page      | Components, Hooks, Services    | Page → Page, Page → CSS другой страницы, Page → AppLayout как локальное исправление |
| Component | UI, Hooks                      | Component → Page, Component → Router                                                |
| Hook      | Services                       | Hook → Router, Hook → Page                                                          |
| Service   | lib, Supabase, другие Services | Service → Component, Service → Page                                                 |
| Layout    | Router, Shared UI, Pages       | Layout → Page-specific логика, Layout → CSS одного модуля                           |
| Router    | Layout, Pages                  | Router → Component уровня страницы                                                  |

## Page может использовать

- Components;
- Hooks;
- Services.

## Page не может

- импортировать другую Page;
- использовать CSS другой страницы;
- изменять общую оболочку ради одного модуля.

---

## Component может использовать

- другие UI-компоненты;
- Hooks.

## Component не может

- импортировать Page;
- напрямую вызывать общую инфраструктуру как модульное решение.

---

## Hooks могут использовать

- Services.

## Hooks не должны

- зависеть от UI-структуры страницы;
- хранить page-specific стили.

---

## Services не должны зависеть от UI

Services должны работать только с данными и внешними интеграциями.

---

# Алгоритм разработки новой задачи

При любой новой задаче разработчик обязан:

1. определить модуль;
2. определить страницу;
3. проверить локальные компоненты;
4. изменять сначала Page;
5. затем локальные Components;
6. только после этого Hooks;
7. только затем Services.

AppLayout менять только если проблему невозможно решить локально.

BottomTabBar менять только если изменение относится ко всему приложению.

Router менять только если добавляется новый маршрут.
