# Блок: Тренировки

Версия: 1.0 (Утвержденная концепция)

==========================================
НАЗНАЧЕНИЕ
==========================================

Раздел "Тренировки" является основным рабочим разделом приложения.

Именно здесь пользователь:

• начинает тренировку;
• ведет тренировочный дневник;
• использует шаблоны;
• просматривает историю;
• управляет упражнениями;
• фиксирует результаты;
• прикрепляет фото и видео;
• формирует данные для будущей аналитики.

Раздел полностью самодостаточен и одинаково работает как для самостоятельного пользователя, так и для пользователя с тренером.

Тренер лишь получает доступ к уже существующим данным пользователя.

==========================================

Текущее состояние реализации (2026)

Ниже зафиксировано фактическое состояние текущей кодовой базы относительно архитектурной модели, описанной в этом документе.

Реализовано в текущем коде:

• маршруты раздела Training и базовые экранные состояния: History / Templates / Exercises / Create / New Training;
• основной UI-экран создания тренировки в TrainingPage;
• карточки упражнений с локальным состоянием;
• добавление и удаление упражнений;
• выбор упражнения через ExercisePickerOverlay;
• параметры подходов, сложность, методы интенсивности, суперсеты и сворачивание карточек;
• локальный react state для логики тренировки внутри текущего экрана;
• чтение системных упражнений из таблицы exercises через Supabase в ExerciseList.

Реализовано частично:

• интеграция с Supabase для упражнений: в коде уже есть чтение системных упражнений, но отсутствует единый service layer и логика личных упражнений;
• UI-логика отдельных тренировки и подходов работает локально, однако постоянное хранение в базе ещё не подключено;
• шаблоны, программы и история пока реализованы как пользовательский интерфейс/заглушки и шаблонная структура, а не как работающие сущности из базы.

Ещё не реализовано:

• постоянное хранение тренировок, подходов и упражнений в Supabase;
• схема workout / workout_exercise / sets в базе;
• exerciseService и единый источник данных в сервисном слое;
• RLS-политики для личных и системных упражнений;
• история тренировок из базы;
• реальные связи пользователь ↔ тренер и ownership/author модели для Training.

Важно: это документ описывает и целевую архитектуру, и текущую реализацию. Архитектурная модель сохраняется как план и обязательное требование к будущей реализации, но в текущем коде часть из неё ещё не переведена в постоянное хранилище.

1. # ОСНОВНОЙ ЭКРАН

После нажатия кнопки "Тренировки" на главной странице открывается раздел тренировок.

В верхней части расположены три вкладки:

• История
• Шаблоны
• Упражнения

По умолчанию всегда открывается вкладка "История".

Текущая фактическая реализация в коде соответствует этой структуре: маршруты и экраны находятся в src/modules/training/screens, а UI-логика для новой тренировки и карточек упражнений находится в TrainingPage, TrainingInfo, TrainingExerciseCard и сопутствующих компонентах.

Под вкладками располагается главная кнопка:

▶ Начать тренировку
Системное упражнение:

user_id IS NULL

Личное упражнение:

user_id = auth.uid()

При выборке для пользователя логика должна учитывать оба типа:

user_id IS NULL

OR

user_id = текущий пользователь

---

Пользователь может создать упражнение, которого нет в системной библиотеке.

В базе:

name:

<название упражнения>

user_id:

UUID текущего пользователя

Такое упражнение доступно только этому пользователю.

В будущем, если пользователь во время тренировки вручную вводит новое название упражнения и сохраняет тренировку, система должна:

1. Проверить, существует ли такое личное упражнение.
2. Если нет — создать его.
3. Получить его exercise_id.
4. Связать тренировку с этим exercise_id.

Нельзя хранить упражнение в тренировке только как строку.

Предполагаемая структура связи:

Workout

↓

Workout Exercise

↓

exercise_id

↓

Exercise

Ключевые правила для будущей разработки:

1. Один источник данных для упражнений — Supabase.
2. Страница «Упражнения» и ExercisePickerOverlay используют одну и ту же библиотеку.
3. Системные упражнения доступны всем пользователям.
4. Личные упражнения принадлежат конкретному пользователю и не становятся общими.
5. Тренировка должна хранить exercise_id, а не только название упражнения.
6. Подходы должны быть отдельными сущностями, связанными с конкретным упражнением внутри конкретной тренировки.
7. История упражнения строится через exercise_id.
8. Будущая аналитика должна получать данные из сохранённых тренировок и подходов, а не из визуальных компонентов.
9. UI-компоненты не должны самостоятельно содержать бизнес-логику работы с Supabase.
10. Перед изменением архитектуры необходимо сначала проверить эту документацию и существующий exerciseService, чтобы не создать второй независимый механизм хранения упражнений.

# ========================================== 5. УПРАЖНЕНИЯ

Раздел содержит единую библиотеку упражнений приложения.

Упражнение представляет собой самостоятельную сущность.

Текущее фактическое состояние:

• UI-раздел Exercises уже реализован в TrainingExercisesPage и ExerciseList.
• В текущем коде список упражнений запрашивается из таблицы exercises и фильтруется по muscle_group и поиску.
• На текущем этапе интеграция с Supabase работает только для чтения системных упражнений: запрос использует .is("user_id", null), то есть получает только публичные упражнения.
• Подключение личных упражнений, объединённого списка системных + пользовательских упражнений и создания новых упражнений в БД ещё не завершено.
• Реализация архитектурно соответствует целевому плану, но не является полной persistence layer.

Пользователь может:

• создать упражнение;
• переименовать;
• удалить;
• использовать в шаблонах;
• использовать в тренировках.

Библиотека объединяет системные упражнения и личные упражнения пользователя.

Системные упражнения хранятся как записи с user_id = NULL.

Личные упражнения хранятся как записи с user_id = auth.uid().

Пользователь не ограничен только системной библиотекой и может создать собственное упражнение с любым названием.

Пример личного упражнения:

• Жим лежа;
• Подъем чайника на бицепс;
• Любое собственное название.

# ========================================== 6. КАРТОЧКА УПРАЖНЕНИЯ

При нажатии на упражнение во время тренировки открывается его карточка.

В карточке отображаются:

• название упражнения;
• подходы;
• веса;
• повторения;
• комментарий к упражнению;
• дополнительные параметры.

# Также присутствуют три основные кнопки.

Текущее фактическое состояние реализации в коде:

• Карточка реализована в TrainingExerciseCard и поддерживает свободный ввод названия упражнения.
• Пользователь может выбрать упражнение через ExercisePickerOverlay.
• Карточка поддерживает сворачивание/разворачивание.
• Добавляется набор подходов через кнопку "Добавить подход".
• Каждый подход содержит набор параметров, сложность и методы интенсивности.
• Реализованы локальный комментарий, удаление упражнения и локальный поповер подтверждения удаления.
• Эти элементы уже реально работают в UI и являются частью текущей реализации; однако постоянное хранение данных по карточкам и подходам в БД ещё не подключено.

# 4.1 АРХИТЕКТУРА СИСТЕМЫ УПРАЖНЕНИЙ

Раздел «Упражнения» является единым источником данных для упражнений во всём приложении.

Не должно существовать отдельных списков упражнений в:

• странице «Упражнения»;
• карточке тренировки;
• ExercisePickerOverlay;
• других компонентах.

Все эти места должны получать упражнения из единого источника данных Supabase.

Общая схема:

Supabase

↓

Exercises Service

↓

├── Раздел «Упражнения»

└── ExercisePickerOverlay

    			↓

     Выбор упражнения

    			↓

    		Тренировка

---

Основная таблица:

exercises

Минимальные поля:

• id
• name
• muscle_group
• user_id
• created_at

Будущие поля:

• description
• image_url
• video_url
• updated_at

Поле user_id:

• NULL — системное упражнение, доступное всем пользователям.
• UUID пользователя — личное упражнение конкретного пользователя.

Пользовательские упражнения никогда автоматически не становятся общими для других пользователей.

• Спина — 15
• Ноги — 20
• Ягодицы — 10
• Плечи — 15
• Бицепс — 10
• Трицепс — 10
• Пресс — 10

Количество не является жёстким ограничением и в дальнейшем может расширяться.

/app/training/exercises

# ========================================== 7. НАСТРОЙКИ МЕТРИК

Настройки работают на двух уровнях.

Текущая реализация UI:

• в TrainingExerciseCard реализован выбор параметров через ParametersPopover;
• в подходе можно указать сложность через DifficultyPopover;
• методы интенсивности реализованы в локальном состоянии карточки подхода;
• дополнительные параметры оказываются частью конкретного подхода и тесно привязаны к текущему UI, но ещё не переведены в независимую схему хранения данных.

Фактическая архитектура в коде сейчас поддерживает только локальное состояние; шаблонные настройки и постоянное сохранение настроек уровня шаблона/тренировки пока не развиты в полном виде.

Уровень шаблона.

Пользователь заранее определяет, какие параметры должны использоваться по умолчанию.

Например:

☑ Вес

☑ Повторения

☑ RIR

☑ Отдых

☑ Время

☑ Комментарий

☑ Другие параметры

Все настройки автоматически переносятся в каждую новую тренировку.

---

Уровень конкретной тренировки.

Во время выполнения тренировки пользователь может:

• добавить новую метрику;
• убрать ненужную;
• изменить параметры.

Изменения относятся только к данной тренировке.

Шаблон остается неизменным.

# ========================================== 8. ПОДХОДЫ

Каждый подход является самостоятельной единицей данных.

Текущее фактическое состояние в коде:

• подходы представлены как отдельные объекты в локальном state внутри TrainingExerciseCard;
• для каждого подхода есть поля weight, repetitions, difficulty, distance, calories, speed, power, incline, time, rir, rpe, rest, intensityMethods, isExtraOpen;
• UI уже реализует визуальное добавление, редактирование и раскрытие дополнительных параметров подхода;
• методы интенсивности и сложность поддерживаются в интерфейсе;
• постоянное хранение подходов в базе ещё не подключено.

Для каждого подхода можно хранить:

• repetitions;
• weight;
• difficulty;

В будущем:

• RPE;
• RIR;
• сет;
• дроп-сет;
• кластер;
• темп;
• пауза;
• дополнительное отягощение;
• другие параметры.

Именно подход является минимальной единицей хранения информации.

# ========================================== 9. МЕТОДЫ ВЫПОЛНЕНИЯ

Для каждого подхода можно указать методы выполнения.

Они открываются только после нажатия кнопки настроек.

Текущее фактическое состояние: в UI методы выполнения уже реализованы и управляются через локальный state подхода. В массив intensityMethods добавлены варианты Drop-set, Изометрия, Cluster, Rest-pause, Темповый суперсет, Частичные повторения. Пользователь может выбрать несколько методов одновременно, и их состояние визуально отображается как список меток внутри подхода.

Фактическая архитектура хранения для методов выполнения ещё не вынесена в отдельную схему БД, но UI-логика уже существует и функционирует локально.

Например:

• Drop Set;
• Rest Pause;
• Cluster;
• Tempo;
• Изометрия;
• Частичные повторения;
• Суперсет;
• любые будущие методы.

Можно выбрать несколько методов одновременно.

Архитектура должна позволять без изменений добавлять новые методы выполнения.

# ========================================== 10. РЕДАКТИРОВАНИЕ ТРЕНИРОВКИ

Любую тренировку можно открыть спустя любое время.

Текущее фактическое состояние:

• текущий экран TrainingPage поддерживает редактирование названия, даты, времени, типа тренировки, комментария, списка упражнений и параметров подходов в локальном state;
• упражнения можно добавлять, удалять и сворачивать;
• смена порядка упражнений и перетаскивание пока не реализованы как пользовательское взаимодействие; текущий UI предполагает управление через список в порядке добавления;
• в текущей реализации редактирование не связано с постоянным хранилищем, поэтому история и сохранённые результаты пока не являются полностью связанными с базой данных.

После открытия пользователь может:

• изменить название;
• изменить дату;
• изменить упражнения;
• изменить порядок упражнений;
• изменить подходы;
• изменить веса;
• изменить повторения;
• добавить комментарии;
• добавить фото;
• добавить видео.

История никогда не блокируется.

Все тренировки остаются редактируемыми.

# ========================================== 11. ПОРЯДОК УПРАЖНЕНИЙ

Во время тренировки упражнения можно свободно переставлять местами.

Изменение относится только к данной тренировке.

Шаблон остается неизменным.

# ========================================== 12. ДОПОЛНИТЕЛЬНЫЕ МАТЕРИАЛЫ

Для упражнения можно добавить:

• общий комментарий.

Для каждого отдельного подхода можно прикрепить:

• комментарий;
• фотографии;
• видео.

Это позволяет анализировать технику выполнения даже спустя длительное время.

==========================================
12.1 ХРАНЕНИЕ ВИДЕО
(АРХИТЕКТУРНОЕ ТРЕБОВАНИЕ)
==========================================

Пользователь может прикреплять видео к отдельным подходам во время тренировки или после ее завершения.

Видео предназначены для анализа техники выполнения и должны быть доступны в любой момент, даже спустя годы.

---

Ограничения:

• не более 8 видео на одну тренировку;
• максимальная продолжительность одного видео — 45 секунд.

---

После загрузки каждое видео автоматически обрабатывается.

Система:

• сжимает видео;
• сохраняет только оптимизированную версию;
• автоматически удаляет оригинальный файл.

Это позволяет значительно снизить стоимость хранения без заметной потери качества.

---

Все сохраненные видео постоянно хранятся в системе.

Пользователь может открыть любую прошлую тренировку и просмотреть все прикрепленные материалы независимо от даты их загрузки.

---

Архитектура хранения должна быть ориентирована на минимизацию расходов при сохранении долгосрочного доступа ко всем данным пользователя.

# ========================================== 13. АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ

Фактическое текущее состояние проекта:

• в UI уже реализованы основные интерактивные элементы Training: карточки, параметры, методы, сворачивание, поповеры, локальный scroll;
• в коде пока нет постоянного хранения полной тренировочной модели; все данные на этом этапе хранятся в React state;
• архитектурная модель Workout → Workout Exercise → Exercise → Sets и связанное хранение через exercise_id остаётся целевым архитектурным планом и должна быть реализована как отдельный этап, после чего UI будет переведён на persistent data model.

1. УНИКАЛЬНЫЙ ID

Каждая тренировка имеет собственный уникальный идентификатор.

Название тренировки никогда не используется системой как идентификатор.

Все внутренние связи работают исключительно через ID.

---

2. НЕИЗМЕНЯЕМОСТЬ ШАБЛОНОВ

После создания тренировки шаблон больше с ней не связан.

Изменение шаблона никогда не изменяет уже проведенные тренировки.

---

3. РАСШИРЯЕМАЯ АРХИТЕКТУРА

Система должна позволять без изменения существующей структуры добавлять:

• новые параметры упражнений;
• новые параметры подходов;
• новые методы выполнения;
• новые типы данных.

---

4. НЕЗАВИСИМОСТЬ ИСТОРИИ

Удаление шаблона не влияет на прошлые тренировки.

Удаление упражнения также не влияет на прошлые тренировки, потому что тренировки хранят связь через exercise_id.

История всегда должна открываться полностью независимо от текущего состояния системы.

---

5. САМОДОСТАТОЧНОСТЬ ТРЕНИРОВКИ

Каждая тренировка хранит полную информацию о себе.

Она не зависит от существования шаблонов, упражнений или других объектов.

Даже спустя годы тренировка должна открываться именно в том виде, в котором была сохранена пользователем.

---

6. ОСНОВА АНАЛИТИКИ

Каждое значение, введенное пользователем, должно сохраняться.

Например:

• упражнения;
• подходы;
• веса;
• повторения;
• RIR;
• отдых;
• комментарии;
• методы выполнения;
• фотографии;
• видео;
• дата;
• любые будущие параметры.

История тренировок является единственным источником данных для аналитики.

В дальнейшем именно на основе этих данных строятся:

• графики прогресса;
• динамика рабочих весов;
• динамика повторений;
• тренировочный объем;
• частота выполнения упражнений;
• статистика каждого упражнения;
• любые будущие аналитические отчеты.

==========================================
ГЛАВНЫЙ ПРИНЦИП
==========================================

Тренировка — это самостоятельный объект, содержащий всю информацию о конкретном тренировочном дне.

Шаблон — лишь инструмент для быстрого создания новой тренировки.

История тренировок никогда не теряет данные, не зависит от изменений шаблонов и является фундаментом всей аналитической системы Stubborn Ram.
