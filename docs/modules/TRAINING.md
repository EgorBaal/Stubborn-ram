# Блок: Тренировки

Версия: 1.0 (Утвержденная концепция)

==========================================
НАЗНАЧЕНИЕ
==========================================

Раздел "Тренировки" является основным рабочим разделом приложения.

Именно здесь пользователь:

• начинает тренировку;
• ведет тренировочный дневник;
• использует шаблоны;
• просматривает историю;
• управляет упражнениями;
• фиксирует результаты;
• прикрепляет фото и видео;
• формирует данные для будущей аналитики.

Раздел полностью самодостаточен и одинаково работает как для самостоятельного пользователя, так и для пользователя с тренером.

Тренер лишь получает доступ к уже существующим данным пользователя.

==========================================

Текущее состояние реализации (2026)

Ниже зафиксировано фактическое состояние текущей кодовой базы и production относительно архитектурной модели, описанной в этом документе.

Реализовано:

• Backend API для Training;

• постоянное хранение упражнений внутри тренировок;

После нажатия кнопки "Тренировки" на главной странице открывается раздел тренировок.

В верхней части расположены три вкладки:

Под вкладками располагается главная кнопка:

▶ Начать тренировку

# ========================================== 5. УПРАЖНЕНИЯ

Раздел содержит единую библиотеку упражнений приложения.

Упражнение представляет собой самостоятельную сущность.

Текущее фактическое состояние:

• UI-раздел Exercises реализован в TrainingExercisesPage и ExerciseList.
• Системные упражнения загружаются через Backend API.
• Системный каталог хранится в PostgreSQL.
• В production доступно 232 системных упражнения.
• Список фильтруется по muscle_group и поиску.
• Supabase больше не используется для загрузки упражнений Training.
• Пользовательские упражнения пока не реализованы.
• Создание новых упражнений и объединённый список системных + личных упражнений относятся к следующему этапу.

Пользователь может:

• создать упражнение;
• переименовать;
• удалить;
• использовать в шаблонах;
• использовать в тренировках.

Библиотека объединяет системные упражнения и личные упражнения пользователя.

# ========================================== 6. КАРТОЧКА УПРАЖНЕНИЯ

При нажатии на упражнение во время тренировки открывается его карточка.

В карточке отображаются:

• название упражнения;
• подходы;
• веса;
• повторения;
• комментарий к упражнению;
• дополнительные параметры.

# Также присутствуют три основные кнопки.

Текущее фактическое состояние реализации в коде:

• Карточка реализована в TrainingExerciseCard и поддерживает свободный ввод названия упражнения.
• Пользователь может выбрать упражнение через ExercisePickerOverlay.
• Карточка поддерживает сворачивание/разворачивание.
• Добавляется набор подходов через кнопку "Добавить подход".
• Каждый подход содержит набор параметров, сложность и методы интенсивности.
• Реализованы локальный комментарий, удаление упражнения и локальный поповер подтверждения удаления.
• Эти элементы уже реально работают в UI. Данные карточек и подходов сохраняются через Backend API в PostgreSQL при сохранении тренировки.

# 4.1 АРХИТЕКТУРА СИСТЕМЫ УПРАЖНЕНИЙ

Раздел «Упражнения» является единым источником данных для упражнений во всём приложении.

Не должно существовать отдельных списков упражнений в:

• странице «Упражнения»;
• карточке тренировки;
• ExercisePickerOverlay;
• других компонентах.

Все эти места должны получать упражнения из единого источника данных Supabase.

Общая схема:

Supabase

↓

Exercises Service

↓

├── Раздел «Упражнения»

└── ExercisePickerOverlay

    			↓

     Выбор упражнения

    			↓

    		Тренировка

---

Основная таблица:

exercises

Минимальные поля:

• id
• name
• muscle_group
• user_id
• created_at

Будущие поля:

• description
• image_url
• video_url
• updated_at

Поле user_id:

• NULL — системное упражнение, доступное всем пользователям.
• UUID пользователя — личное упражнение конкретного пользователя.

Пользовательские упражнения никогда автоматически не становятся общими для других пользователей.

---

На первом рабочем этапе необходимо создать базовый набор примерно из 100 упражнений.

Предварительные группы:

• Грудь — 15
• Спина — 15
• Ноги — 20
• Ягодицы — 10
• Плечи — 15
• Бицепс — 10
• Трицепс — 10
• Пресс — 10

Количество не является жёстким ограничением и в дальнейшем может расширяться.

---

Route:

/app/training/exercises

Это полноценный рабочий раздел, а не заглушка.

Он должен позволять:

• видеть группы мышц;
• открывать группу;
• видеть упражнения внутри группы;
• искать упражнения;
• создавать собственное упражнение.

Поиск работает по названию упражнения и использует тот же источник данных, что и обычный список упражнений.

ExercisePickerOverlay должен получать данные из той же таблицы exercises. Если упражнение появилось в разделе «Упражнения», оно автоматически должно быть доступно для выбора в тренировке.

Пользователь должен видеть объединённый список:

• системные упражнения;
• личные упражнения пользователя.

Системное упражнение:

user_id IS NULL

Личное упражнение:

user_id = текущий пользователь

При выборке для пользователя логика должна учитывать оба типа:

user_id IS NULL

OR

user_id = текущий пользователь

---

Пользователь может создать упражнение, которого нет в системной библиотеке.

В базе:

name:

<название упражнения>

user_id:

UUID текущего пользователя

Такое упражнение доступно только этому пользователю.

В будущем, если пользователь во время тренировки вручную вводит новое название упражнения и сохраняет тренировку, система должна:

1. Проверить, существует ли такое личное упражнение.
2. Если нет — создать его.
3. Получить его exercise_id.
4. Связать тренировку с этим exercise_id.

Нельзя хранить упражнение в тренировке только как строку.

Предполагаемая структура связи:

Workout

↓

Workout Exercise

↓

exercise_id

↓

Exercise

Для упражнений необходимо учитывать server-side проверку ownership и прав доступа.

Системные упражнения должны быть доступны всем авторизованным пользователям.

Личные упражнения должны быть доступны только:

• владельцу;
• при необходимости административной части приложения.

Пользователь не должен иметь возможность через клиентский код получить или изменить чужие личные упражнения.

Проверки доступа выполняются Backend API.

Работу с Backend API необходимо выносить в отдельный service:

src/modules/training/services/exercises/exerciseService.js

Предполагаемая ответственность:

• getExercises()
• getExercisesByGroup()

React-компоненты не должны содержать SQL или сложную логику работы с Backend API.

Текущий временный массив упражнений в ExerciseList.jsx является заглушкой и после завершения миграции на Backend API должен быть удалён.

---

Ключевые правила для будущей разработки:

1. 1. Один источник данных для упражнений — PostgreSQL через Backend API.
2. Страница «Упражнения» и ExercisePickerOverlay используют одну и ту же библиотеку.
3. Системные упражнения доступны всем пользователям.
4. Личные упражнения принадлежат конкретному пользователю и не становятся общими.
5. Тренировка должна хранить exercise_id, а не только название упражнения.
6. Подходы должны быть отдельными сущностями, связанными с конкретным упражнением внутри конкретной тренировки.
7. История упражнения строится через exercise_id.
8. Будущая аналитика должна получать данные из сохранённых тренировок и подходов, а не из визуальных компонентов.
9. UI-компоненты не должны самостоятельно содержать бизнес-логику работы с Backend API.
10. Перед изменением архитектуры необходимо сначала проверить эту документацию и существующий exerciseService, чтобы не создать второй независимый механизм хранения упражнений.

# ========================================== 7. НАСТРОЙКИ МЕТРИК

# ========================================== 8. ПОДХОДЫ

Каждый подход является самостоятельной единицей данных.

Текущее фактическое состояние в коде:

• подходы представлены как отдельные объекты в локальном state внутри TrainingExerciseCard;
• для каждого подхода есть поля weight, repetitions, difficulty, distance, calories, speed, power, incline, time, rir, rpe, rest, intensityMethods, isExtraOpen;
• UI уже реализует визуальное добавление, редактирование и раскрытие дополнительных параметров подхода;
• методы интенсивности и сложность поддерживаются в интерфейсе;
• постоянное хранение подходов подключено через Backend API и PostgreSQL.

Для каждого подхода можно хранить:

• repetitions;
• weight;
• difficulty;

В будущем:

• RPE;
• RIR;
• сет;
• дроп-сет;
• кластер;
• темп;
• пауза;
• дополнительное отягощение;
• другие параметры.

Именно подход является минимальной единицей хранения информации.

# ========================================== 9. МЕТОДЫ ВЫПОЛНЕНИЯ

Для каждого подхода можно указать методы выполнения.

Они открываются только после нажатия кнопки настроек.

Текущее фактическое состояние: в UI методы выполнения уже реализованы и управляются через локальный state подхода. В массив intensityMethods добавлены варианты Drop-set, Изометрия, Cluster, Rest-pause, Темповый суперсет, Частичные повторения. Пользователь может выбрать несколько методов одновременно, и их состояние визуально отображается как список меток внутри подхода.

Методы выполнения сохраняются в поле intensity_methods конкретного WorkoutSet. UI управляет ими через локальное состояние до сохранения тренировки.

Например:

• Drop Set;
• Rest Pause;
• Cluster;
• Tempo;
• Изометрия;
• Частичные повторения;

• любые будущие методы.

Можно выбрать несколько методов одновременно.

Архитектура должна позволять без изменений добавлять новые методы выполнения.

# ========================================== 10. РЕДАКТИРОВАНИЕ ТРЕНИРОВКИ

Любую тренировку можно открыть спустя любое время.

==========================================
12.1 ХРАНЕНИЕ ВИДЕО
(АРХИТЕКТУРНОЕ ТРЕБОВАНИЕ)
==========================================

Пользователь может прикреплять видео к отдельным подходам во время тренировки или после ее завершения.

Видео предназначены для анализа техники выполнения и должны быть доступны в любой момент, даже спустя годы.

---

Ограничения:

• не более 8 видео на одну тренировку;
• максимальная продолжительность одного видео — 45 секунд.

---

После загрузки каждое видео автоматически обрабатывается.

Система:

• сжимает видео;
• сохраняет только оптимизированную версию;
• автоматически удаляет оригинальный файл.

Это позволяет значительно снизить стоимость хранения без заметной потери качества.

---

Все сохраненные видео постоянно хранятся в системе.

Пользователь может открыть любую прошлую тренировку и просмотреть все прикрепленные материалы независимо от даты их загрузки.

---

Архитектура хранения должна быть ориентирована на минимизацию расходов при сохранении долгосрочного доступа ко всем данным пользователя.

# ========================================== 13. АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ

Фактическое текущее состояние проекта:

• UI реализует основные интерактивные элементы Training: карточки, параметры, методы, сворачивание, поповеры и локальное состояние текущей тренировки;
• постоянное хранение тренировочной модели реализовано через Backend API + PostgreSQL;

# ========================================== 2. КАНОНИЧЕСКАЯ СТРУКТУРА ДАННЫХ

Основная структура:

USER

↓

WORKOUT

↓

WORKOUT_EXERCISE

↓

WORKOUT_SET

Workout

• конкретная тренировка;
• принадлежит пользователю;
• имеет собственный уникальный ID.

WorkoutExercise

• конкретное упражнение внутри конкретной тренировки;
• связано с Exercise через exercise_id;
• имеет собственный уникальный ID;
• хранит порядок упражнения в тренировке;
• хранит параметры, относящиеся к выполнению упражнения
внутри конкретной тренировки.

WorkoutSet

• конкретный подход;
• является самостоятельной единицей данных;
• имеет собственный уникальный ID;
• принадлежит конкретному WorkoutExercise;
• содержит фактически выполненные параметры подхода.

# ========================================== 3. УНИКАЛЬНЫЕ ИДЕНТИФИКАТОРЫ

Каждая сущность получает собственный уникальный внутренний ID.

Минимально:

• workout_id;
• workout_exercise_id;
• workout_set_id;
• exercise_id.

Название упражнения, название тренировки или дата
никогда не используются в качестве идентификатора.

Все связи между сущностями выполняются через ID.

ID создаются системой автоматически.

# ========================================== 4. УПРАЖНЕНИЕ И EXERCISE_ID

Упражнение является самостоятельной сущностью.

Тренировка не должна хранить упражнение только как строку.

Правильная связь:

Workout

↓

WorkoutExercise

↓

exercise_id

↓

Exercise

Системные упражнения:

user_id IS NULL

Личные упражнения:

user_id = auth.uid()

При создании тренировки пользователь может выбрать
существующее системное или личное упражнение.

Если пользователь вводит новое упражнение вручную,
система должна:

1. проверить существование личного упражнения;
2. при отсутствии создать его;
3. получить exercise_id;
4. сохранить связь WorkoutExercise с этим exercise_id.

Это необходимо для корректной истории упражнения
и будущей аналитики.

# ========================================== 5. ПОДХОД КАК МИНИМАЛЬНАЯ ЕДИНИЦА ДАННЫХ

Каждый подход хранится отдельно.

Подход не является просто строкой или частью текста.

Для каждого WorkoutSet могут храниться:

• weight;
• repetitions;
• difficulty;
• RIR;
• RPE;
• rest;
• time;
• distance;
• speed;
• power;
• incline;
• intensityMethods;
• другие параметры.

Архитектура должна позволять добавлять новые параметры
без разрушения существующих данных.

# ========================================== 6. МЕТОДЫ ВЫПОЛНЕНИЯ

Методы выполнения относятся к конкретному подходу.

Например:

• Drop-set;
• Rest-pause;
• Cluster;
• Изометрия;
• Темповый метод;
• Частичные повторения;
• Суперсет;
• будущие методы.

Один подход может одновременно иметь несколько методов.

Архитектура должна позволять добавлять новые методы
без изменения существующей логики исторических данных.

# ========================================== 7. МЕДИА ПОДХОДА

К конкретному подходу пользователь может прикрепить
дополнительные материалы.

Поддерживаются:

• фотографии;
• видео;
• комментарий.

Материалы должны сохраняться постоянно.

Видео предназначены в том числе для анализа техники
и должны оставаться доступными спустя годы.

Физические файлы хранятся в Object Storage / S3.

В PostgreSQL сохраняются:

• ID;
• принадлежность объекту;
• тип файла;
• storage path;
• MIME type;
• необходимые технические параметры;
• дата создания;
• другая необходимая метаинформация.

Необходимо избегать хранения самих больших медиафайлов
непосредственно в PostgreSQL.

# ========================================== 8. ОБРАТНАЯ СВЯЗЬ

Обратная связь является частью исторического контекста
существующего объекта тренировки.

Она не должна превращаться в отдельный чат.

Обратная связь может относиться к:

• тренировке;
• упражнению;
• конкретному подходу.

Точная окончательная модель target scope
(workout / exercise / set) остается предметом отдельного
архитектурного решения.

Предпочтительный принцип:

существующий объект

↓

обратная связь

↓

текст / фото / видео

Обратная связь должна сохраняться отдельно от основных
данных тренировки, но иметь прямую связь с объектом,
к которому она относится.

# ========================================== 9. АВТОР И ВЛАДЕЛЕЦ ОБРАТНОЙ СВЯЗИ

Архитектура должна поддерживать различие между:

author_id

и

owner_id

Пример:

Комментарий пользователя:

Автор:
пользователь

Владелец данных:
пользователь

Комментарий тренера:

Владелец данных:
пользователь

Таким образом тренер может создавать обратную связь
по данным пользователя, не становясь владельцем этих данных.

Это соответствует общей архитектуре платформы.

# ========================================== 10. ОБРАТНАЯ СВЯЗЬ НЕ ЯВЛЯЕТСЯ ЧАТОМ

Внутри отдельного подхода не создается отдельная
переписка.

Не должно существовать:

Workout Set Chat

Exercise Chat

Workout Chat

Также не создаются отдельные чаты для:

• упражнений;
• подходов;
• тренировок;
• отчетов.

Общий чат платформы остается единственным чатом
между пользователем и тренером.

Обратная связь внутри тренировки является историческим
контекстом конкретного объекта, а не самостоятельной
перепиской.

Пользователь без тренера должен иметь возможность:

1. создать тренировку;
2. выбрать или создать упражнение;
3. добавить подходы;
4. заполнить параметры;
5. добавить комментарий;
6. прикрепить фотографии;
7. прикрепить видео;
8. сохранить тренировку;
9. закрыть приложение;
10. позже открыть тренировку;
11. увидеть все сохраненные данные;
12. открыть историю упражнения;
13. просматривать прошлые выполнения.

После сохранения все данные должны существовать в PostgreSQL через Backend API
и быть доступны после повторного открытия приложения,
на любом устройстве и спустя любое количество времени.

Использование только React state в качестве постоянного
хранилища не допускается.

# ========================================== 21. BACKEND API

Целевая архитектура:

React UI

↓

Training Services

↓

Backend API

↓

PostgreSQL + Object Storage

React-компоненты не должны самостоятельно содержать
сложную бизнес-логику работы с Backend API.

Для работы с данными используются отдельные services.

Минимально предполагаются сервисы для:

• workouts;
• workout exercises;
• workout sets;
• exercises;
• media;
• feedback.

Конкретная структура service layer определяется
при непосредственной реализации.

Текущее состояние:

Training API уже реализован для основных операций:

• получение системных упражнений;
• получение истории тренировок;
• получение тренировки по ID;
• создание тренировки;
• обновление тренировки;
• удаление тренировки.

Frontend использует trainingService для основных операций с тренировками.

# ========================================== 22. RLS И БЕЗОПАСНОСТЬ

Постоянные данные тренировок должны защищаться
через server-side проверки Backend API.

Пользователь имеет доступ к собственным данным.

Системные упражнения доступны авторизованным пользователям.

Личные упражнения доступны владельцу.

Будущий тренер получает доступ к данным пользователя
не через изменение ownership, а через связь
тренер ↔ пользователь и соответствующие права.

# ========================================== 23. ТРЕНЕР НЕ СТАНОВИТСЯ ВЛАДЕЛЬЦЕМ

Даже если тренер:

• изменяет программу;
• оставляет комментарий;
• добавляет видео;
• добавляет фотографию;
• дает рекомендации;

владельцем пользовательских данных остается пользователь.

Авторство сохраняется отдельно.

========================================== 24. ИСТОРИЯ НЕ ДОЛЖНА ЗАВИСЕТЬ
ОТ ТЕКУЩЕГО СОСТОЯНИЯ
==========================================

Прошлая тренировка должна оставаться доступной
даже если впоследствии:

• изменился шаблон;
• изменилось упражнение;
• упражнение было удалено из текущей библиотеки;
• изменился план;
• изменился тренер;
• сотрудничество завершилось.

Исторические данные не должны разрушаться
из-за изменения текущих объектов.

# ========================================== 25. ЧТО НЕ ДЕЛАЕМ

Не создаем:

• отдельный чат для каждого упражнения;
• отдельный чат для каждого подхода;
• отдельную историю с копиями тренировок;
• отдельную копию тренировки внутри отчета;
• отдельную копию тренировки внутри аналитики;
• отдельную базу тренировок для тренера;
• хранение тренировок только в React state.

Не дублируем один и тот же объект
в нескольких модулях.

# ========================================== 26. ТЕКУЩЕЕ UI-РЕШЕНИЕ ОБРАТНОЙ СВЯЗИ

В текущем интерфейсе рассматривается свайп подхода.

Свайп влево открывает действия с правой стороны.

Вместо трех независимых действий:

• фото;
• видео;
• комментарий;

целевым вариантом является одно действие:

«Обратная связь».

Нажатие открывает контекстный интерфейс,
в котором пользователь может работать
с обратной связью конкретного подхода.

Это UI-решение является представлением
существующей архитектуры данных и не должно
определять структуру базы данных.

Свайп вправо остается отдельным действием
для операций:

• Скопировать;
• Удалить.

# ========================================== 27. РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ МОДУЛЕЙ

ТРЕНИРОВКИ

Хранят и отображают фактические данные тренировочного
процесса.

ОТЧЕТ

Агрегирует существующие данные за выбранный период
и предоставляет их тренеру.

ЧАТ

Обеспечивает непрерывное общение и ссылки
на существующие объекты платформы.

ИСТОРИЯ УПРАЖНЕНИЯ

Представляет накопленные выполнения конкретного
упражнения.

АНАЛИТИКА

Анализирует сохраненные данные и строит
графики/статистику.

ОБРАТНАЯ СВЯЗЬ

Хранит контекстную информацию, связанную
с существующим объектом тренировки.

# ========================================== 28. НЕЗАКРЫТЫЕ АРХИТЕКТУРНЫЕ ВОПРОСЫ

Следующие решения еще необходимо принять
до окончательной реализации схемы:

1. На каком уровне допускается обратная связь:

   • Workout;
   • WorkoutExercise;
   • WorkoutSet;
   • либо на нескольких уровнях одновременно.

2. Точная структура Feedback.

Необходимо определить, будет ли это:

Feedback

или:

FeedbackMessage

и какие поля будут обязательными.

3. Структура вложений.

Необходимо окончательно определить:

• один или несколько файлов на одну обратную связь;
• допустимые типы;
• ограничения размера;
• обработку видео;
• порядок файлов.

4. Нужно определить, может ли пользователь добавлять
   несколько последовательных сообщений обратной связи
   к одному объекту или используется одна запись,
   которая редактируется.

5. Необходимо определить, должна ли обратная связь
   иметь собственную временную хронологию.

6. Необходимо определить точный UX открытия обратной связи:

• popover;
• bottom sheet;
• modal;
• отдельный экран.

7. Необходимо определить окончательный механизм
   перехода из истории упражнения к конкретной тренировке
   и конкретному подходу.

8. Необходимо определить правила удаления/редактирования
   исторической обратной связи.

9. Необходимо определить окончательную структуру
   параметров WorkoutSet и механизм расширения
   для будущих параметров.

10. Необходимо определить окончательную схему
    лимитов и обработки видео.

Эти вопросы не должны нарушать основной принцип
архитектуры.

# ========================================== 29. ПРИНЯТОЕ АРХИТЕКТУРНОЕ РЕШЕНИЕ

На текущем этапе утверждается следующая модель:

ТРЕНИРОВКА

→ является каноническим источником тренировочных данных;

УПРАЖНЕНИЕ

→ самостоятельная сущность, связанная через exercise_id;

ПОДХОД

→ самостоятельная сущность с собственным ID;

МЕДИА

→ постоянные данные, связанные с существующим объектом;

ОБРАТНАЯ СВЯЗЬ

→ контекстные исторические данные,
а не отдельный чат;

ЧАТ

→ единственный общий канал общения;

ОТЧЕТ

→ представление существующих данных за период;

ИСТОРИЯ УПРАЖНЕНИЯ

→ запрос к существующим тренировочным данным;

АНАЛИТИКА

→ обработка тех же канонических данных;

POSTGRESQL

→ постоянное хранилище структурированных данных;

OBJECT STORAGE / S3

→ постоянное хранение медиа;

BACKEND API

→ основной механизм проверки доступа к данным.

ГЛАВНЫЙ ПРИНЦИП СИСТЕМЫ
==========================================

Данные создаются один раз.

Данные сохраняются один раз.

Данные принадлежат пользователю.

Все остальные модули получают доступ
к тем же данным.

Подход является историческим объектом.

Аналитика является обработкой тех же данных.

от тренера, шаблонов и текущего состояния интерфейса.
