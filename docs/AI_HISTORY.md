- питанию;

- истории прогресса;
- сообщениям тренера;
- уведомлениям.

Использование мобильного формата позволяет сделать взаимодействие максимально удобным и похожим на настоящее приложение.

Разрабатывать сначала полноценную desktop-версию.

Отклонен.

---

Создавать мобильный опыт первым, затем адаптировать под большие экраны.

Выбран.

Причина:

Соответствует поведению пользователей и принципам современного мобильного продукта.

---

## Последствия для проекта

При создании каждого нового экрана необходимо:

- сначала проектировать мобильную версию;

- затем адаптировать под планшеты и ПК.

# Решение №4

Дата:

Август 2026

Статус:

Принято

---

## Принятое решение

Stubborn Ram строится по модульной архитектуре.

Каждый крупный функциональный раздел платформы является отдельным модулем.

Основные модули:

- HOME;
- PROFILE;
- TRAINING;
- FOOD;
- WEIGHT;
- REPORT;
- PHOTO_AND_MEASUREMENTS;
- CHAT;
- ANALYTICS;
- LIBRARY;
- NOTIFICATIONS.

Каждый модуль имеет собственную документацию, ответственность и правила работы.

---

## Причина решения

Платформа планируется как долгосрочный продукт, который будет постоянно развиваться.

Создание единого большого приложения без разделения на модули приведет к:

- сложному сопровождению;
- смешиванию логики разных разделов;
- увеличению количества ошибок;
- сложности добавления новых функций.

Модульная структура позволяет развивать каждый раздел независимо, сохраняя общую архитектуру.

---

## Рассмотренные варианты

### Вариант 1

Создать один большой набор страниц и компонентов без четкого разделения.

Отклонен.

Причина:

Такой подход усложняет поддержку и масштабирование.

---

### Вариант 2

Создать независимые модули с общей архитектурой.

Выбран.

Причина:

Позволяет добавлять новые функции без переписывания существующего проекта.

---

## Последствия для проекта

При разработке новых функций необходимо:

- определить, к какому модулю относится функция;
- изучить документацию соответствующего модуля;
- сохранять границы ответственности между разделами;
- не переносить логику одного модуля в другой без необходимости.

Любой новый крупный функционал сначала должен быть описан как часть существующего модуля или как новый модуль.

## Принятое решение

---

## Принятое решение

Все взаимодействия с внешними системами должны проходить через отдельный сервисный слой.

Компоненты пользовательского интерфейса не должны напрямую обращаться к:

- Supabase;
- базе данных;
- Edge Functions;
- внешним API.

UI отвечает только за отображение и пользовательское взаимодействие.

Сервисный слой отвечает за:

- получение данных;
- отправку данных;
- взаимодействие с внешними системами;
- обработку бизнес-операций.

---

## Причина решения

Разделение интерфейса и внешней логики позволяет сохранить:

- простоту компонентов;
- возможность замены внешних сервисов;
- удобство тестирования;
- безопасность;
- масштабируемость проекта.

Если компоненты напрямую работают с базой данных, со временем возникает:

- дублирование запросов;
- сложное изменение логики;
- нарушение архитектуры;
- трудность поддержки.

---

## Рассмотренные варианты

### Вариант 1

Компоненты напрямую обращаются к Supabase.

Отклонен.

Причина:

Создает сильную связанность интерфейса и базы данных.

Любое изменение структуры данных требует изменения большого количества компонентов.

---

### Вариант 2

Использовать отдельный сервисный слой.

Выбран.

Причина:

Позволяет разделить ответственность между частями приложения.

---

## Последствия для проекта

Новые функции должны проектироваться следующим образом:

Пользовательский интерфейс

↓

Service Layer

↓

Supabase / API / Edge Functions

↓

Database

---

При создании нового функционала необходимо заранее определить:

- какой сервис отвечает за данные;
- какие операции доступны;
- где находится бизнес-логика.

Компоненты должны оставаться максимально простыми и отвечать только за интерфейс.

# Решение №9

Август 2026

---

## Принятое решение

В Stubborn Ram используется ролевая модель пользователей.

Основные роли:

- Client (клиент);
- Coach (тренер);
- Admin (администратор).

Каждая роль имеет собственные возможности, ограничения и сценарии использования.

---

## Причина решения

Платформа является системой взаимодействия между тренером и клиентами.

Для корректной работы необходимо разделить:

- личные данные пользователей;
- доступ к информации;
- ответственность участников системы;
- пользовательские сценарии.

Без четкого разделения ролей невозможно безопасно реализовать:

- отчеты;
- программы тренировок;
- питание;
- аналитику;
- чат;
- историю прогресса.

---

## Рассмотренные варианты

### Вариант 1

Все пользователи имеют одинаковый уровень доступа.

Отклонен.

Причина:

Не обеспечивает безопасность и не соответствует модели работы тренера с клиентами.

---

### Вариант 2

Использовать отдельные роли с разными правами.

Выбран.

Причина:

Соответствует реальному бизнес-процессу онлайн-коучинга.

---

## Последствия для проекта

При проектировании новых функций необходимо учитывать роль пользователя.

Примеры:

Client:

- видит свои данные;
- отправляет отчеты;
- отслеживает прогресс;
- получает рекомендации.

Coach:

- управляет клиентами;
- анализирует отчеты;
- создает программы;
- дает обратную связь.

Admin:

- управляет системой;
- контролирует технические процессы.

- кто является владельцем данных;
- кто может их читать;
- кто может изменять данные;
- какие ограничения доступа существуют.

## Причина решения

Большая платформа содержит множество взаимосвязанных систем:

- пользователи;
- тренеры;
- программы;
- питание;
- отчеты;
- аналитика;
- коммуникация;
- уведомления.

Попытка реализовать все одновременно увеличивает:

- сложность;
- количество ошибок;
- время разработки;
- риск неправильных решений.

---

### Вариант 1

Высокий риск усложнения проекта и потери контроля.

### Вариант 2

Создавать продукт последовательными этапами.

Выбран.

Причина:

Позволяет проверять каждую часть системы и улучшать продукт постепенно.

---

## Последствия для проекта

Каждый новый этап должен:

- иметь понятную цель;
- иметь описание в ROADMAP.md;
- иметь требования в документации;
- проходить проверку перед переходом к следующему этапу.

Новые функции добавляются только после понимания их роли в общей архитектуре.

Главный принцип:

Сначала создается надежный фундамент.

Затем на нем строится расширение платформы.
