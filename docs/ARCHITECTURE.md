# Назначение документа

Этот документ описывает фактическую архитектуру проекта Stubborn Ram.

Он показывает, как устроен проект, как взаимодействуют его части и по каким принципам развивается кодовая база.

---

# Главный принцип

Проект строится по принципу:

**простая архитектура, которую легко расширять.**

Каждый новый модуль должен добавляться без переписывания существующего проекта.

# Архитектурные слои проекта

## App

Ответственность:

- запуск корневого приложения.

Допустимые зависимости:

- Router.

Запрещённые зависимости:

- прямое использование логики конкретного модуля.

---

## Router

Ответственность:

- маршрутизация лендинга, авторизации, анкеты и внутреннего приложения.

Допустимые зависимости:

- Layout;
- Pages.

Запрещённые зависимости:

- UI-логика конкретной страницы.

---

## Auth

Ответственность:

- состояние сессии и защита маршрутов.

Допустимые зависимости:

- Services;
- Context.

Запрещённые зависимости:

- page-specific стили.

---

## AppLayout

Ответственность:

- общая оболочка внутренних страниц.

Допустимые зависимости:

- Pages;
- общие компоненты.

Запрещённые зависимости:

- модульная логика конкретной страницы.

---

## Pages

Ответственность:

- отдельная страница приложения.

Допустимые зависимости:

- Components;
- Hooks;
- Services.

Запрещённые зависимости:

- импорт другой Page;
- CSS другой страницы.

---

## Components

Ответственность:

- отдельные блоки интерфейса.

Допустимые зависимости:

- Hooks;
- другие UI-компоненты.

Запрещённые зависимости:

- импорт Page.

---

## Hooks

Ответственность:

- повторно используемая логика состояния.

Допустимые зависимости:

- Services.

Запрещённые зависимости:

- page-specific UI-слои.

---

## Services

Ответственность:

- работа с Supabase и внешними интеграциями.

Допустимые зависимости:

- другие сервисы;
- низкоуровневые клиенты.

Запрещённые зависимости:

- UI-компоненты;
- Page-компоненты;
- CSS.

---

# Текущее состояние приложения

На текущем этапе реализованы:

- домашняя страница приложения;
- страница профиля;
- защищённый внутренний shell;
- маршруты для лендинга, авторизации, анкеты и внутренней части;
- базовая авторизация через Supabase;
- страницы-заглушки для ряда модулей.

Особое архитектурное изменение текущего этапа:

- страницы больше не зависят от общего `.app-page`-класса;
- каждая страница имеет собственный Page.css;
- локальная геометрия HomePage перенесена в локальный CSS;
- ProfilePage и другие страницы изолированы от общей page-оболочки.

---

# Текущие ограничения

1. Маршруты внутреннего приложения пока не разделены на полноценный модульный набор.
2. Некоторые placeholder-страницы имеют похожую структуру и нуждаются в дальнейшей унификации.
3. Часть общей инфраструктуры всё ещё используется как общая платформа для всех модулей.

Эти ограничения не требуют переписывания архитектуры, но должны учитываться при добавлении новой функциональности.

---

# Принцип разделения ответственности

Каждый слой отвечает только за свою задачу.

- Pages отвечают за страницу.
- Components отвечают за UI-блоки.
- Hooks отвечают за поведение и состояние.
- Services отвечают за данные и интеграции.
- AppLayout отвечает за общий shell.

Никакой слой не должен брать на себя обязанности другого слоя без необходимости.

↓

# Состояние приложения

На текущем этапе используется React State.

Основное состояние анкеты хранится внутри Questionnaire.

По мере появления личного кабинета и авторизации возможно внедрение глобального управления состоянием, если это будет действительно необходимо.

---

# Работа с серверной частью

Любые обращения к базе данных выполняются через Supabase.

Компоненты взаимодействуют с серверной частью исключительно через слой services.

Именно services инкапсулирует всю работу с Supabase и внешними сервисами.

Компоненты интерфейса не должны напрямую обращаться к серверу.

Правильно:

```

Component

↓

Service

↓

Supabase

↓

Database

```

Неправильно:

```

Component

↓

fetch()

↓

Database

```

---

# Работа с Email

Отправка писем осуществляется через Edge Function.

Схема работы:

```

Frontend

↓

Supabase

↓

Edge Function

↓

Resend

↓

Email

```

Отправка выполняется через сервис Resend с корпоративного адреса:

noreply@stubbornram.ru

Это позволяет безопасно хранить API-ключи, исключает их попадание во фронтенд и обеспечивает корректную доставку писем.

---

# Работа с базой данных

Структура базы данных поддерживается в отдельном документе DATABASE_SCHEMA.md.

Любое изменение структуры данных сначала отражается в DATABASE_SCHEMA.md, после чего реализуется в Supabase.

Это позволяет поддерживать архитектуру и документацию синхронизированными.

---

# Работа с CSS

Каждый крупный компонент имеет собственный CSS-файл.

Не создавать один огромный style.css.

Структура должна оставаться модульной.

---

# Масштабирование

При добавлении нового раздела создается новый компонент.

Не расширять существующий компонент бесконечно.

Если файл начинает быстро увеличиваться — его необходимо разделить.

# Архитектурные принципы

✔ Один компонент = одна задача.

✔ Один файл = одна ответственность.

✔ Повторяющийся код выносится.

✔ Не использовать сложные решения без необходимости.

✔ Новые функции должны добавляться без переписывания существующего проекта.

✔ Компоненты должны быть максимально независимыми.

✔ Код должен быть понятен через год без дополнительного объяснения.

✔ Секреты (API-ключи) никогда не размещаются во фронтенде.

✔ Взаимодействие с внешними сервисами осуществляется через отдельный слой сервисов или Edge Functions.

---

# Заключение

Архитектура Stubborn Ram строится вокруг простоты, читаемости и масштабируемости.

На текущем этапе проект представляет собой полноценное веб-приложение с подключенной серверной частью, автоматическим деплоем, собственной базой данных и системой отправки заявок.

Дальнейшее развитие проекта будет происходить путем добавления новых независимых модулей без изменения существующей архитектуры.

Следующим фундаментальным этапом развития проекта является проектирование структуры базы данных (DATABASE_SCHEMA.md), вокруг которой будут строиться авторизация, личные кабинеты, программы тренировок, питание, отчеты и остальные подсистемы платформы.
