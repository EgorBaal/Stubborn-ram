# Назначение документа

Этот документ описывает архитектуру проекта Stubborn Ram.

Его задача — объяснить, как устроен проект, как взаимодействуют его части и по каким принципам развивается кодовая база.

Любой новый разработчик должен понимать архитектуру проекта после прочтения данного документа.

---

# Главный принцип

Проект строится по принципу:

**простая архитектура, которую легко расширять.**

Каждый новый модуль должен добавляться без переписывания существующего проекта.

# Архитектура компонентов

Каждый компонент отвечает только за одну задачу.

Компонент не должен одновременно:

- отображать интерфейс;
- хранить большое количество логики;
- выполнять сетевые запросы;
- заниматься валидацией.

По возможности эти обязанности разделяются.

---

# Текущее состояние App Shell

Реализованы:

- HOME экран приложения;
- BottomTabBar;
- Header, Notification Section, Module Grid;
- страницы-заглушки модулей.

Текущее ограничение этапа:

- AppLayout используется как общий layout для внутренних маршрутов приложения, однако часть страниц по-прежнему рендерит BottomTabBar напрямую.

Это не блокирует текущую разработку, но требует консолидации перед дальнейшим расширением App Shell.

---

# Известные технические ограничения текущего этапа

1. Отсутствует route-level code splitting для клиентских страниц.
2. Есть дублирующиеся маршруты для части модулей (`/app/activity` и `/app/activity-module`, `/app/report` и `/app/report-module`).
3. В клиенте присутствуют тяжелые медиа-ресурсы, требующие дальнейшей оптимизации загрузки.

Эти ограничения запланированы к проработке до масштабирования бизнес-логики модулей.

По мере появления личного кабинета и авторизации возможно внедрение глобального управления состоянием, если это будет действительно необходимо.

# Работа с серверной частью

Любые обращения к базе данных выполняются через Supabase.

Компоненты взаимодействуют с серверной частью исключительно через слой services.

Именно services инкапсулирует всю работу с Supabase и внешними сервисами.

Компоненты интерфейса не должны напрямую обращаться к серверу.

Правильно:

```
Component

↓

Service

↓

Supabase

↓

Database
```

Неправильно:

```
Component

↓

fetch()

↓

Database
```

---

# Работа с Email

Отправка писем осуществляется через Edge Function.

Схема работы:

```
Frontend

↓

Supabase

↓

Edge Function

↓

Resend

↓

Email
```

Отправка выполняется через сервис Resend с корпоративного адреса:

noreply@stubbornram.ru

Это позволяет безопасно хранить API-ключи, исключает их попадание во фронтенд и обеспечивает корректную доставку писем.

---

# Работа с базой данных

Структура базы данных поддерживается в отдельном документе DATABASE_SCHEMA.md.

Любое изменение структуры данных сначала отражается в DATABASE_SCHEMA.md, после чего реализуется в Supabase.

Это позволяет поддерживать архитектуру и документацию синхронизированными.

---

# Работа с CSS

Каждый крупный компонент имеет собственный CSS-файл.

Не создавать один огромный style.css.

Структура должна оставаться модульной.

---

# Масштабирование

При добавлении нового раздела создается новый компонент.

Не расширять существующий компонент бесконечно.

Если файл начинает быстро увеличиваться — его необходимо разделить.

# Архитектурные принципы

✔ Один компонент = одна задача.

✔ Один файл = одна ответственность.

✔ Повторяющийся код выносится.

✔ Не использовать сложные решения без необходимости.

✔ Новые функции должны добавляться без переписывания существующего проекта.

✔ Компоненты должны быть максимально независимыми.

✔ Код должен быть понятен через год без дополнительного объяснения.

✔ Секреты (API-ключи) никогда не размещаются во фронтенде.

✔ Взаимодействие с внешними сервисами осуществляется через отдельный слой сервисов или Edge Functions.

---

# Заключение

Архитектура Stubborn Ram строится вокруг простоты, читаемости и масштабируемости.

На текущем этапе проект представляет собой полноценное веб-приложение с подключенной серверной частью, автоматическим деплоем, собственной базой данных и системой отправки заявок.

Дальнейшее развитие проекта будет происходить путем добавления новых независимых модулей без изменения существующей архитектуры.

Следующим фундаментальным этапом развития проекта является проектирование структуры базы данных (DATABASE_SCHEMA.md), вокруг которой будут строиться авторизация, личные кабинеты, программы тренировок, питание, отчеты и остальные подсистемы платформы.
