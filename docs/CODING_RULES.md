# CODING_RULES.md

# Правила разработки проекта Stubborn Ram

Версия: 0.1

---

# Назначение документа

Этот документ определяет единые правила написания кода в проекте Stubborn Ram.

Все изменения в проекте должны соответствовать данным правилам.

Главная цель — сохранить код простым, понятным и легко поддерживаемым даже спустя несколько лет.

---

# Основной принцип

Код пишется не только для компьютера.

Код пишется для людей.

Через год разработчик должен быстро понимать, что происходит в любом файле.

---

# Простота важнее сложности

Всегда выбирать наиболее простое решение.

Не использовать сложные конструкции, если задача решается проще.

---

# Один компонент — одна задача

Компонент должен отвечать только за одну ответственность.

Плохо:

```
Questionnaire.jsx

- отображает интерфейс

- валидирует данные

- отправляет запросы

- считает калории

- открывает модальные окна
```

Хорошо:

```
Questionnaire.jsx

↓

QuestionCard.jsx

↓

validation.js

↓

services
```

Каждый файл занимается только своей задачей.

---

# Один файл — одна ответственность

Каждый файл отвечает только за один тип логики.

Например

```
questions.js

↓

только вопросы
```

```
validation.js

↓

только проверка
```

```
QuestionCard.jsx

↓

только отображение
```

---

# Не создавать большие компоненты

Если компонент становится слишком большим, его необходимо разделить.

Ориентиры:

до 200 строк — отлично;

200–350 строк — допустимо;

более 350 строк — оценить возможность разделения;

более 500 строк — разделение обязательно.

---

# Не дублировать код

Если одинаковый код встречается несколько раз, его необходимо вынести.

Например:

- функцию;
- компонент;
- helper;
- service;
- hook.

---

# Логика отделяется от интерфейса

JSX должен содержать минимум сложной логики.

По возможности вычисления выполняются заранее.

Плохо:

```
JSX

↓

много условий

↓

много вычислений

↓

длинные выражения
```

Хорошо:

```
логика

↓

готовые данные

↓

JSX
```

---

# Работа с API

Компоненты не обращаются к серверу напрямую.

Все запросы проходят через папку:

```
services/
```

---

# Работа с данными

Любая бизнес-логика должна находиться отдельно от отображения.

Например:

```
Questionnaire

↓

validation

↓

services

↓

API
```

---

# Именование файлов

Компоненты

PascalCase

```
Hero.jsx

QuestionCard.jsx

SupportCarousel.jsx
```

---

Вспомогательные файлы

camelCase

```
validation.js

helpers.js

calculateCalories.js
```

---

# Именование переменных

Использовать понятные английские названия.

Плохо

```
a

b

temp

data2
```

Хорошо

```
currentQuestion

clientWeight

dailyCalories

proteinTarget
```

---

# CSS

Каждый крупный компонент имеет собственный CSS-файл.

Не создавать один общий CSS на весь проект.

---

# Комментарии

Комментарии писать только тогда, когда они действительно помогают понять код.

Не комментировать очевидные вещи.

---

# Перед изменением существующего кода

Перед любым изменением необходимо ответить на три вопроса.

1.

Что именно меняется?

2.

Почему это меняется?

3.

Не сломает ли это другие части проекта?

---

# Перед созданием нового компонента

Ответить на вопросы.

Можно ли использовать существующий компонент?

Можно ли расширить существующий компонент без ухудшения архитектуры?

Если нет — создать новый компонент.

---

# Перед установкой новой библиотеки

Спросить себя.

Можно ли решить задачу без новой зависимости?

Если можно — не устанавливать библиотеку.

Каждая новая зависимость увеличивает сложность проекта.

---

# Git

Каждый законченный этап разработки считается отдельной версией проекта.

После завершения крупного этапа рекомендуется:

- обновить документацию;
- сделать резервную копию;
- зафиксировать изменения в Git.

---

# Документация

Документация является частью проекта.

После завершения любого крупного этапа необходимо обновить соответствующие файлы в папке docs.

---

# Главное правило проекта

Всегда отдавать предпочтение:

простоте,

понятности,

стабильности,

масштабируемости.

Красивый код — это код, который легко читать, легко изменять и который не приходится переписывать при добавлении нового функционала.
