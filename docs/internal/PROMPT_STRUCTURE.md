# PROMPT_STRUCTURE.md

# Стандарт формирования промптов для AI-разработчика

Версия документа: 1.0

Последнее обновление: август 2026

---

# Назначение документа

PROMPT_STRUCTURE.md определяет единый стандарт формирования задач для AI-разработчика (GitHub Copilot Agent).

Документ предназначен для ChatGPT, который формирует промпты для Copilot.

Цель документа:

- уменьшить количество ошибок;
- сократить расход контекста и кредитов;
- обеспечить стабильное качество реализации;
- сохранить единую архитектуру проекта;
- исключить самостоятельные архитектурные решения AI.

Данный документ описывает не архитектуру проекта, а правила постановки задач AI-разработчику.

---

# Общий принцип

Каждый новый промпт должен иметь одинаковую структуру.

Структура промптов не должна изменяться без отдельного архитектурного решения.

Последовательность важнее скорости.

---

# Общий порядок формирования промпта

Каждый промпт должен состоять из следующих этапов:

1. Изучение документации.
2. Анализ задачи.
3. Определение области изменений.
4. Реализация только утвержденной области.
5. Проверка результата.
6. Подготовка отчета.

---

# Классификация задач

Каждая задача перед началом работы должна быть отнесена к одной из трех категорий.

Light Task

Небольшие изменения интерфейса.

Например:

- CSS;
- UI;
- отступы;
- цвета;
- анимации;
- иконки;
- небольшие исправления компонентов.

Для Light Task:

- использовать уже изученный контекст текущей сессии;
- не перечитывать обязательную документацию без необходимости;
- изучать только файлы, непосредственно относящиеся к задаче.

---

Standard Task

Обычная разработка функциональности.

Например:

- новый экран;
- новый компонент;
- изменение существующей логики;
- навигация;
- маршрутизация;
- работа с состоянием.

Для Standard Task:

- изучить обязательную документацию;
- изучить документацию текущего модуля;
- при необходимости изучить связанные файлы проекта.

---

Architecture Task

Изменения архитектуры проекта.

Например:

- база данных;
- авторизация;
- Application Shell;
- маршрутизация приложения;
- изменение структуры модулей;
- изменение ответственности компонентов.

Для Architecture Task:

обязательно изучить всю необходимую архитектурную документацию перед началом работы.

---

# Определение категории задачи

Перед началом выполнения AI обязан самостоятельно определить категорию задачи.

После определения категории AI обязан следовать только правилам данной категории.

Запрещается использовать требования более высокой категории для задач более низкой категории без объективной необходимости.

Если в процессе работы категория задачи изменилась, AI обязан сообщить об этом пользователю и только после подтверждения перейти к новому уровню требований.

---

# Изучение документации

Перед выполнением любой задачи AI обязан определить категорию задачи и только после этого изучить документацию в объеме, соответствующем данной категории.

Первым всегда читается:

docs/core/AGENTS.md

После этого читаются все документы из папки:

docs/core

в установленном порядке.

Эти документы являются обязательными для любой задачи.

Они определяют:

- правила работы AI;
- контекст проекта;
- архитектуру;
- правила разработки;
- дизайн-систему;
- рабочий процесс.

---

# Использование уже изученного контекста

AI не должен повторно перечитывать документацию без необходимости.

Если задача относится к текущему этапу разработки и необходимый контекст уже изучен в рамках текущей сессии, следует использовать его.

Повторное чтение документации требуется только если:

- начинается работа над новой подсистемой;
- происходит переход к другому модулю;
- изменяется архитектура;
- изменяется база данных;
- возникает необходимость проверки документации.

Повторное чтение обязательной документации для каждого небольшого исправления запрещается.

Главная цель — минимизация расхода контекста и кредитов без потери качества реализации.

---

# Документация по текущей задаче

После изучения обязательной документации AI определяет, какие документы относятся к текущей задаче.

Например.

Работа с Home:

↓

docs/modules/HOME.md

Работа с Training:

↓

docs/modules/TRAINING.md

Работа с базой данных:

↓

docs/architecture/DATABASE_SCHEMA.md

Работа с авторизацией:

↓

docs/architecture/AUTH_ARCHITECTURE.md

Работа с пользовательскими сценариями:

↓

docs/flows/

AI должен читать только документацию, необходимую для выполнения текущей задачи.

---

# Дополнительная документация

AI имеет право самостоятельно изучить дополнительные документы проекта, если это действительно необходимо.

Например:

- проверка архитектурной зависимости;
- анализ существующей реализации;
- проверка фирменного стиля;
- поиск повторно используемых компонентов;
- проверка существующей логики;
- предотвращение дублирования;
- анализ влияния изменений на другие части проекта.

Без необходимости читать дополнительные документы запрещается.

---

# Изменение документации

Документация проекта изменяется только если:

- изменилось поведение системы;
- изменился архитектурный контракт;
- появился новый стандарт разработки;
- пользователь отдельно попросил обновить документацию.

AI запрещается изменять документацию без объективной необходимости.

---

# Анализ перед реализацией

До внесения любых изменений AI обязан определить:

- что именно изменяется;
- зачем выполняется изменение;
- какие файлы будут затронуты;
- затрагивается ли архитектура;
- затрагивается ли документация.

Если требования недостаточно понятны —

ОСТАНОВИТЬСЯ.

Сообщить об этом.

Запросить уточнение.

Самостоятельно принимать решения запрещено.

---

# Investigation Mode

Если причина проблемы неизвестна, AI запрещается сразу изменять код.

Сначала необходимо провести исследование.

Этап исследования должен включать:

- определение первопричины;
- анализ затрагиваемых файлов;
- определение области изменений;
- объяснение причины возникновения проблемы;
- предложение возможных вариантов решения.

До окончания исследования создание patch запрещается.

Реализация начинается только после определения причины либо после отдельного подтверждения пользователя.

---

# Правило остановки

Если в процессе исследования выясняется, что задача выходит за первоначально утвержденную область изменений, AI обязан остановить реализацию.

AI должен:

- объяснить причину;
- перечислить дополнительные области изменений;
- дождаться отдельного подтверждения пользователя.

Самостоятельно расширять задачу запрещается.

---

# Контроль области изменений

Каждый промпт обязан содержать два раздела.

Разрешено:

- какие файлы изменяются;
- какие папки изменяются;
- какие действия разрешены.

Запрещено:

- изменение несвязанных файлов;
- изменение бизнес-логики;
- изменение дизайна;
- изменение архитектуры;
- рефакторинг вне утвержденной области.

AI не имеет права самостоятельно расширять область задачи.

---

# Принцип локальности

Каждая задача должна решаться минимальным количеством изменений.

Предпочтение всегда отдается устранению первопричины проблемы.

Запрещается:

- переписывать компонент полностью;
- выполнять рефакторинг без необходимости;
- заменять рабочую реализацию новой без объективной причины.

Минимальное корректное изменение предпочтительнее масштабной переработки.

---

# Архитектурные изменения

Если во время выполнения задачи AI обнаруживает необходимость:

- изменить архитектуру;
- изменить структуру проекта;
- изменить ответственность модулей;
- изменить устройство Application Shell;

работа должна быть немедленно остановлена.

AI обязан сообщить о найденной проблеме и дождаться отдельного утверждения.

Самостоятельно принимать архитектурные решения запрещено.

---

# Независимость модулей

Каждый модуль проекта должен оставаться независимым.

Изменение одного модуля не должно требовать изменения других модулей без отдельного согласования.

Любой модуль должен иметь возможность быть полностью замененным.

---

# Стандартная структура промпта

Каждый промпт должен содержать:

1. Контекст задачи.

2. Цель.

3. Разрешенные изменения.

4. Запрещенные изменения.

5. Последовательность реализации.

6. Проверку результата.

7. Итоговый отчет.

---

# Проверка результата

После выполнения задачи AI обязан провести проверку.

При необходимости проверить:

- импорты;
- маршрутизацию;
- ссылки;
- старые пути;
- неиспользуемые файлы;
- дублирование;
- сборку проекта.

Если задача затрагивает код —

обязательно выполнить:

npm run build

если изменение затрагивает кодовую базу и сборка проекта доступна.

---

# Политика проверки

Тип проверки зависит от категории задачи.

Light Task

- выполнить npm run build, если изменялся код или CSS;
- при работе с мобильным интерфейсом рекомендуется проверка на реальном устройстве.

Standard Task

- обязательно выполнить npm run build;
- проверить затронутую функциональность.

Architecture Task

- выполнить npm run build;
- проверить архитектурные зависимости;
- убедиться, что изменение не нарушило работу других модулей.

Если изменялась только документация, запуск npm run build не требуется.

---

# Политика коммитов

Каждая задача завершается только после проверки пользователем.

После подтверждения успешной проверки AI рекомендует создать отдельный Git-коммит.

Запрещается объединять несколько независимых исправлений в один коммит без отдельного указания пользователя.

---

# Итоговый отчет

После выполнения задачи AI обязан предоставить отчет.

Отчет должен содержать:

- краткое описание выполненной работы;
- список измененных файлов;
- список обновленной документации;
- результаты проверки;
- затронута ли архитектура;
- следующий рекомендуемый шаг.

---

# Эффективность

Не читать документацию, не относящуюся к задаче.

Не расходовать контекст без необходимости.

Предпочитать небольшие точные промпты.

Не объединять несколько независимых задач в один большой промпт.

---

# Повторное использование контекста

Если в рамках текущей сессии уже были изучены:

- документация;
- архитектура;
- необходимые файлы;

AI обязан повторно использовать уже полученный контекст.

Повторное чтение допускается только при объективной необходимости.

Приоритет всегда отдается использованию уже имеющегося контекста.

---

# Оптимизация расхода кредитов

При формировании промптов необходимо стремиться к минимальному расходу контекста.

Следует:

- использовать уже изученный контекст текущей сессии;
- читать только документацию, относящуюся к задаче;
- открывать только необходимые файлы;
- не выполнять повторный поиск без необходимости;
- не запускать исследование всего проекта для локальных изменений.

Для небольших исправлений предпочтительны короткие точные промпты.

Полное изучение проекта допускается только для Architecture Task.

---

# Стиль коммуникации

Отчеты должны быть короткими и понятными.

AI должен сообщать:

- что сделано;
- почему это сделано;
- что осталось сделать.

Длинные объяснения приводятся только по запросу.

---

# Главный принцип

Главная цель разработки — не быстро выполнить задачу.

Главная цель — сохранить качество проекта.

Каждый промпт должен способствовать:

- предсказуемой реализации;
- стабильной архитектуре;
- чистому коду;
- повторному использованию решений;
- минимизации технического долга.

Последовательность важнее скорости.

Качество важнее количества.

Архитектура важнее временных решений.
