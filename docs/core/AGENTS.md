# AGENTS.md

# Руководство по разработке с использованием AI

## Платформа Stubborn Ram CRM

Версия: 1.1

---

# Назначение

Этот документ определяет обязательные правила для любого AI-агента, работающего над проектом Stubborn Ram.

Он распространяется на любого AI-помощника для разработки, включая (но не ограничиваясь):

- GitHub Copilot
- Codex
- Claude Code
- Cursor AI
- будущих AI-агентов для разработки

Каждый AI-агент обязан соблюдать данный документ перед внесением любых изменений в проект.

Настоящий документ имеет приоритет над любым стандартным поведением AI-помощника.

---

# Источник истины

Источником истины является документация.

Если документация и код противоречат друг другу — приоритет имеет документация.

Документация изменяется только после явного одобрения.

---

# Обязательный порядок действий перед каждой задачей

Перед началом любой задачи AI ОБЯЗАН выполнить следующие шаги.

## Шаг 1. Прочитать всю основную документацию в установленном порядке

Прочитать каждый документ из папки `docs/core` в следующем порядке:

1. AGENTS.md
2. PROJECT_CONTEXT.md
3. WORKFLOW.md
4. ARCHITECTURE.md
5. CODING_RULES.md
6. DESIGN_SYSTEM.md
7. DEVELOPMENT_RULES.md

Этот шаг является обязательным.

---

## Шаг 2. Определить, какие документы относятся к текущей задаче

После прочтения основной документации определить, какие части проекта затрагивает текущая задача.

Примеры:

- Работа с Home → прочитать `docs/modules/HOME.md`
- Работа с Training → прочитать `docs/modules/TRAINING.md`
- Работа с базой данных → прочитать `docs/architecture/DATABASE_SCHEMA.md`
- Работа с авторизацией → прочитать `docs/architecture/AUTH_ARCHITECTURE.md`
- Работа с пользовательскими сценариями → прочитать документы из `docs/flows/`

---

## Шаг 3. Читать только документацию, непосредственно относящуюся к задаче

AI не должен автоматически читать всю папку `docs`.

AI должен читать только:

1. обязательные документы из `docs/core`;
2. документы, непосредственно относящиеся к текущей задаче.

Это правило используется по умолчанию.

---

# Дополнительные права на чтение

AI имеет право читать дополнительные документы проекта только тогда, когда существует объективная необходимость проверить одно из следующего:

- архитектурную зависимость;
- существующую реализацию;
- фирменный стиль и язык дизайна продукта;
- способы повторного использования компонентов;
- ранее принятые решения и исторический контекст;
- риск нарушения работы других частей проекта.

Это право допускается использовать только при наличии объективной необходимости и достаточного обоснования.

---

# Обязательные правила

AI обязан соблюдать следующие правила.

Запрещается:

- изменять архитектуру без одобрения;
- изменять бизнес-логику без явного указания;
- выполнять рефакторинг вне утверждённой области задачи;
- изменять несвязанные файлы;
- добавлять функциональность, которая не была запрошена;
- самостоятельно принимать архитектурные решения;
- догадываться о намерениях пользователя.

Если задача сформулирована неоднозначно —

ОСТАНОВИТЬСЯ.

Запросить уточнение.

---

# Важный принцип

Если во время выполнения задачи AI обнаруживает проблему архитектуры, противоречие в документации или необходимость изменить существующую структуру проекта —

необходимо немедленно остановиться.

AI обязан:

- сообщить о найденной проблеме;
- объяснить, почему она возникла;
- предложить возможные варианты решения;

но

не имеет права самостоятельно реализовывать архитектурные изменения.

Любые архитектурные изменения требуют отдельного согласования.

---

# Философия разработки

Проект разрабатывается по следующей последовательности.

1. Идея.

2. Обсуждение.

3. Документация.

4. Одобрение.

5. Реализация.

6. Проверка.

7. Обновление документации.

8. Git Commit.

Изменение этой последовательности запрещено.

---

# Решения по продукту

Все ключевые решения по проекту должны быть зафиксированы в документации.

Если решение ещё не задокументировано —

реализация не начинается.

Сначала обновляется документация.

Только после этого допускается реализация.

---

# Перед написанием кода

Перед изменением любого файла AI обязан определить:

- что именно требуется изменить;
- зачем это изменение необходимо;
- какие файлы будут затронуты;
- какие зависимости могут быть затронуты;
- затрагивается ли архитектура;
- требуется ли обновление документации.

Если хотя бы один из этих пунктов невозможно определить однозначно —

необходимо остановиться и запросить уточнение.

Самостоятельно делать предположения запрещено.

---

# Работа с документацией

Документация является обязательной частью проекта.

Если изменение влияет на архитектуру, структуру проекта, процесс разработки или поведение системы —

необходимо определить, требует ли это обновления документации.

Документация должна оставаться актуальной.

Устаревшая документация не допускается.

Если документация противоречит реализации —

необходимо сообщить об этом до начала выполнения задачи.

---

# Принцип минимальных изменений

Если документ или файл уже существует,

AI должен стремиться изменять его минимально.

Разрешается:

- добавлять новые разделы;
- уточнять существующие разделы;
- исправлять ошибки;
- обновлять ссылки;
- актуализировать информацию.

Запрещается:

- полностью переписывать документ;
- массово сокращать документ;
- изменять структуру документа без явного указания пользователя.

Каждое изменение должно быть минимально необходимым для решения поставленной задачи.

---

# Правила работы с Git

После завершения задачи AI обязан определить, готова ли работа к фиксации в системе контроля версий.

Если задача завершена полностью и проект находится в рабочем состоянии —

необходимо рекомендовать выполнить:

1. Проверку проекта.

2. Git Add.

3. Git Commit.

4. Git Push.

AI не должен выполнять Git-команды самостоятельно, если это не было явно запрошено пользователем.

---

# Когда необходимо остановиться

AI обязан остановить выполнение задачи в следующих случаях:

- отсутствует необходимая документация;
- документация противоречит архитектуре;
- задача требует изменения архитектуры;
- задача требует изменения структуры проекта;
- требования пользователя неоднозначны;
- существует несколько возможных вариантов реализации без явного выбора.

В таких случаях AI должен:

1. остановить выполнение;

2. описать обнаруженную проблему;

3. объяснить, почему невозможно безопасно продолжить работу;

4. дождаться решения пользователя.

---

# Проверка после реализации

После завершения реализации AI обязан определить, какие проверки необходимо выполнить.

При необходимости проверить:

- корректность импортов;
- маршрутизацию;
- ссылки между файлами;
- отсутствие старых путей;
- отсутствие неиспользуемых файлов;
- отсутствие дублирования;
- соответствие архитектуре;
- необходимость обновления документации.

Если задача затрагивает код —

необходимо выполнить сборку проекта:

```
npm run build
```

если это возможно.

При необходимости также выполнить:

- lint;
- тесты;
- дополнительные проверки, относящиеся к текущей задаче.

---

# Итоговый отчёт

После завершения задачи AI обязан предоставить структурированный отчёт.

Отчёт должен содержать:

1. Краткое описание выполненной работы.

2. Список изменённых файлов.

3. Список обновлённой документации.

4. Какие проверки были выполнены.

5. Затронута ли архитектура проекта.

6. Следующий рекомендуемый шаг.

Отчёт должен быть кратким, понятным и содержать только фактическую информацию.

---

# Финальный чек-лист

Перед завершением задачи AI должен убедиться, что:

- выполнены только разрешённые изменения;
- не были изменены несвязанные файлы;
- архитектура не была изменена без согласования;
- документация остаётся актуальной;
- при необходимости выполнена сборка проекта;
- подготовлен итоговый отчёт.

Если хотя бы один пункт не выполнен —

задача считается незавершённой.

---

# Главный принцип

Главная цель разработки —

не максимально быстро выполнить задачу.

Главная цель —

сохранить качество проекта на долгосрочную перспективу.

Каждое изменение должно делать проект:

- более понятным;
- более поддерживаемым;
- более масштабируемым;
- более предсказуемым;
- более стабильным.

Качество всегда важнее скорости.

Архитектура всегда важнее временных решений.

Последовательность всегда важнее количества выполненных задач.
