# WORKFLOW.md

# Workflow разработки проекта Stubborn Ram

Версия: 1.1  
Статус: актуализировано под целевую архитектуру  
Дата обновления: сентябрь 2026

---

# Назначение документа

Документ описывает единый процесс разработки проекта.

Все новые функции и архитектурно значимые изменения создаются по одному и тому же сценарию.

Документация является источником истины для реализации.

---

# Этап 1. Идея

Новая идея сначала обсуждается в ChatGPT.

На этом этапе определяется:

- необходимость функции;
- логика работы;
- пользовательский сценарий;
- влияние на другие разделы;
- необходимость изменения архитектуры;
- необходимость изменения данных или инфраструктуры.

На этом этапе код не изменяется.

---

# Этап 2. Проектирование

После обсуждения создается архитектура функции.

Формируется «серая карточка», содержащая полное описание будущего раздела или изменения.

В зависимости от задачи в ней фиксируются:

- цель;
- пользовательский сценарий;
- состояния;
- данные;
- permissions;
- зависимости;
- UI;
- API;
- media;
- уведомления;
- analytics;
- edge cases.

Если изменение затрагивает инфраструктуру, это должно быть явно указано.

---

# Этап 3. Проверка архитектуры

Перед документированием проверяется:

- нет ли конфликта с существующей архитектурой;
- не дублируется ли существующая функция;
- не требуется ли новый внешний сервис;
- не меняется ли ownership;
- не меняется ли permission model;
- не появляется ли новая canonical source;
- не возникает ли зависимости одного модуля от другого.

Если существует несколько архитектурных вариантов, выбор выполняется до реализации.

---

# Этап 4. Документация

После утверждения решение переносится в соответствующий документ.

Для модулей используется:

```text
docs/modules/...
```

Для архитектурных изменений используются соответствующие корневые документы проекта.

Документация становится источником истины.

При разработке новых модулей обязательно учитывать принцип локальной изоляции:

- собственный Page.jsx;
- собственный Page.css;
- собственные локальные компоненты;
- собственные hooks/services при необходимости.

---

# Этап 5. Подготовка задачи для реализации

После обновления документации формируется конкретная задача для Codex.

В задаче должны быть определены:

- что изменить;
- зачем изменить;
- какие файлы предполагается затронуть;
- какая документация является источником истины;
- какие ограничения нельзя нарушать;
- какие проверки необходимо выполнить.

Codex сначала изучает соответствующую документацию и только после этого приступает к реализации.

---

# Этап 6. Реализация

Реализация выполняется минимальными изменениями.

Приоритет:

1. соответствие документации;
2. безопасность;
3. стабильность;
4. простота;
5. производительность;
6. минимальный scope.

Не следует одновременно переписывать несколько независимых частей проекта.

Если в процессе реализации обнаружена архитектурная проблема, реализация останавливается до принятия решения.

---

# Этап 7. Проверка

После реализации проверяется:

- соответствие документации;
- корректность импортов;
- маршрутизация;
- ссылки между файлами;
- отсутствие старых путей;
- отсутствие неиспользуемых файлов;
- отсутствие дублирования;
- изоляция модуля;
- permissions;
- loading/error/empty states;
- визуальное соответствие Design System;
- mobile layout;
- desktop layout.

Если задача затрагивает код, необходимо по возможности выполнить:

```text
npm run build
```

---

# Этап 8. Функциональная проверка

Для пользовательской функции необходимо пройти основной сценарий от начала до конца.

Например:

```text
Открыть страницу
↓
Создать объект
↓
Сохранить
↓
Обновить страницу
↓
Проверить сохранение
↓
Изменить
↓
Проверить результат
```

Для доступа тренера дополнительно проверяются:

- owner;
- active relationship;
- archived relationship;
- разрешенные действия;
- запрещенные действия.

Для media дополнительно проверяются:

- upload;
- processing;
- preview;
- private access;
- deletion/retention.

---

# Этап 9. Проверка безопасности

Для изменений, связанных с данными или доступом, необходимо проверить:

- серверную permission check;
- ownership;
- отсутствие обхода API;
- отсутствие секретов во frontend;
- приватность файлов;
- rate limiting для чувствительных endpoint;
- корректность ошибок.

Frontend hiding не считается security control.

---

# Этап 10. Завершение

После завершения обновляется:

```text
CHANGELOG.md
```

При необходимости обновляются:

```text
PROJECT_CONTEXT.md
ARCHITECTURE.md
ROADMAP.md
DATABASE_SCHEMA.md
SECURITY.md
PERMISSIONS_ARCHITECTURE.md
```

Если изменилась архитектура, соответствующий документ должен быть актуализирован.

---

# Этап 11. Git

После полной проверки определяется готовность к фиксации.

Рекомендуемый порядок:

1. проверить проект;
2. проверить diff;
3. проверить отсутствие секретов;
4. Git Add;
5. Git Commit;
6. Git Push.

Git-команды не выполняются автоматически без явного запроса пользователя.

Commit должен представлять логически завершенный этап.

---

# Этап 12. После завершения

После commit задача считается завершенной только если:

- документация соответствует реализации;
- build проходит;
- основной сценарий проверен;
- нет известных критических ошибок;
- изменения зафиксированы в Git.

Следующая задача начинается с чтения актуальной документации, а не с предположений о текущем состоянии проекта.

---

# Когда необходимо остановиться

AI обязан остановить выполнение, если:

- отсутствует необходимая документация;
- документация противоречит архитектуре;
- задача требует изменения архитектуры;
- задача требует изменения структуры проекта;
- требования неоднозначны;
- существует несколько возможных вариантов реализации без явного выбора;
- обнаружен риск потери данных;
- обнаружен риск нарушения безопасности;
- обнаружена необходимость новой внешней интеграции.

В таких случаях необходимо:

1. остановить выполнение;
2. описать проблему;
3. объяснить последствия;
4. предложить варианты;
5. дождаться решения пользователя.

---

# Правило миграций

Любая миграция инфраструктуры выполняется отдельно от обычной feature-разработки.

Перед миграцией необходимо:

1. определить целевую архитектуру;
2. определить source и target;
3. создать backup;
4. проверить rollback;
5. подготовить staging;
6. выполнить миграцию;
7. проверить данные;
8. проверить авторизацию;
9. проверить файлы;
10. проверить внешние интеграции;
11. только после этого переключать production traffic.

Старая инфраструктура не удаляется до завершения rollback window.

---

# Правило database changes

Изменение database schema требует:

```text
Discussion
↓
DATABASE_SCHEMA.md
↓
Approval
↓
Migration
↓
Verification
```

Нельзя менять production database только ради удобства текущего frontend-кода.

---

# Правило новых сервисов

Новый внешний сервис можно подключать только после проверки:

- зачем он нужен;
- нельзя ли использовать существующий сервис;
- где обрабатываются данные;
- где физически хранятся данные;
- есть ли API/contract;
- стоимость;
- ограничения;
- возможность замены provider;
- юридические требования.

После согласования сервис должен подключаться через соответствующий service/adapter.

---

# Правило изменений общей инфраструктуры

Если задача относится только к одному модулю, нельзя менять:

- AppLayout;
- BottomTabBar;
- global CSS;
- Router;
- общие services

без доказанной необходимости.

Если изменение общей инфраструктуры действительно необходимо, оно оформляется как отдельное архитектурное изменение.

---

# Правило минимального scope

Одна задача должна решать одну логическую проблему.

Не следует одновременно:

- менять дизайн;
- переносить backend;
- переписывать database;
- менять permissions;
- исправлять другой несвязанный баг.

Исключение — когда эти изменения являются частью одного утвержденного архитектурного этапа.

---

# Definition of Done

Задача считается завершенной, если:

- решение соответствует документации;
- реализация соответствует утвержденной архитектуре;
- изменены только необходимые файлы;
- модульная изоляция сохранена;
- security checks выполнены;
- пользовательский сценарий проверен;
- build выполнен;
- документация обновлена при необходимости;
- CHANGELOG обновлен;
- изменения готовы к Git commit.

---

# Главный принцип

Сначала принимается решение.

Потом оно документируется.

Потом реализуется.

Потом проверяется.

И только после этого считается частью Stubborn Ram.

```text
Idea
↓
Discussion
↓
Design
↓
Documentation
↓
Approval
↓
Implementation
↓
Verification
↓
Documentation Update
↓
Git Commit
```

Нельзя перескакивать через архитектурные этапы ради скорости.

Цель workflow — сделать разработку предсказуемой и не допускать повторных миграций и архитектурных переделок.
