# ARCHITECTURE.md

# Архитектура проекта Stubborn Ram

Версия: 1.2

Последнее обновление: сентябрь 2026

---

# Назначение документа

Этот документ описывает фактическую архитектуру проекта Stubborn Ram.

Он показывает, как устроен проект, как взаимодействуют его части и по каким принципам развивается кодовая база.

---

# Главный принцип

Проект строится по принципу:

**простая архитектура, которую легко расширять.**

Каждый новый модуль должен добавляться без переписывания существующего проекта.

---

# Текущая архитектура проекта

```text
Пользователь
↓
React App
↓
Router
↓
Layout
↓
Pages
↓
Components / Hooks / Services
↓
Backend API
↓
PostgreSQL / Object Storage / Workers
```

Frontend не имеет прямого доступа к PostgreSQL, внутренним серверным ресурсам или секретам инфраструктуры.

# Архитектурные слои проекта

## App

Ответственность:

- запуск корневого приложения.

Допустимые зависимости:

- Router.

Запрещённые зависимости:

- прямое использование логики конкретного модуля.

---

## Router

Ответственность:

- маршрутизация лендинга, авторизации, анкеты и внутреннего приложения.

Допустимые зависимости:

- Layout;
- Pages.

Запрещённые зависимости:

- UI-логика конкретной страницы.

---

## Auth

Ответственность:

- состояние сессии;
- защита маршрутов;
- взаимодействие с Auth Service.

Допустимые зависимости:

- Services;
- Context.

Запрещённые зависимости:

- page-specific стили.

---

## AppLayout

Ответственность:

- общая оболочка внутренних страниц.

Допустимые зависимости:

- Pages;
- общие компоненты.

Запрещённые зависимости:

- модульная логика конкретной страницы.

---

## Pages

Ответственность:

- отдельная страница приложения.

Допустимые зависимости:

- Components;
- Hooks;
- Services.

Запрещённые зависимости:

- импорт другой Page;
- CSS другой страницы.

---

## Components

Ответственность:

- отдельные блоки интерфейса.

Допустимые зависимости:

- Hooks;
- другие UI-компоненты.

Запрещённые зависимости:

- импорт Page.

---

## Hooks

Ответственность:

- повторно используемая логика состояния.

Допустимые зависимости:

- Services.

Запрещённые зависимости:

- page-specific UI-слои.

---

## Services

Ответственность:

- работа с Backend API;
- работа с внешними интеграциями;
- изоляция frontend от конкретной серверной реализации.

Допустимые зависимости:

- другие сервисы;
- низкоуровневые клиенты.

Запрещённые зависимости:

- UI-компоненты;
- Page-компоненты;
- CSS;
- прямой доступ к PostgreSQL.

Frontend должен взаимодействовать с серверной частью только через Services.

---

# Backend API

Backend API является единой серверной точкой доступа приложения.

Он отвечает за:

- авторизацию;
- проверку сессии;
- проверку прав доступа;
- работу с профилями;
- coach-client relationships;
- чат;
- отчёты;
- media;
- тренировки;
- signed URLs для файлов;
- серверную бизнес-логику;
- работу с PostgreSQL;
- работу с Object Storage;
- постановку фоновых задач.

Frontend не должен обращаться непосредственно к базе данных или Object Storage.

---

# PostgreSQL

PostgreSQL является основной базой данных приложения.

В PostgreSQL хранятся структурированные данные:

- пользователи и профили;
- связи coach-client;
- сообщения;
- отчёты;
- обратная связь;
- metadata файлов;
- тренировки;
- упражнения;
- настройки;
- другие бизнес-данные проекта.

Структура базы данных описывается отдельно в:

`docs/architecture/DATABASE_SCHEMA.md`

Этот документ является источником истины для структуры базы данных.

---

# Object Storage

Фотографии, видео и другие пользовательские файлы не хранятся непосредственно в PostgreSQL.

Для них используется S3-совместимое объектное хранилище.

Object Storage используется для:

- фотографий;
- видео;
- документов;
- вложений чата;
- вложений отчётов;
- media тренировок.

Пользовательские файлы по умолчанию являются приватными.

Доступ к ним осуществляется через Backend API после проверки прав пользователя и временные signed URLs.

В PostgreSQL хранится metadata файла и его связь с соответствующим объектом приложения.

---

# Workers

Длительные и тяжёлые операции не должны выполняться внутри обычного HTTP-запроса.

Worker используется для фоновых операций, например:

- обработка видео;
- конвертация видео;
- сжатие media;
- другие длительные операции.

На начальном этапе Worker может работать на том же сервере, что и Backend API.

При росте нагрузки он может быть вынесен на отдельный сервер без изменения frontend API.

---

# Текущий MVP

На текущем этапе основным приоритетом является MVP для реального ведения первых клиентов.

MVP включает:

- Auth;
- Coach / Client Relationship;
- Chat;
- Media;
- Reports;
- Coach Feedback;
- базовый Coach Cabinet;
- базовый Client Cabinet;
- Training persistence после критических модулей MVP.

Главный критерий MVP:

**тренер должен иметь возможность реально вести клиента через Stubborn Ram от общения до получения недельного отчёта и отправки обратной связи.**

Остальные модули платформы не отменяются.

Они реализуются после завершения MVP.

---

# Работа с серверной частью

Любые обращения к серверной части выполняются через Services.

Схема:

```text
Component
↓
Hook
↓
Service
↓
Backend API
↓
PostgreSQL / Object Storage / Worker
```

Допускается прямой вызов Service из Component, если Hook для конкретной операции не требуется.

Запрещено:

```text
Component
↓
PostgreSQL
```

или:

```text
Component
↓
Object Storage
```

или:

```text
Component
↓
внутренний серверный ресурс
```

Frontend не должен содержать credentials базы данных, Object Storage или других серверных секретов.

---

# Работа с Email

Email является внешней интеграцией Backend.

Схема:

```text
Frontend
↓
Service
↓
Backend API
↓
Email Service
↓
Email Provider
↓
Email
```

Frontend не взаимодействует с Email Provider напрямую.

Конкретный email provider является заменяемой инфраструктурной зависимостью.

Это позволяет заменить поставщика без изменения пользовательского интерфейса.

---

# Работа с базой данных

Структура базы данных поддерживается в отдельном документе:

`docs/architecture/DATABASE_SCHEMA.md`

Любое изменение структуры данных сначала отражается в `DATABASE_SCHEMA.md`, после чего реализуется в целевой PostgreSQL.

Это позволяет поддерживать архитектуру и документацию синхронизированными.

---

# Работа с Media

Media является отдельным инфраструктурным слоем.

Основные правила:

- PostgreSQL хранит metadata;
- Object Storage хранит сами файлы;
- пользовательские файлы приватны;
- доступ проверяется сервером;
- signed URLs используются для безопасной выдачи файлов;
- автоматическое удаление пользовательских отчётов и их media не используется;
- политика хранения не должна удалять пользовательские материалы по возрасту.

Подробная архитектура media описывается в:

`docs/modules/MEDIA.md`

если такой документ существует или будет создан.

---

# Работа с Chat

Chat использует:

```text
PostgreSQL
+
WebSocket
+
Object Storage
```

PostgreSQL является источником истины для истории сообщений.

WebSocket используется для realtime-доставки сообщений.

Если WebSocket временно недоступен, сообщения не должны теряться.

История должна быть доступна через обычный Backend API.

Вложения чата хранятся через общий Media слой.

Подробная архитектура Chat описывается в:

`docs/modules/CHAT.md`

---

# Работа с Reports

Reports использует:

```text
PostgreSQL
+
Object Storage
+
Backend API
```

Отчёт содержит структурированные данные и ссылки на media.

Клиент может:

- создать отчёт;
- добавить текст;
- прикрепить фотографии;
- прикрепить видео;
- прикрепить другие необходимые материалы;
- отправить отчёт тренеру.

Тренер может:

- открыть отчёт;
- просмотреть материалы;
- написать обратную связь;
- прикрепить собственные материалы;
- отправить обратную связь клиенту.

Отправленные отчёты и их media не удаляются автоматически.

Подробная логика описывается в:

`docs/modules/REPORT.md`

---

# Работа с Training

Training является отдельным бизнес-модулем.

Canonical model:

```text
Workout
↓
WorkoutExercise
↓
WorkoutSet
```

Training не должен зависеть от конкретного frontend-хранилища.

Медиа тренировок используют общий Media слой.

Training persistence подключается к Backend API и PostgreSQL.

Существующий Training UI не должен переписываться без необходимости только из-за миграции backend.

---

# Работа с CSS

Каждый крупный компонент имеет собственный CSS-файл.

Не создавать один огромный `style.css`.

Структура должна оставаться модульной.

---

# Масштабирование

При добавлении нового раздела создается новый компонент или модуль.

Не расширять существующий компонент бесконечно.

Если файл начинает быстро увеличиваться — его необходимо разделить.

При увеличении нагрузки допускается:

- вынесение Worker на отдельный сервер;
- добавление дополнительных серверных ресурсов;
- добавление CDN;
- оптимизация Object Storage;
- другие инфраструктурные изменения.

При этом публичный Backend API и frontend architecture должны оставаться стабильными.

---

# Bottom Tab Bar

BottomTabBar существует в проекте только в одном экземпляре.

Он рендерится исключительно внутри AppLayout.

Ни одна страница не должна самостоятельно импортировать или рендерить BottomTabBar.

Если какой-либо модуль содержит BottomTabBar, при миграции он удаляется из страницы и остаётся только в AppLayout.

---

# 3. Независимость модулей

Каждый модуль отвечает только за своё содержимое.

Модуль не отвечает за:

- навигацию приложения;
- общую оболочку;
- размещение BottomTabBar;
- размещение TopBar;
- глобальные уведомления.

---

# 4. Поведение страниц

Каждая страница самостоятельно определяет своё поведение.

---

# Independent Scroll Contexts

- AppLayout не владеет вертикальной прокруткой страниц.
- Один route = один независимый scroll context.
- Главная страница является фиксированной и не использует вертикальный scroll.
- Для большинства страниц используется единый переиспользуемый компонент PageScroll.
- Chat использует собственную специализированную систему прокрутки сообщений.
- Scroll одного модуля никогда не влияет на другой модуль.

Например:

- фиксированная страница;
- прокручиваемая страница;
- прокрутка под BottomTabBar;
- контент ограничен рабочей областью.

Изменение поведения одной страницы не должно требовать изменения других страниц.

---

# Startup Screen Architecture

- Startup Screen используется только при холодном запуске приложения.
- Startup Screen показывается только авторизованным пользователям.
- Startup Screen не используется для лендинга.
- После завершения холодного запуска Startup Screen не участвует в runtime-сценариях.
- Startup Screen имеет собственную независимую внутреннюю логику и не зависит от Loading Overlay.

---

# Loading Overlay Architecture

- Loading Overlay используется только внутри уже запущенного приложения.
- Loading Overlay используется только для длительных операций.
- Loading Overlay не используется во время холодного запуска приложения.
- Loading Overlay является единой системой ожидания проекта для тяжёлых runtime-операций.
- Startup Screen и Loading Overlay являются полностью независимыми подсистемами.

Loading Overlay применяется для:

- загрузки библиотеки;
- загрузки аналитики;
- открытия тренировок;
- открытия питания;
- загрузки фотографий;
- открытия видео;
- буферизации видео;
- загрузки истории;
- получения данных с сервера;
- синхронизации;
- загрузки отчётов;
- загрузки и отправки media;
- любых будущих тяжёлых операций.

---

# Infrastructure Reuse Principle

- Любая новая функциональность должна максимально использовать существующую инфраструктуру проекта.
- Запрещается создавать новые Provider, Context или глобальные системы, если существующая инфраструктура уже решает задачу.
- Предпочтение всегда отдаётся расширению существующей архитектуры.
- Любая новая тяжёлая операция должна подключаться к существующей Loading System (LoadingProvider + LoadingOverlay), а не к локальным отдельным loader-системам.
- Новый внешний сервис не подключается только ради будущей функции.
- Платные инфраструктурные сервисы подключаются только тогда, когда они необходимы текущему этапу.

---

# 5. Главный принцип проекта

Любой модуль должен быть полностью заменяемым.

Должна существовать возможность полностью переписать один модуль, удалить его или заменить другим без необходимости изменять остальные модули или инфраструктуру приложения.

---

# Архитектурные ограничения по миграции и разработке

Новые правила становятся обязательными для всех последующих этапов разработки.

Их соблюдение обязательно при:

- переносе модулей;
- миграции страниц;
- добавлении новых модулей;
- создании новых компонентов;
- изменении структуры приложения.

Любая миграция должна сохранять принцип независимости модулей и не допускать дублирования ответственности между модулем и AppLayout.

Миграция с Supabase выполняется поэтапно.

Supabase не удаляется до завершения новой backend-инфраструктуры, проверки данных и подтверждения работоспособности production-сценариев.

---

# Состояние приложения

На текущем этапе используется React State там, где локального состояния достаточно.

Основное состояние конкретных страниц и компонентов не должно без необходимости переноситься в глобальное состояние.

Авторизация и серверные данные получают данные через соответствующие Services.

Глобальное управление состоянием вводится только при наличии реальной архитектурной необходимости.

---

# Принцип миграции

Во время миграции запрещено переписывать frontend только ради смены backend-провайдера.

Существующий UI должен по возможности продолжать работать через Services.

Основная задача миграции:

```text
Supabase Services
↓
Backend API Services
```

а не:

```text
Переписать весь frontend
↓
новый backend
```

Существующие компоненты и страницы изменяются только там, где это действительно необходимо для подключения новой архитектуры.

# Архитектурные принципы

✔ Один компонент = одна задача.

✔ Один файл = одна ответственность.

✔ Повторяющийся код выносится.

✔ Не использовать сложные решения без необходимости.

✔ Новые функции должны добавляться без переписывания существующего проекта.

✔ Компоненты должны быть максимально независимыми.

✔ Код должен быть понятен через год без дополнительного объяснения.

✔ Секреты (API-ключи) никогда не размещаются во фронтенде.

✔ Взаимодействие с backend и внешними сервисами осуществляется через отдельный слой Services.

✔ PostgreSQL является источником истины для структурированных данных.

✔ Object Storage является источником истины для пользовательских файлов.

✔ История сообщений и отчётов не должна теряться из-за проблем realtime или frontend.

✔ Пользовательские media не должны удаляться автоматически.

✔ Платные внешние сервисы не подключаются заранее без необходимости текущего этапа.

✔ Provider-specific реализация должна быть изолирована от UI и бизнес-модулей.

---

# Заключение

Архитектура Stubborn Ram строится вокруг простоты, читаемости, стабильности и масштабируемости.

Целевая backend-архитектура проекта:

```text
React / PWA
↓
Services
↓
Backend API
├── PostgreSQL
├── Object Storage
├── WebSocket
└── Workers
```

Supabase является legacy-инфраструктурой текущей миграции и не является целевой архитектурой проекта.

Текущий этап развития проекта — MVP для реального ведения первых клиентов.

После завершения MVP проект будет расширяться независимыми модулями без повторной фундаментальной миграции backend.
