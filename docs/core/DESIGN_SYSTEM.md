# DESIGN_SYSTEM.md

# Дизайн-система проекта Stubborn Ram

Версия: 1.0  
Статус: актуализировано  
Дата обновления: сентябрь 2026

---

# 1. Назначение документа

Данный документ описывает правила оформления интерфейса Stubborn Ram.

Его цель — сохранить единый стиль приложения независимо от количества экранов и компонентов.

Любой новый экран должен соответствовать этим правилам.

Дизайн-система относится к frontend и не зависит от выбранной backend-инфраструктуры.

---

# 2. Общая концепция

Stubborn Ram — это веб-приложение для сопровождения клиентов.

Интерфейс должен восприниматься как современное мобильное приложение, которым удобно пользоваться каждый день.

Основные качества дизайна:

- минимализм;
- строгость;
- современность;
- удобство;
- скорость восприятия;
- отсутствие визуального шума;
- спокойствие;
- надежность;
- профессиональный вид.

Главная задача интерфейса — быстро донести информацию и помочь пользователю выполнить действие без лишних усилий.

---

# 3. Основной стиль

Используется:

- темная тема;
- большое количество свободного пространства;
- минимум цветов;
- крупные карточки;
- плавные анимации;
- хорошая читаемость;
- максимальный акцент на содержании.

Интерфейс не должен быть визуально перегружен.

---

# 4. Цветовая палитра

## Основной фон

```text
#080808
```

Используется как основной фон приложения.

## Карточки

```text
#121212
```

Используется для:

- карточек;
- форм;
- модальных окон;
- информационных блоков.

## Акцент

```text
#ff6200
```

Акцент используется только для важных элементов:

- основных кнопок;
- активных состояний;
- ссылок;
- прогресса;
- элементов навигации;
- важных действий.

Не использовать акцентный цвет в большом количестве.

## Основной текст

```text
#ffffff
```

## Вторичный текст

```text
#bdbdbd
```

## Ошибка

```text
#ff4d4f
```

## Успешное действие

```text
#2ecc71
```

В проекте используется один основной акцентный цвет.

Не добавлять новые самостоятельные акцентные цвета без отдельного архитектурного решения.

---

# 5. Шрифт

Основной шрифт:

```text
Comfortaa
```

Используется во всем проекте.

Не смешивать разные шрифты без необходимости.

---

# 6. Типографика

Типографика должна обеспечивать четкую визуальную иерархию.

Используются уровни:

- основной заголовок;
- заголовок секции;
- заголовок карточки;
- основной текст;
- вторичный текст;
- подпись;
- служебный текст.

Не использовать большое количество разных размеров текста.

Точные размеры могут отличаться в зависимости от компонента, но визуальная иерархия должна оставаться одинаковой по всему приложению.

---

# 7. Карточки

Карточки являются одним из основных элементов интерфейса.

Карточка должна:

- иметь четкую границу содержания;
- иметь достаточное внутреннее пространство;
- быть легко читаемой;
- не содержать лишнего декоративного оформления.

Карточки разных модулей должны восприниматься как части одной системы.

Не создавать отдельный визуальный стиль карточек для каждого модуля.

---

# 8. Скругления

В проекте используется единый принцип скругления.

Не следует использовать множество разных радиусов без необходимости.

Компоненты одного типа должны иметь одинаковое или близкое скругление.

Новый отдельный радиус должен появляться только при наличии понятной UI-причины.

---

# 9. Кнопки

Кнопки должны иметь единый визуальный язык.

Основная кнопка:

- использует акцентный цвет;
- четко обозначает главное действие;
- имеет достаточную область нажатия;
- визуально отличается от второстепенных действий.

Второстепенные действия не должны конкурировать с основной кнопкой.

Не создавать отдельный стиль кнопок для каждого модуля.

---

# 10. Формы

Любая форма должна иметь понятную последовательность:

```text
Заголовок
↓
Описание (если необходимо)
↓
Поля
↓
Кнопка действия
↓
Экран/состояние успешной отправки
```

Поля должны иметь:

- понятную подпись;
- достаточную область ввода;
- единый размер;
- понятное состояние ошибки;
- понятное состояние focus.

---

# 11. Состояния элементов

Основные интерактивные элементы должны учитывать:

- default;
- hover — где применимо;
- active;
- focus;
- disabled;
- loading;
- error;
- success — где применимо.

На мобильных устройствах не следует полагаться только на hover.

---

# 12. Навигация

Навигация должна быть максимально простой.

Пользователь всегда должен понимать:

- где он находится;
- что делать дальше;
- как вернуться назад.

Основная оболочка приложения является общей для модулей.

Модули не создают собственные независимые системы основной навигации.

---

# 13. App Shell

Общие элементы приложения должны визуально восприниматься как единая оболочка.

К ним относятся:

- AppLayout;
- BottomTabBar;
- общие глобальные элементы интерфейса.

Модульные страницы не должны создавать альтернативный shell без архитектурной необходимости.

---

# 14. BottomTabBar

BottomTabBar является частью общего App Shell.

Он должен визуально соответствовать:

- темной теме;
- общей типографике;
- акцентному цвету;
- mobile-first подходу.

Его размеры и позиционирование должны учитывать:

- разные размеры экранов;
- safe-area;
- PWA standalone mode;
- мобильные браузеры.

Но изменение BottomTabBar ради одного отдельного модуля не допускается.

---

# 15. Личные кабинеты

Все экраны кабинета клиента и кабинета тренера должны использовать единые принципы оформления.

Не допускается создание отдельных дизайн-стилей для разных разделов платформы.

Все страницы должны восприниматься как части одного приложения.

---

# 16. Mobile First

Все новые экраны сначала проектируются для телефона.

После этого адаптируются под:

- планшет;
- desktop.

Mobile UI является основным сценарием использования.

---

# 17. Адаптивность

Все новые компоненты должны корректно работать:

- на мобильных устройствах;
- на планшетах;
- на ПК;
- в мобильном браузере;
- в PWA standalone mode.

Особое внимание:

- iOS Safari;
- Android Chrome;
- safe-area;
- маленькие экраны;
- высокие экраны;
- landscape;
- большие desktop-экраны.

Не создавать отдельные независимые дизайны для каждой платформы без необходимости.

---

# 18. Отступы

Отступы должны создавать визуальный ритм.

Не следует использовать случайные значения для каждого элемента.

Компоненты одного типа должны иметь согласованные:

- padding;
- gap;
- margin;
- расстояния между заголовком и содержанием.

---

# 19. Изображения

Изображения должны иметь:

- одинаково аккуратное качество;
- корректное соотношение сторон;
- предсказуемое поведение при разных размерах контейнера.

Изображение не должно неожиданно ломать layout.

Для пользовательских фотографий и видео визуальное представление должно учитывать реальные ограничения media-модуля.

---

# 20. Видео

Видео-интерфейс должен быть простым.

Не перегружать карточки видео дополнительными элементами.

При отображении пользовательского видео необходимо обеспечить:

- понятную кнопку воспроизведения;
- корректную работу звука;
- адаптацию под ширину экрана;
- отсутствие выхода за границы контейнера.

---

# 21. Анимации

Анимации должны быть:

- плавными;
- короткими;
- функциональными;
- ненавязчивыми.

Их задача — объяснять изменение состояния, а не привлекать внимание любой ценой.

Не использовать большое количество одновременных анимаций.

Анимации не должны блокировать взаимодействие пользователя.

---

# 22. Loading UI

Используется единая система загрузки.

Новые модули не должны создавать собственный визуальный стандарт loading без необходимости.

Loading должен быть понятен пользователю.

Для долгих операций необходимо показывать состояние процесса.

---

# 23. Ошибки

Ошибки должны отображаться спокойно и понятно.

Не показывать пользователю:

- stack trace;
- SQL;
- внутренние технические детали;
- server paths;
- API credentials.

Сообщение должно объяснять:

- что произошло;
- что пользователь может сделать дальше.

---

# 24. Empty States

Пустое состояние должно объяснять причину отсутствия данных и, если возможно, следующий шаг.

Например:

```text
Пока нет тренировок

Создайте первую тренировку, чтобы она появилась здесь.
```

Не оставлять пустую область без объяснения, если пользователю не очевидно, что она означает.

---

# 25. Feedback

После важных действий пользователь должен понимать результат.

Например:

- сохранено;
- отправлено;
- удалено;
- обновлено;
- произошла ошибка.

Feedback не должен перегружать интерфейс.

---

# 26. Форматирование данных

Данные должны отображаться единообразно.

Особенно:

- даты;
- время;
- вес;
- размеры;
- калории;
- макронутриенты;
- проценты;
- тренировки.

Форматирование не должно отличаться между модулями без причины.

---

# 27. Доступность

Интерфейс должен оставаться понятным при:

- увеличении текста;
- снижении точности касания;
- использовании клавиатуры на desktop;
- focus navigation;
- слабом контрасте окружающей среды.

Интерактивные элементы должны иметь достаточную область нажатия.

Не передавать смысл только через цвет.

---

# 28. Контент

Тексты интерфейса должны быть:

- короткими;
- понятными;
- конкретными;
- без лишней технической терминологии для пользователя.

Не использовать огромные блоки текста внутри мобильного интерфейса.

---

# 29. Модальные окна

Модальное окно используется только тогда, когда действие действительно требует отдельного внимания.

Не превращать каждое действие в modal flow.

На мобильном устройстве modal должен:

- помещаться в экран;
- учитывать safe-area;
- не блокировать системную навигацию;
- иметь понятное закрытие.

---

# 30. Таблицы и большие наборы данных

Большие наборы данных должны адаптироваться под мобильный экран.

Не следует просто помещать desktop-таблицу в горизонтальный scroll, если информация может быть представлена более удобным мобильным способом.

Для кабинета тренера допустимы более плотные представления данных, но они должны сохранять общую визуальную систему.

---

# 31. Calendar UI

Календарь должен использовать общие:

- цвета;
- typography;
- states;
- spacing;
- active/selected patterns.

Дата, выбранная пользователем, должна визуально отличаться от:

- сегодняшнего дня;
- даты с данными;
- недоступной даты.

---

# 32. Статусы

Статусы должны иметь единый визуальный язык.

Например:

- active;
- pending;
- archived;
- completed;
- error.

Не использовать новый цвет для каждого статуса без необходимости.

Цвет не должен быть единственным способом определить статус.

---

# 33. Coach / Client UI

Кабинет клиента и кабинет тренера используют одну дизайн-систему.

Разница между ними определяется:

- содержанием;
- доступными действиями;
- плотностью информации;
- permissions;

а не отдельной визуальной темой.

---

# 34. Chat UI

Chat должен визуально соответствовать приложению.

Сообщения должны четко разделяться по автору.

Media, replies, status sent/read и другие элементы должны использовать общие:

- цвета;
- скругления;
- typography;
- spacing.

Chat может иметь специализированное поведение scroll, но не должен создавать отдельный дизайн приложения.

---

# 35. Training UI

Training использует общие:

- карточки;
- кнопки;
- поля;
- typography;
- accent;
- loading;
- error states.

Сложные данные тренировки могут иметь более плотное представление, но визуально должны оставаться частью общей системы.

---

# 36. Food UI

Food должен сохранять общий визуальный язык.

Калории и макронутриенты могут быть визуально выделены, но без появления дополнительных акцентных цветов.

AI screenshot import должен восприниматься как обычная функция приложения, а не как отдельный интерфейс.

---

# 37. Reports / Photos / Measurements

Фото, видео, замеры и отчеты должны использовать единый подход к:

- preview;
- карточкам;
- календарю;
- сравнениям;
- комментариям;
- состояниям загрузки.

Интерфейс не должен визуально разделять пользовательские данные по происхождению.

---

# 38. Главный экран

Home является навигационным центром приложения.

Он должен быстро показывать:

- текущий статус;
- основные действия;
- основные модули;
- важные события;
- доступ к Chat при наличии coach relationship.

Home не должен превращаться в страницу со всей информацией приложения.

---

# 39. Performance как часть UI

Дизайн не должен требовать чрезмерно тяжелых ресурсов.

Особое внимание:

- изображения;
- видео;
- анимации;
- большие списки;
- сложные сравнения;
- мобильный интернет.

Большие media-ресурсы должны загружаться по необходимости.

---

# 40. Запрещается

❌ Пестрые цвета.

❌ Мелкий текст.

❌ Слишком плотное расположение элементов.

❌ Огромные блоки текста.

❌ Разные стили кнопок.

❌ Разные радиусы скругления без причины.

❌ Разные размеры полей ввода без причины.

❌ Разные стили карточек.

❌ Использовать более одного основного акцентного цвета.

❌ Создавать отдельную визуальную тему для каждого модуля.

❌ Исправлять локальную проблему глобальным CSS без необходимости.

---

# 41. Основной принцип дизайна

Каждый новый экран должен выглядеть так, будто он существовал в проекте с самого начала.

Пользователь не должен замечать разницу между старыми и новыми разделами.

Визуальная целостность проекта является одним из главных требований.

---

# 42. Философия интерфейса

Интерфейс Stubborn Ram должен вызывать ощущение:

- спокойствия;
- надежности;
- профессионализма;
- контроля;
- простоты.

Дизайн не должен отвлекать пользователя.

Главная задача интерфейса — помочь человеку быстро понять информацию и выполнить нужное действие.

---

# 43. Будущее развитие

Дизайн-система может расширяться новыми:

- компонентами;
- паттернами;
- состояниями;
- токенами;
- шаблонами экранов.

Но новые элементы должны сначала стать частью общей дизайн-системы, а не появляться как локальные исключения в отдельных модулях.

---

# 44. Definition of Done для UI

Новый экран считается визуально готовым, когда:

- соответствует общей цветовой палитре;
- использует Comfortaa;
- соответствует mobile-first;
- адаптирован под desktop;
- использует общие принципы карточек;
- использует общие кнопки и поля;
- имеет loading/error/empty states;
- не создает конфликтов с другими модулями;
- учитывает safe-area и PWA при необходимости;
- не добавляет необоснованных новых цветов, радиусов или стилей;
- выглядит частью единого Stubborn Ram.
