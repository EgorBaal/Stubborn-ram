# DEVELOPMENT_RULES.md

# Правила разработки модулей

Версия: 1.1

Последнее обновление: август 2026

---

# Общий принцип

Каждый новый модуль приложения должен разрабатываться максимально независимо от остальных модулей.

Каждый модуль обязан иметь собственную структуру и не должен влиять на другие страницы приложения.

---

# Обязательные правила для каждого нового модуля

Каждый новый модуль обязан иметь:

- собственную Page.jsx;
- собственную Page.css;
- собственные локальные компоненты;
- собственные hooks (при необходимости);
- собственные services (при необходимости).

Новый модуль не должен зависеть от реализации другого модуля.

---

# Запрещается

- использовать CSS другой страницы;
- импортировать Page другого модуля;
- изменять AppLayout ради одного конкретного модуля;
- изменять BottomTabBar ради одного конкретного модуля;
- добавлять page-specific стили в index.css;
- использовать общие page-классы вроде `.app-page`;
- переносить стили одного модуля в другой;
- создавать скрытые зависимости между страницами;
- добавлять новую общую инфраструктуру, если проблема решается локально.

---

# Минимум изменений

Любая задача должна затрагивать минимально возможное количество файлов.

Если задача относится только к одному модулю, изменения должны происходить только внутри этого модуля.

Изменение общей инфраструктуры допускается только тогда, когда проблему невозможно решить локально.

Перед изменением любого файла разработчик обязан определить, относится ли он к локальному модулю или к общей инфраструктуре.
Если задача может быть решена внутри одного модуля, изменение общей инфраструктуры запрещено.

---

# Что может быть общим

Общими могут быть только:

- AppLayout;
- BottomTabBar;
- Router;
- Auth;
- Theme (цвета, токены, типографика);
- универсальные UI-компоненты;
- общие утилиты;
- общие сервисы только если они действительно используются несколькими модулями.

---

# Принцип разработки

Изменения внутри одного модуля не должны менять внешний вид или поведение других страниц приложения.

Если изменение одного модуля требует изменения другого — это считается архитектурной ошибкой и должно быть отдельно обосновано.

---

# Приоритет реализации

При разработке сначала использовать:

1. локальные Page.jsx;
2. локальные Page.css;
3. локальные компоненты;
4. локальные hooks;
5. локальные services.

К общим слоям обращаться только тогда, когда функциональность действительно используется несколькими страницами.

---

# Приоритет существующей инфраструктуры

Любая новая функциональность должна в первую очередь использовать уже существующую инфраструктуру проекта.

Запрещается создавать новый Provider, Context или новую глобальную систему, если текущая инфраструктура уже решает задачу.

Для длительных операций ожидания должен использоваться существующий LoadingProvider и LoadingOverlay.

Создание отдельных параллельных систем загрузки для разных модулей не допускается без отдельного архитектурного решения.

---

# Статус документа

Этот документ является обязательным правилом дальнейшей разработки проекта.

Он определяет, как должны создаваться новые страницы, как должны быть организованы локальные компоненты и как следует ограничивать влияние одной задачи на остальные модули.
