# DEVELOPMENT_RULES.md

# Правила разработки модулей

Версия: 1.2  
Статус: актуализировано под целевую архитектуру после миграции backend-инфраструктуры  
Дата обновления: сентябрь 2026

---

# 1. Общий принцип

Каждый новый модуль приложения должен разрабатываться максимально независимо от остальных модулей.

Каждый модуль обязан иметь собственную структуру и не должен влиять на другие страницы приложения.

Основная разработка ведется внутри `src/modules`.

Legacy-структура `src/pages/app` является временным слоем и не должна использоваться как основной путь для новых модулей.

---

# 2. Обязательная структура модуля

Каждый новый модуль обязан иметь:

- собственную `Page.jsx`;
- собственную `Page.css`;
- собственные локальные компоненты;
- собственные hooks — при необходимости;
- собственные services — при необходимости.

Пример:

```text
src/modules/training/

    TrainingPage.jsx
    TrainingPage.css

    components/
    hooks/
    services/
```

Точная внутренняя структура может отличаться, если этого требует модуль.

---

# 3. Независимость модулей

Новый модуль не должен зависеть от реализации другого модуля.

Допустимо использовать:

- общий shell;
- общие UI-компоненты;
- общие утилиты;
- общие базовые сервисы;
- общие инфраструктурные механизмы.

Недопустимо строить модуль так, чтобы он зависел от внутреннего компонента другой страницы.

Модуль должен оставаться заменяемым без переписывания остальных модулей.

---

# 4. AppLayout и Application Shell

`AppLayout` является единственным владельцем общей оболочки приложения.

В shell относятся:

- `BottomTabBar`;
- будущий `TopBar`;
- глобальные уведомления;
- глобальные overlay;
- глобальные модальные окна;
- другие элементы, которые действительно должны существовать на уровне всего приложения.

Модули не импортируют и не рендерят элементы shell самостоятельно.

`BottomTabBar` существует только в одном экземпляре и принадлежит `AppLayout`.

Изменение одного модуля не должно требовать изменения `AppLayout`, если проблема может быть решена локально.

---

# 5. Router

Маршрутизация остается централизованной.

Основной файл:

```text
src/app/router/appRoutes.jsx
```

Модуль не должен самостоятельно создавать независимую систему маршрутизации.

Router отвечает за:

- связь URL с Page;
- разделение публичной и внутренней части приложения;
- подключение AppLayout;
- route-level guards, если они необходимы.

Модуль отвечает за содержимое своей страницы, а не за архитектуру всего Router.

---

# 6. Вертикальная прокрутка

`AppLayout` не владеет вертикальной прокруткой содержимого модульных страниц.

Каждая страница самостоятельно определяет свое поведение:

- фиксированная;
- прокручиваемая;
- прокручиваемая с учетом BottomTabBar;
- ограниченная рабочей областью;
- специализированная схема scroll.

Scroll одного маршрута не должен влиять на другой маршрут.

Chat может использовать специализированный scroll-контекст.

Home может иметь собственное поведение, отличное от обычных страниц.

---

# 7. Запрещается

Запрещается:

- использовать CSS другой страницы;
- импортировать `Page` другого модуля;
- изменять `AppLayout` ради одного конкретного модуля;
- изменять `BottomTabBar` ради одного конкретного модуля;
- добавлять page-specific стили в `index.css`;
- использовать общие page-классы вроде `.app-page`;
- переносить стили одного модуля в другой;
- создавать скрытые зависимости между страницами;
- добавлять новую общую инфраструктуру, если проблема решается локально;
- размещать бизнес-логику конкретного модуля в глобальных файлах без необходимости.

---

# 8. Минимум изменений

Любая задача должна затрагивать минимально возможное количество файлов.

Если задача относится только к одному модулю, изменения должны происходить только внутри этого модуля.

Изменение общей инфраструктуры допускается только тогда, когда проблему невозможно решить локально.

Перед изменением любого файла разработчик обязан определить:

1. относится ли файл к локальному модулю;
2. относится ли файл к общей инфраструктуре;
3. действительно ли изменение общей инфраструктуры необходимо.

Если задача может быть решена внутри одного модуля, изменение общей инфраструктуры запрещено.

---

# 9. Что может быть общим

Общими могут быть только:

- `AppLayout`;
- `BottomTabBar`;
- `Router`;
- Auth layer;
- Theme;
- design tokens;
- универсальные UI-компоненты;
- общие утилиты;
- общие сервисы, если они действительно используются несколькими модулями;
- общие инфраструктурные механизмы.

Общий код не должен становиться местом хранения page-specific логики.

---

# 10. Общие компоненты

Общий UI-компонент создается только тогда, когда:

- он реально используется несколькими модулями;
- его поведение одинаково или достаточно стабильно;
- выделение уменьшает дублирование;
- перенос не создает скрытой зависимости.

Не следует заранее создавать универсальные компоненты «на будущее».

Сначала появляется реальная повторяемость, затем abstraction.

---

# 11. CSS-модуля

Каждый модуль имеет собственный CSS.

Например:

```text
TrainingPage.jsx
TrainingPage.css
```

Стили должны быть локализованы внутри модуля.

Нельзя исправлять проблему одной страницы глобальным CSS-правилом, если это может изменить другие страницы.

Особенно осторожно использовать:

- `body`;
- `html`;
- глобальные class selectors;
- универсальные selectors;
- `!important`.

---

# 12. Service layer

Модуль не обращается напрямую к PostgreSQL, Object Storage или внешнему API.

Целевая цепочка:

```text
Module Page
    ↓
Local Service
    ↓
Backend API
    ↓
Database / Storage / External Service
```

Если service нужен только одному модулю, его можно оставить внутри модуля.

Если service используется несколькими модулями и является действительно общим, он может находиться в shared layer.

---

# 13. Backend является источником истины

Модульный frontend не является источником истины для:

- permissions;
- ownership;
- подписки;
- coach-client relationship;
- бизнес-ограничений;
- безопасности;
- доступа к пользовательским файлам.

Frontend может показывать или скрывать элементы интерфейса.

Но backend обязан повторно проверять каждое защищенное действие.

---

# 14. Работа с персональными данными

Модуль не должен отправлять внешним сервисам персональные данные напрямую.

Если модулю требуется:

- Email;
- AI/OCR;
- платежи;
- Object Storage;
- другие внешние API,

вызов выполняется через Backend API и соответствующий service/adapter.

Особенно важно для:

- Food AI screenshot import;
- пользовательских фото;
- пользовательских видео;
- Chat media;
- отчетов.

---

# 15. Работа с файлами

Модуль не хранит пользовательские файлы в frontend bundle.

Фото, видео и документы передаются через `mediaService`/соответствующий backend endpoint.

Целевая цепочка:

```text
Module
    ↓
mediaService
    ↓
Backend
    ↓
Permission Check
    ↓
Object Storage
```

Постоянные публичные ссылки на приватные пользовательские файлы не используются.

---

# 16. Видео и тяжелые файлы

Модуль отвечает за UI загрузки и отображения.

Production-обработка видео выполняется backend/worker инфраструктурой.

Не следует помещать FFmpeg и серверную обработку непосредственно в React-модуль.

Для Training применяются утвержденные ограничения:

- максимум 8 видео на тренировку;
- максимум 45 секунд на видео;
- сжатие;
- удаление оригинала после успешной обработки.

---

# 17. Chat

Chat является самостоятельным модулем.

Он не должен использовать внутренние компоненты Training, Report или Food как часть своей архитектуры.

Если сообщение содержит ссылку на объект другого модуля, Chat хранит reference на этот объект, а не копирует его бизнес-данные.

Пример:

```text
Chat
  ↓
objectReference
  ↓
Training / Report / Food / ...
```

Одна coach-client связь имеет один основной чат согласно утвержденной архитектуре Chat.

---

# 18. Работа с canonical data

Каждый бизнес-модуль должен иметь один источник истины для своих данных.

Например:

- Training хранит тренировочные данные;
- Food хранит данные питания;
- Weight хранит измерения веса;
- Photos/Measurements хранит фотографии и замеры;
- Report хранит отчеты;
- Activity хранит активность.

Другие модули используют ссылки/запросы к canonical source, а не создают независимые копии.

Это предотвращает расхождение данных.

---

# 19. Hooks

Hooks используются для:

- поведения React;
- локального состояния;
- загрузки/синхронизации данных через service;
- повторяемой логики модуля.

Hook не должен становиться скрытой заменой архитектурному service layer.

Если hook работает с backend, он использует service.

---

# 20. Страница

`Page.jsx` отвечает за координацию своей страницы.

Page не должна одновременно содержать:

- весь UI;
- все API-запросы;
- database logic;
- permission logic;
- бизнес-правила;
- обработку всех внешних сервисов.

Большая страница разбивается на локальные компоненты.

---

# 21. Компоненты модуля

Локальный компонент отвечает за конкретный UI-блок или небольшую функциональную задачу.

Принцип:

> один компонент — одна понятная ответственность.

Например:

```text
TrainingPage
├── TrainingHeader
├── WorkoutList
├── WorkoutCard
├── ExerciseList
└── TrainingActions
```

Конкретное разбиение определяется реальным UI.

---

# 22. Состояние

Следует разделять:

### UI state

Например:

- открыта ли модалка;
- выбранный tab;
- локальный input;
- состояние раскрытия блока.

### Server state

Например:

- тренировки;
- отчеты;
- сообщения;
- вес;
- питание.

### Temporary form state

Например:

- незавершенная анкета;
- редактирование тренировки;
- черновик формы.

Server state не следует бессистемно дублировать в нескольких местах.

---

# 23. Loading

Используется существующая глобальная система loading UI.

Модуль не должен создавать отдельный визуальный стандарт загрузки без необходимости.

Каждая async-операция должна корректно учитывать:

- loading;
- success;
- error;
- retry;
- повторный запрос;
- отмену, если она поддерживается.

---

# 24. Ошибки

Ошибки должны быть понятны пользователю.

В UI не показывать:

- SQL;
- stack trace;
- внутренние endpoint;
- server paths;
- API keys;
- provider credentials.

Технические детали остаются в server logs.

---

# 25. Permissions

Модуль определяет свои бизнес-действия и соответствующие permissions.

Например:

```text
training.view
training.create
training.update
training.delete
```

Конкретный permission проверяется общей permission system.

Нельзя создавать в каждом модуле независимую систему ролей.

---

# 26. Coach / Client

Доступ тренера к данным клиента определяется через существующую архитектуру coach-client relationship и permissions.

Модуль не должен самостоятельно считать:

```text
if coach
```

достаточным условием доступа.

Также учитываются:

- активность relationship;
- ownership;
- author;
- состояние объекта;
- конкретное действие.

---

# 27. Подписка и доступ

Модуль не должен самостоятельно реализовывать всю систему подписок.

Access status определяется общей платформенной логикой.

Модуль использует предоставленный ему результат проверки доступа.

Окончательная проверка критических действий выполняется backend.

---

# 28. Notifications

Модуль не должен создавать собственную независимую систему уведомлений.

Если действие требует уведомления:

```text
Module
↓
Backend
↓
Notification System
```

Формат и каналы уведомлений определяются общей архитектурой Notifications.

---

# 29. Analytics

Модуль может отдавать необходимые события в общую analytics system.

Не следует создавать собственный счетчик или отдельную аналитику внутри каждой страницы.

Analytics не должна становиться источником истины для бизнес-данных.

---

# 30. Scroll restoration

Каждый маршрут должен иметь независимое состояние прокрутки.

Навигация между страницами не должна переносить scroll одного маршрута на другой.

Реализация scroll restoration относится к общей инфраструктуре только в том случае, если проблему невозможно решить на уровне конкретного маршрута.

---

# 31. BottomTabBar

`BottomTabBar` принадлежит `AppLayout`.

Модули:

- не импортируют его;
- не рендерят его;
- не изменяют его CSS;
- не меняют его размеры/позиционирование ради собственного UI.

Если возникает проблема адаптации BottomTabBar к разным устройствам, она рассматривается как отдельная задача общей инфраструктуры.

---

# 32. Работа с адаптивностью

Каждый модуль отвечает за свою адаптивность.

Не следует исправлять mobile layout одного модуля глобальным правилом, которое потенциально влияет на остальные.

Особое внимание:

- iPhone Safari;
- Android;
- safe-area;
- маленькие экраны;
- большие мобильные экраны;
- desktop;
- PWA standalone mode.

---

# 33. Performance

Не оптимизировать заранее без измеримой проблемы.

При необходимости проверяются:

- размер bundle;
- количество запросов;
- изображения;
- видео;
- lazy loading;
- повторные рендеры;
- network waterfall.

Тяжелые операции не должны выполняться в UI thread без необходимости.

---

# 34. Минимизация зависимостей

Новая библиотека добавляется только при реальной необходимости.

Перед добавлением проверить:

- можно ли решить задачу существующими средствами;
- размер;
- поддерживаемость;
- безопасность;
- совместимость;
- необходимость для production.

---

# 35. Архитектурные изменения

Если при разработке модуля выясняется, что требуется:

- новая таблица;
- изменение ownership;
- новый permission;
- новый внешний сервис;
- изменение API;
- изменение authentication;
- изменение storage;
- изменение общего shell;

разработка останавливается на архитектурном уровне.

Сначала обновляется соответствующая документация и принимается решение.

После этого выполняется кодирование.

---

# 36. Порядок разработки

Используется процесс:

```text
Idea
↓
Discussion
↓
Documentation
↓
Approval
↓
Implementation
↓
Verification
↓
Documentation Update
↓
Git Commit
```

Если требования противоречат существующей архитектуре, нельзя молча выбирать один из вариантов.

Необходимо остановиться и согласовать решение.

---

# 37. Проверка после реализации

После значимых изменений необходимо выполнить по возможности:

```text
npm run build
```

Также проверяются:

- основной сценарий;
- mobile layout;
- desktop layout;
- route;
- loading;
- error state;
- permissions;
- сохранение данных;
- отсутствие console errors.

---

# 38. Git

Каждый логический этап оформляется отдельным commit.

Commit должен содержать понятную единицу изменения.

Перед commit:

1. проверить код;
2. проверить build;
3. проверить документацию;
4. убедиться, что не изменены посторонние файлы;
5. убедиться, что секреты не попали в commit.

---

# 39. Что считается нарушением изоляции

Нарушением считается ситуация, когда изменение одного модуля неожиданно меняет:

- CSS другой страницы;
- scroll другой страницы;
- layout другого модуля;
- BottomTabBar;
- AppLayout;
- router behavior;
- permissions другого модуля.

Если изменение действительно является общей инфраструктурной задачей, оно должно быть оформлено как отдельное архитектурное изменение.

---

# 40. Definition of Done для нового модуля

Новый модуль считается готовым, когда:

- он находится в целевой module structure;
- имеет собственную Page;
- имеет собственный CSS;
- локальные компоненты изолированы;
- нет зависимости от внутреннего кода другого модуля;
- backend доступ выполняется через service layer;
- permissions проверяются сервером;
- пользовательские файлы приватны;
- нет секретов во frontend;
- canonical data не дублируется без причины;
- loading/error states реализованы;
- mobile layout проверен;
- build проходит;
- документация соответствует фактической реализации.

---

# 41. Главное правило

Если проблему можно решить внутри одного модуля — решаем внутри одного модуля.

Если требуется изменение общей инфраструктуры — сначала подтверждаем, что это действительно общая проблема.

Общий код должен оставаться маленьким и стабильным.

Цель архитектуры:

> каждый модуль можно развивать, тестировать, исправлять или заменить независимо, не ломая остальную платформу.
