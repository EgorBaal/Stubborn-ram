# PLATFORM_ARCHITECTURE.md

# Архитектура платформы Stubborn Ram

Версия документа:

2.0

Статус:

Архитектурно утверждено для целевой инфраструктуры; реализация после миграции

---

# Назначение документа

PLATFORM_ARCHITECTURE.md описывает общую модель работы платформы Stubborn Ram и связывает между собой основные архитектурные слои.

Документ определяет:

- модель User / Client / Coach / Admin;
- источники полного доступа;
- ограниченный доступ;
- отношения пользователя и тренера;
- владение данными;
- разделение authentication, permissions и access;
- основные модули платформы;
- целевую серверную архитектуру;
- хранение структурированных данных и файлов;
- требования к расширяемости;
- базовые правила взаимодействия модулей.

Документ не заменяет специализированные архитектурные документы модулей.

---

# 1. Главный принцип платформы

Stubborn Ram — это единая пользовательская платформа, в которой один аккаунт может использовать разные режимы и функции без создания отдельных аккаунтов.

Пользователь может:

- использовать платформу самостоятельно;
- быть клиентом тренера;
- в будущем быть тренером;
- использовать разные функции независимо друг от друга;
- сохранять всю историю при изменении статуса доступа.

Роль в конкретном сценарии не должна превращаться в жесткий тип аккаунта.

---

# 2. User как основная сущность

Основная сущность платформы — User.

User имеет:

- единый `user_id`;
- учетные данные;
- профиль;
- пользовательские данные;
- историю;
- источники доступа;
- связи с другими пользователями;
- настройки.

Один User может одновременно:

- иметь личную подписку;
- быть клиентом тренера;
- в будущем быть тренером;
- иметь собственную историю тренировок и питания.

Не допускается архитектура, в которой для роли Coach требуется отдельный аккаунт.

---

# 3. Client и Coach

Client и Coach являются контекстами использования одного User.

```text
User
 ├── personal data
 ├── client context
 └── coach context
```

Пользователь становится клиентом при наличии активной связи с тренером.

Пользователь может стать тренером без создания нового аккаунта.

Конкретные права определяются не названием роли, а action-based Permission Service.

---

# 4. Admin

Admin — системный уровень доступа.

Admin не является отдельным типом пользователя.

У администратора остается обычный User-аккаунт, к которому добавляется административный уровень.

Административные действия всегда выполняются через Backend и серверные permission checks.

Администратор не получает доступ к паролям пользователей.

---

# 5. Владение пользовательскими данными

Все пользовательские данные принадлежат User.

Тренер не становится владельцем данных клиента.

Связь тренера с клиентом предоставляет тренеру разрешенный доступ к данным в рамках активного relationship и конкретных permissions.

Например:

```text
Client owns workout
Coach may read workout
Coach may leave feedback
```

Это принципиально отличается от модели:

```text
Coach owns client data
```

Последняя модель не используется.

---

# 6. Auth, Access и Permissions

Это три разных слоя.

## Authentication

Отвечает на вопрос:

**Кто пользователь?**

Authentication управляет:

- регистрацией;
- Email;
- паролем;
- сессией;
- восстановлением доступа.

## Access

Отвечает на вопрос:

**Имеет ли пользователь полный доступ к платформе?**

Access учитывает:

- Trial;
- личную подписку;
- подписку тренера;
- active relationship;
- другие предусмотренные источники доступа.

## Permissions

Отвечает на вопрос:

**Может ли этот пользователь выполнить конкретное действие с конкретным объектом?**

Например:

```text
training.create
training.read
training.update
report.create
report.read
chat.send
media.upload
```

Authentication ≠ Access ≠ Permissions.

---

# 7. Источники полного доступа

Полный доступ предоставляется, если существует хотя бы один активный источник:

1. Trial;
2. личная подписка;
3. активное сопровождение тренером с действующей подпиской тренера.

```text
Trial
  OR
Personal Subscription
  OR
Coach Subscription + Active Relationship
        ↓
    Full Access
```

Приоритет между источниками не нужен.

---

# 8. Trial

Trial:

- предоставляется один раз;
- длится 10 календарных дней;
- начинается после подтверждения Email и создания профиля;
- не перезапускается при смене устройства;
- не перезапускается при повторном входе.

Trial является серверным источником полного доступа.

---

# 9. Личная подписка

Личная подписка предоставляет самостоятельный полный доступ.

На текущем этапе:

- срок — один календарный месяц;
- автоматического продления нет;
- после окончания подписки Access пересчитывается;
- история пользователя сохраняется.

Платежная модель описана в PAYMENT_ARCHITECTURE.md.

---

# 10. Доступ через тренера

Клиент получает полный доступ при наличии:

- активной связи с тренером;
- действующей подписки тренера;
- необходимых разрешений.

Если подписка тренера закончилась, предусмотрен grace period 72 часа.

После grace period доступ пересчитывается.

История клиента не удаляется.

---

# 11. Ограниченный доступ

Если у пользователя отсутствуют все источники полного доступа, аккаунт не блокируется.

Пользователь сохраняет:

- вход;
- просмотр истории;
- просмотр ранее созданных тренировок;
- просмотр питания;
- просмотр веса;
- просмотр отчетов;
- просмотр фотографий;
- просмотр аналитики;
- просмотр переписки;
- управление аккаунтом;
- возможность восстановить полный доступ.

Создание новых данных, требующих полного доступа, блокируется.

Это позволяет пользователю не терять накопленную историю.

---

# 12. Данные не удаляются из-за окончания доступа

Окончание Trial или подписки не является основанием для удаления пользовательских данных.

Сохраняются:

- тренировки;
- упражнения;
- подходы;
- питание;
- вес;
- измерения;
- фотографии;
- отчеты;
- сообщения;
- медиа;
- аналитическая история;
- связи и их история в пределах политики хранения.

Удаление определяется отдельными правилами lifecycle и безопасности.

---

# 13. Coach-Client Relationship

Связь Coach → Client является отдельной сущностью.

Она имеет состояние, например:

```text
Active
Archived
```

При архивировании:

- новые collaborative actions блокируются;
- исторические данные сохраняются;
- тренер перестает иметь доступ, который зависел от active relationship;
- данные клиента остаются у клиента.

Подробная архитектура описана в COACH_CLIENT_RELATIONSHIP.md.

---

# 14. Авторы и владельцы

В системе необходимо различать:

- owner;
- author;
- viewer;
- collaborator.

Например:

```text
Workout
owner = Client
author = Client
coach = collaborator
```

Другой объект может иметь:

```text
Report
owner = Client
author = Client
coach = reviewer
```

Эти поля нельзя заменять одним универсальным `user_id`.

Это позволяет системе развиваться в сторону нескольких специалистов.

# 15. Основные модули

Платформа состоит из независимых бизнес-модулей.

Основные:

1. Home;
2. Authentication / Account;
3. Training;
4. Food;
5. Activity;
6. Weight;
7. Photos & Measurements;
8. Weekly Reports;
9. Chat;
10. Analytics;
11. Coach / Client;
12. Media;
13. Notifications;
14. Payments;
15. Admin.

Каждый модуль имеет собственную бизнес-логику, но использует общие инфраструктурные сервисы.

---

# 16. Home

Home является навигационным центром приложения.

Он показывает состояние и входы в основные модули:

- Training;
- Food;
- Activity;
- Reports;
- Photos;
- Measurements;
- Weight.

Home не хранит собственную копию данных этих модулей.

Он получает canonical data через Backend API.

---

# 17. Training

Training является каноническим источником данных о тренировках.

Основная модель:

```text
Workout
  ↓
WorkoutExercise
  ↓
WorkoutSet
```

Упражнение хранится как ссылка на Exercise entity, а не как произвольная строка.

Training должен поддерживать:

- создание тренировок;
- историю;
- упражнения;
- подходы;
- видео;
- feedback;
- связь с отчетами;
- связь с Chat;
- аналитику.

Подробная модель определяется TRAINING.md.

---

# 18. Food

Food разделяет:

- план;
- фактическое питание.

Хранятся:

- calories;
- protein;
- fat;
- carbohydrates;
- water;
- salt.

Источники:

- ручной ввод;
- FatSecret;
- AI/OCR импорт.

AI/OCR используется только через Backend и provider adapter.

Скриншоты для AI-импорта не должны становиться постоянным источником пользовательских данных.

---

# 19. Activity

Activity хранит активность пользователя по календарю.

Поддерживаются:

- шаги;
- кардио;
- дополнительная активность;
- дневные цели;
- планы;
- данные Apple Health / Health Connect;
- ручной ввод.

Activity остается отдельным каноническим источником данных.

---

# 20. Weight

Weight является каноническим источником данных о весе.

Поддерживаются:

- несколько измерений в день;
- календарная история;
- первичное утреннее измерение натощак как основное при наличии;
- аналитика;
- история без перезаписи прошлых значений.

Вес не дублируется в других модулях как независимый источник истины.

---

# 21. Photos & Measurements

Основная сущность — контрольная точка.

Контрольная точка может включать:

- вес;
- фотографии;
- измерения;
- комментарии;
- дату.

Предусмотрены:

- четыре базовые позиции фотографий;
- пользовательские позиции;
- видео;
- измерения;
- сравнение;
- календарная история;
- face blur без AI.

Данные сохраняются независимо от статуса подписки.

---

# 22. Weekly Reports

Weekly Report объединяет данные пользователя за определенный отчетный период.

Отчет может содержать:

- фотографии;
- видео;
- данные питания;
- тренировочную информацию;
- вес;
- измерения;
- комментарий пользователя;
- обратную связь тренера.

Report не должен создавать независимые копии канонических данных без необходимости.

Он использует ссылки или snapshot-механику там, где это необходимо для сохранения исторического состояния.

---

# 23. Chat

На текущем этапе предусматривается один чат на пару Coach ↔ Client.

Chat поддерживает:

- текст;
- голос;
- фотографии;
- видео;
- документы;
- ответы;
- поиск;
- черновики;
- sent/read state;
- ссылки на объекты платформы.

Не создаются отдельные чаты для:

- каждой тренировки;
- каждого отчета;
- каждого упражнения.

Chat использует Backend WebSocket infrastructure.

Данные сообщений хранятся в PostgreSQL, файлы — в Object Storage.

---

# 24. Media

Media является инфраструктурным слоем для пользовательских файлов.

Типы:

- фотографии;
- видео;
- голосовые сообщения;
- документы;
- тренировочные видео;
- материалы тренера.

Файлы хранятся в приватном Object Storage.

Доступ к файлам выдается через Backend.

Прямое публичное размещение пользовательских файлов не допускается.

---

# 25. Обработка видео

Видео тренировок не должно обрабатываться frontend как финальная система хранения.

Backend принимает файл и передает его в Media/Video processing pipeline.

Предусмотрены:

- ограничение количества видео;
- ограничение длительности;
- серверная компрессия;
- удаление оригинала после успешной обработки, если это разрешено политикой хранения;
- хранение оптимизированной версии.

Для Training текущие ограничения:

- максимум 8 видео на тренировку;
- максимум 45 секунд на видео.

FFmpeg используется серверно.

На раннем этапе worker может работать на той же серверной машине.

При росте нагрузки обработка выносится на отдельный worker.

---

# 26. Notifications

Notifications являются отдельным модулем.

Они могут использовать:

- in-app notifications;
- Email;
- будущие push notifications.

Модули создают события, а Notification Service определяет способ доставки.

Модуль не должен напрямую вызывать Email-провайдера.

---

# 27. Analytics

Аналитика приложения строится на канонических данных PostgreSQL.

Frontend не является источником аналитической истины.

Публичный лендинг может использовать Yandex Metrica.

Персональные и медицинские/фитнес-данные пользователя не должны отправляться в публичную аналитическую систему без отдельного архитектурного и юридического решения.

---

# 28. Backend API

Backend API является центральной точкой доступа приложения.

Схема:

```text
React / PWA
      ↓
   Backend API
      ↓
 ┌────┼───────────────────────┐
 ▼    ▼          ▼            ▼
Auth Access   Permissions   Services
                      │
                      ▼
                  PostgreSQL
                      │
              ┌───────┴───────┐
              ▼               ▼
         Object Storage    Providers
```

Frontend не имеет прямого доступа к PostgreSQL.

---

# 29. PostgreSQL

PostgreSQL является основной базой структурированных данных.

В ней хранятся:

- пользователи;
- профили;
- отношения;
- подписки;
- платежные записи;
- тренировки;
- питание;
- активность;
- вес;
- измерения;
- отчеты;
- сообщения;
- ссылки на медиа;
- системные события;
- необходимые audit records.

Точная физическая схема определяется DATABASE_SCHEMA.md.

---

# 30. Object Storage

Object Storage используется для файлов.

Целевой вариант — Selectel Object Storage/S3-compatible storage.

Файлы не должны храниться непосредственно в PostgreSQL как основной механизм.

PostgreSQL хранит metadata и references.

Пример:

```text
media
 ├── id
 ├── owner_id
 ├── object_key
 ├── mime_type
 ├── size
 ├── created_at
 └── access metadata
```

---

# 31. Email

Email используется для:

- подтверждения Email;
- восстановления пароля;
- изменения Email;
- платежных уведомлений;
- системных уведомлений.

Целевой серверный provider adapter — Unisender Go при завершении юридической и договорной проверки.

Frontend не взаимодействует с Email API напрямую.

---

# 32. AI / OCR

AI используется как дополнительный сервис.

Основной текущий сценарий:

- импорт питания по скриншотам.

Архитектура:

```text
Frontend
   ↓
Backend
   ↓
AI Provider Adapter
   ↓
AI/OCR Provider
```

Для российского контура рассматривается Yandex AI Studio/Vision OCR.

AI-провайдер не должен быть жестко встроен в Food module.

В будущем провайдер может быть заменен без изменения пользовательского интерфейса.

---

# 33. Payments

Payments является отдельным модулем.

Backend взаимодействует с платежным провайдером через adapter.

На текущем этапе рассматриваются:

- YooKassa;
- T-Bank acquiring.

Payment Service не передает платежные данные напрямую в другие модули.

Он изменяет состояние платежей/подписок, после чего Access Service пересчитывает доступ.

---

# 34. Infrastructure

Целевая инфраструктура:

```text
Domain
  ↓
DNS
  ↓
CDN
  ↓
Frontend / PWA
  ↓
Backend API
  ├── PostgreSQL
  ├── Object Storage
  ├── Email Provider
  ├── AI Provider
  └── Payment Provider
```

Базовый инфраструктурный провайдер — Selectel.

На первом этапе не используются:

- Kubernetes;
- Redis без необходимости;
- сложная микросервисная архитектура.

Backend строится как модульный монолит с четким разделением сервисов.

---

# 35. Почему модульный монолит

Stubborn Ram не требует микросервисной архитектуры на старте.

Модульный монолит позволяет:

- быстро развивать продукт;
- проще выполнять миграции;
- проще резервировать данные;
- проще тестировать;
- снизить стоимость инфраструктуры;
- избежать лишней сетевой сложности.

При реальной нагрузке отдельные тяжелые компоненты могут быть вынесены:

- Video Worker;
- Notification Worker;
- AI Worker;
- отдельные фоновые очереди.

Выделение происходит только при наличии реальной необходимости.

---

# 36. Производительность

Ключевые требования:

- быстрый первый экран;
- минимальный JavaScript;
- lazy loading тяжелых модулей;
- оптимизированные изображения;
- CDN;
- серверная обработка видео;
- пагинация больших историй;
- индексы PostgreSQL;
- отсутствие лишних запросов;
- кэширование там, где оно действительно необходимо.

Производительность не должна достигаться за счет нарушения каноничности данных.

---

# 37. PWA

Приложение остается PWA.

Поддерживаются:

- установка на домашний экран;
- мобильная навигация;
- safe areas;
- корректная работа viewport;
- offline-friendly оболочка там, где это безопасно;
- сохранение сессии;
- быстрый запуск.

Offline-режим не должен позволять обходить серверные permissions или создавать неконтролируемые конфликты данных.

---

# 38. App Shell

App Shell является общей частью приложения.

Он отвечает за:

- основной layout;
- навигацию;
- BottomTabBar;
- общие состояния загрузки;
- системные уведомления;
- PWA shell.

Бизнес-модули не создают собственный AppLayout или BottomTabBar.

---

# 39. Router

Маршрутизация централизована.

Источник маршрутов:

```text
src/app/router/appRoutes.jsx
```

Модули не должны самостоятельно создавать конкурирующую глобальную маршрутизацию.

Защита маршрутов выполняется на двух уровнях:

1. frontend route guards для UX;
2. Backend permissions/access checks для безопасности.

---

# 40. Безопасность

Основные правила:

- никакого прямого доступа frontend к PostgreSQL;
- секреты только на сервере;
- private Object Storage;
- server-side permission checks;
- rate limiting;
- audit logging;
- backups;
- re-authentication критических действий;
- подготовка к 2FA;
- безопасные сессии;
- контроль загрузки файлов;
- серверная обработка видео;
- provider adapters;
- минимизация персональных данных.

Подробности определяются SECURITY.md.

---

# 41. Резервное копирование

Критические данные должны иметь резервные копии.

Минимально:

- PostgreSQL backups;
- Object Storage backup/retention strategy;
- проверка восстановления;
- документированный rollback.

Backup считается частью инфраструктуры, а не дополнительной опцией.

---

# 42. Миграция с текущей системы

Переход с Supabase выполняется поэтапно:

```text
Current Supabase
      ↓
Backup
      ↓
Target PostgreSQL schema
      ↓
Migration
      ↓
Data verification
      ↓
Backend verification
      ↓
DNS switch
      ↓
Rollback window
      ↓
Old infrastructure decommission
```

Старая система не отключается до успешной проверки новой.

---

# 43. Масштабирование

Масштабирование начинается только после появления реальной нагрузки.

Первый этап:

```text
1 Backend VM
1 PostgreSQL
1 Object Storage
CDN
```

Далее при необходимости:

```text
Backend
 ├── API instances
 ├── Video Worker
 ├── Notification Worker
 └── AI Worker
```

PostgreSQL масштабируется отдельно.

Не следует добавлять инфраструктурные компоненты только «на будущее».

---

# 44. Архитектурное правило модулей

Каждый бизнес-модуль:

- имеет собственную ответственность;
- использует canonical data;
- не дублирует бизнес-логику другого модуля;
- использует Backend Services;
- использует общий Permission Service;
- не знает детали платежного провайдера;
- не знает детали Email-провайдера;
- не обращается напрямую к PostgreSQL из React.

# 46. Главное архитектурное правило

Для любого пользовательского действия система должна последовательно ответить:

```text
1. Кто это?
        ↓
Authentication

2. Имеет ли он право пользоваться функцией?
        ↓
Access

3. Может ли он выполнить конкретное действие?
        ↓
Permissions

4. С каким объектом выполняется действие?
        ↓
Ownership / Relationship / Object State

5. Как сохранить результат?
        ↓
Backend Service → PostgreSQL / Object Storage
```

Эта последовательность является базовой моделью всей платформы.

# Итоговая архитектура Stubborn Ram

```text
                         ┌───────────────┐
                         │   User / PWA  │
                         └───────┬───────┘
                                 │
                                 ▼
                         ┌───────────────┐
                         │  Backend API  │
                         └───────┬───────┘
                                 │
          ┌──────────────────────┼──────────────────────┐
          ▼                      ▼                      ▼
   Authentication             Access              Permissions
          │                      │                      │
          └──────────────────────┼──────────────────────┘
                                 │
                                 ▼
                       ┌──────────────────┐
                       │ Business Modules │
                       └────────┬─────────┘
                                │
       ┌────────────────────────┼─────────────────────────┐
       ▼             ▼          ▼          ▼              ▼
   Training        Food      Activity    Reports         Chat
       │             │          │          │              │
       └─────────────┴──────────┴──────────┴──────────────┘
                                │
                                ▼
                           PostgreSQL
                                │
                       ┌────────┴────────┐
                       ▼                 ▼
                 Object Storage      Audit / Events

External providers are connected only through Backend adapters:
Email / AI-OCR / Payments
```

**Главная модель Stubborn Ram:**

**один User → единая история данных → независимые модули → единый Access → единый Permission Service → Backend как единственная серверная точка контроля.**

Эта модель должна сохраняться при дальнейшем развитии платформы.
