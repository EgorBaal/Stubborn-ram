# PAYMENT_ARCHITECTURE.md

# Архитектура платежей и подписок Stubborn Ram

Версия документа:

2.0

Статус:

Архитектурно утверждено для целевой инфраструктуры; реализация после базовой миграции

---

# Назначение документа

PAYMENT_ARCHITECTURE.md определяет модель платного доступа Stubborn Ram.

Документ описывает:

- источники полного доступа;
- личную подписку пользователя;
- подписку тренера;
- пробный период;
- срок действия доступа;
- grace period для сопровождения тренером;
- возвраты;
- отсутствие автоматического продления на текущем этапе;
- поведение после окончания оплаты;
- ограничения при отсутствии полного доступа;
- подготовку к подключению платежного провайдера.

Платежная система является отдельным модулем и не должна смешиваться с authentication, permissions или хранением пользовательских данных.

---

# 1. Основной принцип

Платеж не является самим правом доступа.

Платеж создает или продлевает определенный источник доступа.

Фактическое право пользователя выполнять действие вычисляется общей системой Access/Permissions.

Схема:

```text
Payment
   ↓
Subscription / Payment Record
   ↓
Access Source
   ↓
Access Service
   ↓
Permission Check
   ↓
Allowed / Denied
```

Frontend не определяет наличие оплаченного доступа самостоятельно.

---

# 2. Источники полного доступа

На платформе предусмотрены три независимых источника полного доступа:

1. Trial;
2. личная подписка пользователя;
3. активное сопровождение тренером с действующей подпиской тренера.

Если хотя бы один источник активен, пользователь получает полный доступ.

Приоритет между источниками не устанавливается.

---

# 3. Trial

Пробный период:

- предоставляется один раз на аккаунт;
- длится 10 календарных дней;
- начинается после подтверждения Email и создания профиля;
- не продлевается автоматически;
- не запускается повторно при смене устройства или повторном входе.

Trial является бесплатным источником полного доступа.

Факт предоставления Trial должен храниться на сервере и быть неизменяемо связан с аккаунтом.

---

# 4. Личная подписка

Личная подписка предоставляет пользователю самостоятельный полный доступ к платформе.

Текущая модель:

- подписка оплачивается пользователем;
- срок действия — один календарный месяц;
- автоматического продления на текущем этапе нет;
- после окончания оплаченного периода доступ повторно вычисляется системой.

Если у пользователя одновременно есть личная подписка и активное сопровождение тренером, оба источника существуют независимо.

Удаление одного источника не должно затрагивать другой.

---

# 5. Подписка тренера

Тренер может иметь собственную платную подписку на сервис сопровождения клиентов.

Она предоставляет тренеру возможность использовать функциональность, связанную с клиентами, в рамках разрешенного лимита.

При наличии действующей подписки тренера его активные клиенты получают полный доступ к платформе согласно правилам COACH_CLIENT_RELATIONSHIP.md.

Таким образом:

```text
Coach Subscription
        ↓
Active Coach Relationship
        ↓
Client Full Access
```

Клиентская связь с тренером и платеж тренера являются разными сущностями.

Окончание подписки тренера не удаляет:

- профиль тренера;
- профиль клиента;
- историю тренировок;
- отчеты;
- переписку;
- медиа;
- другие пользовательские данные.

---

# 6. Grace Period тренера

Для сопровождения тренером предусмотрен grace period:

- 72 часа после окончания оплаченного периода тренера.

В течение grace period существующие активные клиентские отношения продолжают предоставлять соответствующий доступ.

Если подписка тренера не продлена после окончания grace period:

- новые операции, требующие действующей подписки тренера, блокируются;
- существующие клиентские данные сохраняются;
- история не удаляется;
- клиентские аккаунты не удаляются.

Дальнейшее поведение клиента определяется общей системой Access.

---

# 7. Календарный месяц

Личная подписка имеет срок действия один календарный месяц.

При оформлении подписки система фиксирует:

- дату и время начала;
- дату и время окончания;
- идентификатор платежа;
- идентификатор подписки;
- пользователя;
- тариф;
- сумму;
- валюту;
- статус.

Точная реализация расчета периода должна быть единообразной на Backend.

Frontend не вычисляет окончание подписки самостоятельно.

---

# 8. Отсутствие автоматического продления

На текущем этапе автоматическое продление подписки не используется.

После окончания периода:

```text
Active
  ↓
Expired
  ↓
Access recalculation
```

Пользователь должен самостоятельно оформить следующий период.

Архитектура при этом должна позволять в будущем добавить recurring payments без перестройки всей системы.

---

# 9. Платежный провайдер

Платежный провайдер не должен быть жестко встроен в бизнес-логику приложения.

Используется adapter/service слой:

```text
Payment Service
      ↓
Payment Provider Adapter
      ↓
Provider
```

На текущем этапе для российского рынка рассматриваются:

- YooKassa;
- T-Bank acquiring.

Окончательный провайдер выбирается перед реализацией платежного модуля с учетом:

- условий договора;
- комиссии;
- API;
- webhook-механизма;
- требований к возвратам;
- юридических требований;
- требований к хранению платежных данных.

Платежная архитектура не должна зависеть от конкретного провайдера настолько, чтобы смена провайдера требовала переписывания пользовательских модулей.

---

# 10. Backend является источником истины

Все критические платежные состояния определяются Backend.

Frontend не может самостоятельно установить:

- что платеж успешен;
- что подписка активна;
- что срок продлен;
- что возврат выполнен;
- что пользователь получил полный доступ.

Основным источником истины являются серверные записи платежей и подписок.

---

# 11. Webhook платежного провайдера

После подключения платежного провайдера Backend должен принимать серверные уведомления о событиях платежной системы.

Типовые события:

- успешная оплата;
- отмена;
- возврат;
- истечение;
- изменение состояния платежа;
- иные события, предусмотренные API выбранного провайдера.

Webhook должен проходить:

- проверку подлинности;
- проверку структуры;
- идемпотентную обработку;
- запись события;
- обновление платежного состояния.

Повторная доставка одного webhook не должна создавать повторную подписку или повторно зачислять оплату.

---

# 12. Идемпотентность

Платежные операции должны быть идемпотентными.

Для каждой операции система должна иметь уникальный идентификатор или набор идентификаторов, позволяющий определить, что событие уже обработано.

Это особенно важно для:

- webhook;
- повторных запросов;
- пользовательского обновления страницы;
- сетевых ошибок;
- повторной отправки платежного запроса.

---

# 13. Статусы платежа

Платеж и подписка — разные сущности.

Платеж может иметь собственный жизненный цикл, например:

```text
Created
  ↓
Pending
  ↓
Succeeded
  ↓
Refunded
```

или:

```text
Created
  ↓
Canceled / Failed
```

Статус платежа не должен напрямую использоваться frontend как универсальное право доступа.

Backend преобразует платежное состояние в состояние подписки/источника доступа.

---

# 14. Статусы подписки

Подписка должна иметь собственное состояние.

Минимальная логика:

```text
Pending
Active
Expired
Canceled
```

При необходимости могут использоваться дополнительные технические состояния.

Статус подписки вычисляется и изменяется Backend.

---

# 15. Возвраты

На текущем этапе предусмотрена возможность возврата в течение:

- 7 календарных дней.

Возврат должен выполняться через платежный механизм провайдера.

После подтвержденного возврата Backend должен:

1. зафиксировать возврат;
2. связать его с исходным платежом;
3. обновить состояние подписки;
4. пересчитать источник доступа;
5. при необходимости перевести пользователя в ограниченный доступ.

История платежа и возврата не удаляется.

---

# 16. Частичные и технические возвраты

Архитектура должна позволять хранить информацию о:

- полной сумме платежа;
- сумме возврата;
- дате возврата;
- причине возврата;
- внешнем идентификаторе операции.

Поддержка частичных возвратов может быть добавлена позже, если она потребуется выбранному платежному провайдеру и бизнес-модели.

---

# 17. Что происходит после окончания личной подписки

Если личная подписка заканчивается:

1. Backend определяет, существует ли другой источник полного доступа.
2. Если активен Trial — полный доступ сохраняется.
3. Если есть активное сопровождение тренером — полный доступ сохраняется.
4. Если других источников нет — пользователь переходит в ограниченный доступ.

История пользователя сохраняется.

Никакие бизнес-данные не удаляются из-за окончания подписки.

---

# 18. Ограниченный доступ

При отсутствии любого действующего источника полного доступа пользователь:

- может войти;
- может просматривать историю;
- может просматривать сохраненные данные;
- может использовать настройки аккаунта;
- может оформить новую подписку.

Создание новых данных и другие операции, требующие полного доступа, блокируются.

Подробные правила определяются AUTH_ARCHITECTURE.md и PERMISSIONS_ARCHITECTURE.md.

---

# 19. Отмена подписки

Поскольку автоматического продления сейчас нет, отмена автопродления на текущем этапе не требуется.

Если пользователь не покупает следующий период, подписка просто заканчивается в установленную дату.

В будущем при внедрении автоматического продления необходимо отдельно определить:

- отмену автопродления;
- дату окончания оплаченного периода;
- повторные попытки списания;
- неуспешные платежи;
- grace period;
- уведомления.

---

# 20. Уведомления о платежах

Система должна поддерживать транзакционные уведомления:

- платеж создан;
- платеж успешно завершен;
- платеж не завершен;
- подписка скоро заканчивается;
- подписка закончилась;
- возврат выполнен.

Email отправляется через серверный Email Service.

Платежный модуль не должен напрямую вызывать внешний Email API.

---

# 21. Безопасность платежных данных

Stubborn Ram не должен хранить данные банковской карты пользователя.

Карточные данные обрабатываются платежным провайдером в рамках его платежной инфраструктуры.

В базе Stubborn Ram сохраняются только необходимые данные о платежной операции, например:

- пользователь;
- сумма;
- валюта;
- статус;
- дата;
- внешний идентификатор;
- тариф;
- информация о возврате;
- технические метаданные.

Секретные ключи платежного провайдера хранятся только на Backend/серверной инфраструктуре.

Они не попадают во frontend и Git.

---

# 22. Связь с Permissions

Payment Service не выдает права на отдельные действия напрямую.

После изменения состояния платежа Access Service пересчитывает доступ.

Далее Permission Service принимает решение для конкретного действия.

Пример:

```text
Payment succeeded
       ↓
Subscription active
       ↓
Access source active
       ↓
User has full access
       ↓
Permission: training.create = allowed
```

---

# 23. Связь с Coach-Client Relationship

Подписка тренера не является свойством клиента.

Она является свойством аккаунта тренера.

Клиент получает соответствующий источник доступа только при наличии:

- действующей подписки тренера;
- активной связи Coach → Client.

Если связь архивирована, подписка тренера не должна автоматически давать клиенту доступ через старую связь.

Исторические данные клиента сохраняются.

---

# 24. Архитектура данных

Целевая логическая модель:

```text
User
 │
 ├── Payment
 │      └── Payment Provider ID
 │
 ├── Personal Subscription
 │
 ├── Trial
 │
 └── Coach Relationship
          │
          └── Coach Subscription
```

Платежи и подписки должны иметь собственные записи.

Нельзя использовать только поле вроде:

`is_paid = true`

как единственный источник истины.

Необходимо сохранять историю изменения платежного состояния.

---

# 25. Аудит платежей

Критические платежные операции должны быть журналируемыми.

Минимально необходимо иметь возможность определить:

- кто совершил действие;
- какой платеж затронут;
- какой внешний идентификатор использовался;
- какое состояние было до операции;
- какое состояние стало после;
- когда произошло изменение;
- каким серверным событием оно вызвано.

Это необходимо для расследования ошибок и спорных платежных ситуаций.

---

# 26. Отсутствие зависимости модулей от платежного провайдера

Модули Training, Food, Activity, Reports, Photos, Measurements, Weight, Chat и Analytics не должны напрямую знать API платежного провайдера.

Они работают только с результатом общей проверки доступа.

Например:

```text
Training
   ↓
Permission Service
   ↓
Access Service
   ↓
Subscription / Trial / Coach Relationship
```

Это позволяет заменить платежного провайдера без переписывания бизнес-модулей.

---

# 27. Будущее автоматическое продление

Архитектура должна позволять позднее добавить:

- recurring payments;
- сохраненный платежный метод у провайдера;
- автоматическое списание;
- уведомление перед списанием;
- повторные попытки;
- grace period;
- отмену автопродления.

Эти возможности не реализуются на текущем этапе.

---

# 28. Минимальный MVP платежной системы

На первом этапе достаточно реализовать:

1. личный тариф;
2. создание платежа;
3. переход пользователя на платежную страницу провайдера;
4. прием webhook;
5. идемпотентную обработку;
6. создание/продление личной подписки;
7. расчет срока в один календарный месяц;
8. возврат в течение 7 дней;
9. единый Access Service;
10. уведомления о платежах;
11. журналирование платежных событий.

Автоматическое продление, промокоды, рассрочки, сложные тарифы и marketplace не входят в MVP.

---

# 29. Подготовка к масштабированию

Платежная архитектура должна поддерживать:

- несколько тарифов;
- разные типы подписок;
- разные валюты;
- несколько платежных провайдеров;
- корпоративные тарифы;
- marketplace;
- будущие услуги нескольких специалистов.

Добавление новых типов продуктов не должно требовать изменения базовой модели авторизации.

---

# Итоговая модель

```text
                    ┌─────────────────────┐
                    │     User / Coach    │
                    └──────────┬──────────┘
                               │
                               ▼
                       ┌───────────────┐
                       │ Payment       │
                       │ Service       │
                       └───────┬───────┘
                               │
                     ┌─────────▼─────────┐
                     │ Provider Adapter  │
                     └─────────┬─────────┘
                               │
                         Payment Provider
                               │
                             Webhook
                               │
                               ▼
                    ┌─────────────────────┐
                    │ Subscription State  │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │    Access Service   │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │ Permission Service  │
                    └──────────┬──────────┘
                               │
                         Allow / Deny
```

Главное правило:

**Платеж подтверждает экономическое событие. Подписка формирует источник доступа. Access Service определяет наличие полного доступа. Permission Service определяет, разрешено ли конкретное действие.**

Это разделение является обязательным для целевой архитектуры Stubborn Ram.
