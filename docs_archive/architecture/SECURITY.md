---

# 1. Назначение документа

Этот документ определяет базовые принципы безопасности платформы Stubborn Ram.

Документ является частью архитектуры проекта и применяется ко всем модулям, данным, API, административным функциям, файлам и интеграциям.

Безопасность строится по принципам:

- минимально необходимые права;
- разделение пользовательских и административных возможностей;
- серверная проверка доступа;
- отсутствие секретов во frontend;
- защита персональных данных;
- контроль доступа к файлам;
- аудит критических административных действий;
- безопасное хранение паролей и токенов;
- возможность дальнейшего усиления защиты без изменения бизнес-архитектуры.

---

# 2. Системные уровни доступа

На текущем этапе используются два системных уровня доступа.

## User

Обычный пользователь платформы.

## Admin

Администратор платформы.

Уровень доступа Admin используется исключительно для обслуживания платформы.

Дополнительные права предоставляются только при наличии соответствующего уровня доступа.

Роли не должны использоваться как единственный механизм определения разрешенного действия. Конкретное действие дополнительно проверяется общей системой permissions.

---

# 3. Назначение администратора

Администратор существует исключительно для обеспечения работоспособности платформы.

Администратор может использовать административные инструменты только для:

- технической поддержки пользователей;
- решения проблем с авторизацией;
- решения проблем с подписками;
- решения проблем с оплатой;
- восстановления доступа;
- анализа ошибок платформы;
- обеспечения безопасности системы.

Административные полномочия не используются для обычного использования платформы.

---

# 4. Административный доступ

Администратор использует собственный аккаунт платформы.

Создание отдельного административного аккаунта на уровне пользовательской модели не требуется.

Если аккаунт обладает уровнем доступа Admin, пользователю становятся доступны административные функции.

При этом сервер всегда проверяет:

1. аутентификацию;
2. системный уровень доступа;
3. конкретное permission/action;
4. объект и его состояние;
5. при необходимости — дополнительные ограничения безопасности.

Frontend не является источником истины для административных прав.

---

# 5. Режим администратора

Пользователь с уровнем доступа Admin получает возможность переключения в режим администратора.

Переключение выполняется только внутри собственного аккаунта.

Во время просмотра пользовательских данных система должна явно отображать, что используется административный режим.

## Переключение режима

Если аккаунт обладает системным уровнем доступа Admin, пользователь получает возможность переключения в режим администратора.

Переключение выполняется внутри собственного аккаунта и не требует повторной авторизации как другого пользователя.

Переключатель режима администратора отображается только пользователям с уровнем доступа Admin.

Переход в режим администратора не изменяет учетную запись пользователя и не выполняет вход под учетной записью другого человека.

Для критических административных операций в целевой реализации может потребоваться повторное подтверждение личности (re-authentication), даже если обычное переключение режима его не требует.

---

# 6. Просмотр пользовательских данных

Администратор имеет право просматривать пользовательские данные исключительно для выполнения задач технической поддержки и обслуживания платформы.

Пароль пользователя никогда не отображается и не может быть получен администратором.

Администратор не выполняет вход под учетной записью пользователя.

## Административный просмотр

При открытии пользовательского профиля используется специальный режим административного просмотра.

Во время административного просмотра интерфейс должен явно отображать, что администратор просматривает чужой аккаунт.

Административный просмотр используется исключительно для:

- технической поддержки пользователей;
- обеспечения безопасности платформы;
- исполнения пользовательского соглашения;
- диагностики технических проблем.

Доступ администратора к чувствительным данным должен быть минимально необходимым для конкретной задачи.

---

# 7. Поиск пользователей

Администратор может находить пользователей по:

- user_id;
- Email;
- имени;
- фамилии.

В дальнейшем список способов поиска может быть расширен без изменения общей архитектуры платформы.

Поиск не должен предоставлять администратору больше данных, чем необходимо для выполнения административной задачи.

---

# 8. Полномочия администратора

Администратор имеет право изменять только системные данные, необходимые для обслуживания платформы.

На текущем этапе к ним относятся:

- статус подписки;
- срок действия подписки;
- статус Trial;
- связь пользователя с тренером;
- системный статус аккаунта.

Изменение пользовательских бизнес-данных не должно выполняться без соответствующего административного сценария и audit log.

Критические операции должны иметь:

- проверку permission;
- серверную проверку;
- запись в audit log;
- указание администратора;
- указание объекта;
- время операции;
- тип действия;
- при необходимости — причину операции.

---

# 9. Permissions и серверная проверка

Система permissions является единой точкой определения доступности действий.

Permissions являются action-based.

Роль User/Admin сама по себе не определяет все разрешения.

При проверке учитываются:

- системный уровень;
- владелец объекта;
- автор объекта;
- связь Client–Coach;
- статус этой связи;
- состояние объекта;
- статус доступа пользователя;
- конкретное действие.

Клиентский интерфейс может скрывать недоступные действия, но это не является защитой.

Каждое защищенное действие обязательно проверяется на сервере.

---

# 10. Аутентификация

Аутентификация должна выполняться через целевой Backend API.

Frontend не хранит пароли и не получает доступ к внутренним механизмам хранения учетных данных.

Пароли должны храниться только в форме безопасных password hashes с использованием стандартного современного механизма password hashing.

В системе предусматриваются:

- регистрация;
- подтверждение Email;
- вход;
- выход;
- восстановление пароля;
- persistent session;
- защита маршрутов;
- смена Email;
- уведомления о критических изменениях аккаунта.

Будущая 2FA/MFA должна добавляться поверх существующей модели аутентификации, не меняя бизнес-данные пользователя.

---

# 11. Сессии и токены

Сессионные токены не должны попадать в исходный код frontend.

Секреты backend хранятся только на сервере или в защищенном хранилище секретов.

Предпочтительный механизм браузерной сессии — защищенная серверная cookie-модель с:

- HttpOnly;
- Secure;
- подходящим SameSite;
- ограниченным сроком действия;
- возможностью отзыва сессии.

Точные значения cookie-параметров определяются при реализации Backend API с учетом production-домена.

---

# 12. Защита frontend

Во frontend запрещено хранить:

- database password;
- private API keys;
- SMTP credentials;
- payment secret keys;
- AI provider secret keys;
- S3 secret keys;
- административные секреты;
- другие server-side credentials.

Frontend взаимодействует только с публичными endpoint/API, предназначенными для клиента.

Все внешние сервисы подключаются через Backend API или соответствующий server-side service layer.

---

# 13. Backend API

Backend API является основной точкой контроля доступа к данным и бизнес-логике.

Backend отвечает за:

- аутентификацию;
- авторизацию;
- permissions;
- работу с PostgreSQL;
- работу с Object Storage;
- загрузку и выдачу файлов;
- обработку отчетов;
- работу чата;
- отправку Email;
- AI/OCR;
- платежные интеграции;
- audit logging;
- rate limiting;
- валидацию входных данных.

Прямой доступ frontend к базе данных не используется в целевой архитектуре.

---

# 14. База данных

Целевая база данных — PostgreSQL.

Доступ к PostgreSQL разрешен только backend-сервисам.

Database credentials не должны находиться во frontend или Git-репозитории.

Используется принцип least privilege:

- отдельные учетные данные для приложений;
- минимально необходимые права;
- отсутствие общего административного пароля в коде;
- отдельные права для миграций и runtime, если это необходимо.

RLS может использоваться как дополнительный уровень defense-in-depth, но основной контроль бизнес-доступа выполняет Backend API.

---

# 15. Персональные данные

Stubborn Ram обрабатывает персональные данные пользователей.

К персональным данным могут относиться:

- имя;
- Email;
- телефон;
- данные профиля;
- анкета;
- данные тренировок;
- питание;
- вес;
- замеры;
- фотографии;
- видео;
- отчеты;
- переписка;
- данные о взаимодействии с тренером.

Для production необходимо обеспечить:

- законное основание обработки;
- информирование пользователя;
- необходимые согласия;
- политики обработки персональных данных;
- процедуры удаления/архивирования;
- контроль доступа;
- журналирование критических действий;
- резервное копирование;
- восстановление после сбоя;
- выполнение применимых требований законодательства РФ.

Российское размещение инфраструктуры само по себе не заменяет юридические и организационные меры.

---

# 16. География хранения данных

Целевая инфраструктура для пользовательских данных размещается в российском регионе.

Основные компоненты:

- Backend;
- PostgreSQL;
- Object Storage;
- внутренние очереди/worker-процессы

не должны без отдельного архитектурного решения переносить пользовательские данные в иностранные регионы.

Любая внешняя интеграция, получающая персональные данные, должна быть отдельно проверена до подключения.

Особенно отдельно проверяются:

- AI/OCR;
- Email;
- платежи;
- аналитика;
- внешние API.

---

# 17. Object Storage и файлы

Фото и видео пользователей хранятся в Object Storage.

Файлы не должны быть публичными по умолчанию.

Доступ к файлу предоставляется через backend authorization.

Предпочтительная схема:

User
↓
Backend API
↓
проверка permission
↓
короткоживущая ссылка / потоковая выдача
↓
Object Storage

Прямые постоянные публичные ссылки на пользовательские файлы не используются.

Для каждого файла должны сохраняться как минимум:

- file id;
- owner;
- object key;
- тип файла;
- размер;
- дата загрузки;
- связанный объект;
- статус обработки.

---

# 18. Загрузка видео

Видео является потенциально тяжелым ресурсом.

Для загрузок необходимо предусмотреть:

- ограничение размера;
- проверку MIME/type;
- серверную валидацию;
- безопасное имя/object key;
- временное хранение исходника;
- FFmpeg processing;
- удаление исходника после успешной обработки, если он больше не нужен;
- хранение обработанной версии;
- ограничения продолжительности.

Для Training ранее определено:

- максимум 8 видео на тренировку;
- максимум 45 секунд на видео;
- сжатие;
- удаление оригинала после успешной обработки.

Эти ограничения являются частью бизнес-архитектуры Training.

---

# 19. Chat

Чат реализуется внутри Stubborn Ram.

Основные данные хранятся в PostgreSQL.

Медиафайлы чата хранятся в Object Storage.

Real-time доставка сообщений выполняется через собственный Backend/WebSocket слой.

Внешний realtime-провайдер не является обязательным компонентом архитектуры.

Для чата применяются те же правила:

- permission check;
- проверка coach-client relationship;
- приватность объектов;
- приватное хранение файлов;
- audit logging для административного доступа.

---

# 20. Email

Transactional Email отправляется через server-side Email service.

Email credentials и API keys никогда не передаются frontend.

Backend должен:

- формировать письмо;
- передавать его Email provider;
- сохранять только необходимый технический статус;
- обрабатывать ошибки доставки;
- не раскрывать секретный API key клиенту.

Перед production-подключением Email provider должен быть отдельно проверен на соответствие требованиям обработки пользовательских данных и выбранной юрисдикции.

---

# 21. AI и OCR

AI/OCR вызывается только через Backend API.

Frontend не получает секретный ключ AI-провайдера.

Перед отправкой пользовательских данных внешнему AI-сервису backend должен определить:

- какие данные действительно нужны;
- можно ли удалить лишние персональные данные;
- где обрабатываются данные;
- сохраняет ли провайдер запросы;
- срок хранения;
- возможность отключения хранения.

Для FOOD AI screenshot import исходное изображение после распознавания не должно храниться дольше, чем необходимо для операции, согласно архитектуре Food.

AI-провайдер подключается через service adapter, чтобы в будущем его можно было заменить без изменения бизнес-логики.

---

# 22. Платежи

Платежные данные банковских карт не хранятся в Stubborn Ram.

Оплата выполняется через внешний платежный сервис.

Backend получает только необходимые:

- payment id;
- статус;
- сумму;
- идентификатор пользователя;
- технические метаданные.

Secret keys платежного провайдера хранятся только на backend.

Платежный provider подключается через paymentService adapter.

---

# 23. Rate limiting и защита API

Публичные и чувствительные endpoint должны иметь rate limiting.

Особенно защищаются:

- login;
- registration;
- password recovery;
- Email verification;
- file upload;
- chat send;
- AI/OCR;
- payment endpoints;
- административные endpoint.

Дополнительно применяются:

- request validation;
- размерные лимиты;
- timeout;
- защита от повторной отправки критических операций;
- безопасная обработка ошибок.

Внешнему клиенту не возвращаются stack traces и внутренние credentials.

---

# 24. Audit Log

Критические административные и системные действия должны журналироваться.

Минимально необходимо фиксировать:

- actor;
- action;
- object type;
- object id;
- timestamp;
- результат;
- при необходимости reason;
- технический request/correlation id.

Audit log используется для расследования:

- административного доступа;
- изменения подписки;
- изменения coach-client relationship;
- восстановления доступа;
- критических security events;
- подозрительных действий.

Audit log не должен содержать пароли и секретные токены.

---

# 25. Резервное копирование

PostgreSQL должен регулярно резервироваться.

Для production предусматриваются:

- автоматические backups;
- point-in-time recovery, если поддерживается выбранным managed PostgreSQL;
- проверка восстановления;
- отдельное хранение резервных копий;
- понятный срок хранения.

Object Storage также должен иметь стратегию защиты от случайного удаления критических данных.

Backup считается полезным только после проверки реального восстановления.

---

# 26. Логи и мониторинг

Система должна собирать технические логи backend.

В логах запрещено хранить:

- пароли;
- session tokens;
- API keys;
- полные платежные реквизиты;
- содержимое приватной переписки без необходимости;
- лишние персональные данные.

Необходимо иметь возможность обнаруживать:

- падения API;
- рост ошибок;
- проблемы с БД;
- ошибки Object Storage;
- проблемы Email;
- проблемы AI;
- необычную административную активность.

---

# 27. Ошибки и отказоустойчивость

Ошибка внешнего сервиса не должна приводить к раскрытию внутренних данных.

Каждая внешняя интеграция должна иметь:

- timeout;
- controlled retry;
- обработку ошибки;
- понятный fallback;
- журналирование технической причины.

Критические данные сначала сохраняются в собственную систему, а затем передаются внешнему сервису, если это архитектурно возможно.

Это особенно важно для:

- Email;
- AI;
- платежей;
- внешних API.

---

# 28. Секреты и переменные окружения

Production secrets хранятся вне frontend bundle.

Локальная разработка использует `.env`/`.env.local`, которые не должны попадать в Git.

В Git запрещено коммитить:

- `.env` с секретами;
- private keys;
- service account credentials;
- database passwords;
- API tokens.

Перед production необходимо проверить repository history на случайно опубликованные секреты.

---

# 29. Административная безопасность

Для Admin должны применяться более строгие меры, чем для обычного User.

Целевые меры:

- отдельный административный audit trail;
- rate limiting;
- уведомления о критических security events;
- re-authentication для критических операций;
- будущая 2FA/MFA;
- минимизация доступа к пользовательским данным;
- отсутствие возможности узнать пароль пользователя.

Администратор не должен иметь технической возможности получить пароль пользователя в открытом виде.

---

# 30. Уведомления безопасности

Пользователь должен получать security notification при критических изменениях аккаунта, например:

- смена Email;
- восстановление доступа;
- изменение пароля;
- другие критические операции, определенные при реализации Auth.

Такие уведомления не должны содержать секреты.

---

# 31. Архивирование и удаление

Удаление данных должно учитывать бизнес-архитектуру платформы.

История пользователя не должна исчезать только из-за:

- окончания подписки;
- прекращения coach-client relationship;
- перехода пользователя между статусами.

Используется soft archive там, где это предусмотрено архитектурой.

Физическое удаление выполняется только там, где оно действительно требуется, и должно учитывать:

- юридические требования;
- retention policy;
- связанные объекты;
- backups;
- audit requirements.

# 33. Миграция безопасности

Миграция должна выполняться без преждевременного отключения текущей системы.

Порядок:

1. Создать резервные копии текущих данных.
2. Подготовить целевую PostgreSQL.
3. Подготовить Object Storage.
4. Реализовать Backend API.
5. Перенести данные.
6. Проверить пользователей и связи.
7. Проверить доступы.
8. Проверить файлы.
9. Проверить Email.
10. Проверить критические security scenarios.
11. Переключить production traffic.
12. Сохранить старую систему в режиме rollback window.
13. После успешного периода эксплуатации удалить старую инфраструктуру.

До подтверждения успешной миграции старая система считается резервным контуром.

---

# 34. Definition of Done для SECURITY

Документ и архитектура считаются реализованными для production, когда:

- frontend не содержит server secrets;
- Backend проверяет authentication и permissions;
- Admin access журналируется;
- пароли недоступны администраторам;
- пользовательские файлы приватны;
- Object Storage защищен;
- API имеет rate limiting;
- PostgreSQL закрыт от прямого клиентского доступа;
- backups настроены;
- восстановление проверено;
- критические security events журналируются;
- Email/AI/payment integrations работают через backend;
- production secrets вынесены из Git;
- требования к персональным данным и трансграничной передаче проверены;
- миграция со старой инфраструктуры имеет rollback plan.

---

# 35. Принцип дальнейшего развития

Безопасность не должна зависеть от конкретного поставщика.

Поэтому:

- database доступ осуществляется через service layer;
- storage — через storage service;
- email — через email service;
- AI — через AI service;
- payments — через payment service;
- realtime — через собственный backend abstraction.

Замена отдельного провайдера не должна требовать переписывания пользовательских модулей.

Это сохраняет архитектурную независимость Stubborn Ram и уменьшает риск повторной миграции.
