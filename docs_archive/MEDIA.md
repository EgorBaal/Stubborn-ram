# Архитектура Media Stubborn Ram

Версия документа: 1.0

Статус: Архитектурно утверждено для MVP; реализация после базовой миграции

---

# 1. Назначение

Media — единая инфраструктура хранения и доступа к пользовательским файлам Stubborn Ram.

Она используется для:

- Chat;
- Weekly Reports;
- Training;
- будущих Photos & Measurements;
- других модулей, которым требуется хранение файлов.

Media не является отдельным пользовательским разделом.

Она предоставляет единую серверную модель хранения файлов и их метаданных.

---

# 2. Основной принцип

Структурированные данные хранятся в PostgreSQL.

Файлы хранятся в private Object Storage.

Схема:

```text
Application Object
       ↓
Media Link
       ↓
Media Metadata
       ↓
Private Object Storage
```

Например:

```text
Report
  ↓
Media Link
  ↓
Media
  ↓
S3 Object
```

Chat, Report и Training не создают собственных систем хранения файлов.

---

# 3. Object Storage

Для MVP используется S3-compatible Object Storage на российской инфраструктуре.

Целевой вариант:

- Selectel Object Storage.

Bucket/container должен быть приватным.

Публичное чтение пользовательских файлов не используется.

---

# 4. Что хранится в PostgreSQL

PostgreSQL хранит метаданные файла, например:

- `media_id`;
- `owner_user_id`;
- `object_key`;
- `file_name`;
- `mime_type`;
- `size`;
- `status`;
- `created_at`;
- `updated_at`;
- технические данные обработки;
- необходимые связи с объектами платформы.

Сам бинарный файл в PostgreSQL не является основным способом хранения.

---

# 5. Media Link

Связь файла с объектом платформы хранится отдельно.

Пример:

```text
Report
  ↓
media_link
  ↓
media
```

Это позволяет один и тот же Media-механизм использовать для разных типов объектов.

В MVP одно сообщение Chat может ссылаться на соответствующий media object.

Точные правила повторного использования одного файла между объектами определяются конкретным модулем.

---

# 6. Ownership

Каждый пользовательский файл имеет владельца.

Ownership не меняется только потому, что другой пользователь получил доступ к объекту, с которым связан файл.

Например:

```text
Client
  ↓ owns
Media
  ↓ linked to
Report
  ↓ accessible by
Coach
```

Тренер получает доступ к файлу через разрешенный доступ к соответствующему объекту, а не становится владельцем файла.

---

# 7. Приватность

Все пользовательские Media по умолчанию являются приватными.

Нельзя:

- хранить пользовательские файлы в публичном bucket;
- выдавать постоянные публичные URL;
- помещать секретные storage credentials во frontend;
- обходить backend permission checks прямым запросом к storage.

---

# 8. Доступ к файлу

Frontend не получает постоянный публичный URL.

Целевая схема:

```text
Frontend
   ↓
Backend API
   ↓
Authentication
   ↓
Permission / Ownership / Relationship Check
   ↓
Signed URL
   ↓
Private Object Storage
```

Signed URL имеет ограниченный срок действия.

Backend определяет, имеет ли пользователь право получить файл.

---

# 9. Загрузка файла

Целевая последовательность:

```text
User
 ↓
Frontend
 ↓
Backend
 ↓
Validation
 ↓
Media Record
 ↓
Object Storage
 ↓
Processing if required
 ↓
Ready
```

Backend должен контролировать:

- авторизацию;
- размер файла;
- MIME type;
- допустимое назначение файла;
- ownership;
- связь с объектом;
- статус обработки.

Frontend может выполнять предварительную валидацию только как UX-улучшение.

---

# 10. Имена и Object Key

Имя пользовательского файла не должно использоваться как единственный идентификатор объекта в storage.

Object key должен генерироваться сервером.

Например:

```text
media/{user_id}/{media_id}/original
media/{user_id}/{media_id}/processed
```

Точная структура ключа определяется реализацией backend.

Она не должна позволять пользователю произвольно выбрать storage path.

---

# 11. Поддерживаемые типы

MVP должен поддерживать основные типы файлов, необходимые для Chat и Reports:

- изображения;
- видео;
- документы;
- аудио для голосовых сообщений.

Конкретный whitelist MIME types и расширений утверждается при реализации upload endpoint.

Неподдерживаемые типы должны отклоняться backend.

---

# 12. Изображения

Для изображений backend должен проверять:

- MIME type;
- размер;
- допустимое расширение;
- фактическое содержимое файла;
- допустимые технические параметры.

При необходимости может создаваться оптимизированная версия изображения.

Оригинал не удаляется автоматически в MVP, если он является пользовательским материалом отчета или другого объекта, для которого требуется постоянное хранение.

---

# 13. Видео

Видео обрабатываются серверно.

Целевая схема:

```text
Upload
 ↓
Private S3
 ↓
FFmpeg Worker
 ↓
Processed Video
 ↓
Ready
```

Для MVP:

- исходный файл может сохраняться;
- обработанная версия используется для просмотра;
- автоматическое удаление пользовательского исходника не применяется без отдельного правила хранения.

Для Training действуют дополнительные ограничения, определенные TRAINING.md, включая текущий лимит до 8 видео на тренировку и до 45 секунд на видео.

---

# 14. FFmpeg Worker

FFmpeg не выполняется в браузере.

Обработка видео выполняется на сервере/worker.

На начальном этапе worker может находиться на том же Cloud Server, если нагрузка небольшая.

При реальной нагрузке обработка может быть вынесена на отдельный worker.

Kubernetes и отдельная микросервисная инфраструктура для этого не требуются на MVP.

---

# 15. Аудио

Голосовые сообщения Chat хранятся как Media.

Chat Message содержит ссылку на Media, а не бинарные данные внутри сообщения.

Автоматическая расшифровка голосовых сообщений не входит в MVP.

---

# 16. Документы

Документы Chat могут храниться через ту же Media-систему.

Backend проверяет:

- тип;
- размер;
- ownership;
- доступ пользователя;
- связь с сообщением.

Документы не публикуются через постоянные публичные URL.

---

# 17. Удаление

В MVP автоматическое удаление Media не используется.

В частности, не создаются lifecycle rules, которые автоматически удаляют пользовательские:

- отчеты;
- сообщения;
- фото;
- видео;
- документы.

Удаление данных выполняется только через предусмотренный серверный процесс и соответствующую политику хранения.

---

# 18. Статусы Media

Минимальный жизненный цикл:

```text
UPLOADING
   ↓
PROCESSING
   ↓
READY
```

При ошибке:

```text
PROCESSING
   ↓
FAILED
```

Для файлов без дополнительной обработки возможен переход:

```text
UPLOADING
   ↓
READY
```

Frontend должен корректно отображать состояние обработки.

---

# 19. Permissions

Для Media используются как минимум:

```text
media.upload
media.read
```

При необходимости могут добавляться:

- `media.delete`;
- `media.update`.

Каждое действие проходит backend permission check.

Доступ к media не считается разрешенным только потому, что пользователь знает `media_id` или storage key.

---

# 20. Relationship Access

Если Media связан с объектом клиента, тренер получает доступ только при наличии соответствующего права на родительский объект.

Пример:

```text
Coach
 ↓
Active Coach/Client Relationship
 ↓
Report.read
 ↓
Report
 ↓
Media.read
 ↓
Signed URL
```

Нельзя открыть файл только по ссылке, если доступ к родительскому объекту отсутствует.

---

# 21. Chat Media

Chat использует общую Media-систему.

Схема:

```text
Chat Message
   ↓
Media Link
   ↓
Media
   ↓
Private Object Storage
```

Сообщение хранит metadata/reference, а бинарный файл находится в Object Storage.

---

# 22. Report Media

Report использует ту же Media-систему.

Схема:

```text
Report
   ↓
Media Link
   ↓
Media
   ↓
Private Object Storage
```

Материалы отчета являются частью постоянной истории пользователя.

---

# 23. Training Media

Training использует ту же Media-систему.

Тренировочные видео:

- принадлежат пользователю;
- связаны с тренировкой/упражнением/подходом согласно модели Training;
- доступны тренеру только при наличии соответствующих permissions;
- хранятся в private Object Storage.

---

# 24. Upload Security

Backend обязан выполнять серверную проверку загрузки.

Минимально:

- authentication;
- authorization;
- MIME validation;
- size limits;
- object ownership;
- allowed destination;
- safe object key;
- processing status.

Нельзя доверять только:

- расширению файла;
- MIME type, присланному браузером;
- имени файла.

При необходимости backend проверяет фактическое содержимое файла.

---

# 25. Storage Credentials

Credentials Object Storage:

- находятся только на сервере;
- не попадают во frontend;
- не попадают в Git;
- не передаются пользователю.

Frontend получает только результат backend-операции и временные signed URLs.

---

# 26. Производительность

Media-система должна учитывать:

- мобильный интернет;
- большие видео;
- повторное открытие файлов;
- CDN в будущем;
- серверную обработку видео;
- кэширование безопасных производных файлов.

CDN не является обязательным компонентом MVP.

Он подключается только если реальная нагрузка или география пользователей делает его оправданным.

---

# 27. Ограничения MVP

В MVP не требуется:

- отдельный media microservice;
- Kubernetes;
- Redis только ради Media;
- внешний SaaS для хранения пользовательских файлов;
- публичные пользовательские bucket;
- автоматическая AI-модерация;
- автоматическая транскрипция;
- сложная media analytics система.

---

# 28. Связь с Backend

Frontend работает с Media только через `mediaService`.

Целевая схема:

```text
Module
 ↓
mediaService
 ↓
apiClient
 ↓
Backend API
 ↓
Permission / Ownership Check
 ↓
Object Storage
```

Frontend не обращается к storage credentials или PostgreSQL напрямую.

---

# 29. MVP Definition of Done

Media считается готовым для MVP, когда:

- пользователь может загрузить разрешенный файл;
- backend валидирует загрузку;
- файл сохраняется в private Object Storage;
- metadata сохраняется в PostgreSQL;
- Media связывается с объектом платформы;
- permissions проверяются сервером;
- файл можно безопасно открыть через signed URL;
- Chat может использовать Media;
- Reports может использовать Media;
- Training может использовать Media;
- видео при необходимости проходит серверную обработку;
- ошибки загрузки/обработки корректно отображаются;
- пользовательские материалы не удаляются автоматически.

---

# 30. Связанные документы

Media работает совместно с:

- DATABASE_SCHEMA.md;
- SECURITY.md;
- PERMISSIONS_ARCHITECTURE.md;
- CHAT.md;
- REPORT.md;
- TRAINING.md;
- COACH_CLIENT_RELATIONSHIP.md;
- PROJECT_STRUCTURE.md.

---

# Итог

Media является единой инфраструктурой пользовательских файлов Stubborn Ram.

PostgreSQL хранит metadata и связи.

Private Object Storage хранит бинарные файлы.

Backend контролирует загрузку и доступ.

Signed URLs используются для безопасного просмотра.

Chat, Reports и Training используют одну Media-систему.

Автоматическое удаление пользовательских материалов не используется в MVP.

Видео обрабатывается серверно через FFmpeg Worker.

Архитектура должна оставаться независимой от конкретного storage-провайдера настолько, чтобы его замена не требовала переписывания пользовательских модулей.
