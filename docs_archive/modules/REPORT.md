# Архитектура еженедельных отчетов Stubborn Ram

Версия документа: 1.0

Статус: Архитектурно утверждено для MVP; реализация после базовой миграции

---

# 1. Назначение

Weekly Report — основной рабочий объект взаимодействия клиента и тренера в MVP.

Отчет позволяет клиенту собрать материалы за отчетный период, отправить их тренеру и получить обратную связь.

Отчет является самостоятельным объектом платформы и хранится отдельно от Chat.

Chat может содержать ссылку на отчет, но не является местом хранения самого отчета.

---

# 2. Основной принцип

Один отчет представляет один отчетный период пользователя.

В MVP отчет должен поддерживать:

- создание отчета клиентом;
- заполнение материалов;
- сохранение черновика;
- отправку отчета;
- просмотр собственного отчета клиентом;
- просмотр отчета тренером при наличии соответствующей связи;
- обратную связь тренера;
- постоянное хранение отчета и связанных материалов.

История отчетов не удаляется автоматически.

---

# 3. Жизненный цикл

Основной жизненный цикл:

```text
DRAFT
  ↓
SUBMITTED
  ↓
REVIEWED
```

## DRAFT

Отчет создан, но ещё не отправлен тренеру.

Клиент может продолжать его редактировать.

## SUBMITTED

Клиент отправил отчет.

После отправки отчет становится доступным тренеру для проверки.

SUBMITTED является архивной версией отчета и не редактируется задним числом.

Состояние данных, попавших в отчет, фиксируется на момент отправки.

## REVIEWED

Тренер завершил проверку и оставил обратную связь.

История отчета и обратной связи сохраняется.

## 3.1. Состояние данных в отправленном отчете

Отправленный отчет сохраняет состояние данных на момент отправки.

При открытии исходной сущности из отчета пользователь может видеть её текущее состояние.

Таким образом:

- Report хранит историческое состояние на момент SUBMITTED;
- исходная каноническая сущность может изменяться после отправки;
- просмотр исходной сущности не изменяет архивный Report.

---

# 4. Кто создаёт отчет

В MVP отчет создаёт клиент.

Тренер не создаёт отчет от имени клиента без отдельного архитектурного решения.

---

# 5. Данные отчета

Отчет должен хранить как минимум:

- идентификатор;
- владельца;
- отчетный период;
- дату создания;
- дату отправки;
- дату проверки;
- текущий статус;
- текстовые данные отчета;
- идентификатор связанного Coach/Client Relationship;
- ответы анкеты;
- состав включённых в отчет модулей и элементов;
- выбранный отчетный период;
- timestamps.

Точная физическая структура PostgreSQL определяется DATABASE_SCHEMA.md.

---

# 6. Материалы отчета

К отчету могут относиться пользовательские материалы:

- фотографии;
- видео;
- документы;
- другие поддерживаемые файлы.

Файлы не хранятся внутри PostgreSQL как основное содержимое.

Используется:

```text
Report
   ↓
Media Link
   ↓
Private Object Storage
```

PostgreSQL хранит метаданные и связь файла с отчетом.

# 6.1. Состав и период отчета

По умолчанию отчет формируется за последние 7 дней.

Пользователь может выбрать другой отчетный период или отдельные дни.

По умолчанию отчет включает данные всех основных фитнес-модулей.

Пользователь может:

- исключить отдельный модуль или элемент;
- добавить отдельный элемент, если он доступен для включения в отчет.

Отчет подтягивает данные из канонических сущностей модулей.

Данные не должны дублироваться в Report как самостоятельные копии, кроме данных, которые относятся непосредственно к самому отчету, анкете и зафиксированному состоянию отправки.

---

# 7. Хранение медиа

Медиа отчета являются частью постоянной истории пользователя.

В MVP автоматическое удаление отчетных материалов не используется.

Приватные файлы хранятся в Object Storage.

Доступ к ним предоставляется через backend и signed URLs после проверки permissions.

---

# 8. Отправка отчета

При отправке:

1. Backend проверяет авторизацию;
2. Backend проверяет ownership;
3. Backend проверяет relationship;
4. Backend проверяет право `report.submit`;
5. Backend валидирует обязательные данные;
6. отчет переводится в `SUBMITTED`;
7. дата отправки фиксируется;
8. событие может быть отражено в in-app уведомлениях.

Frontend не может самостоятельно установить статус `SUBMITTED`.

---

# 9. Проверка тренером

Тренер может просматривать отчет клиента только при наличии соответствующего доступа.

Backend проверяет:

- авторизацию тренера;
- активную или допустимую relationship;
- принадлежность отчета клиенту этой relationship;
- право `report.review`.

Тренер не получает прямого доступа к базе или Object Storage.

---

# 10. Обратная связь тренера

Тренер может оставить обратную связь по отчету.

Feedback является отдельными серверными данными.

Обратная связь может относиться:

- ко всему отчету;
- к конкретному модулю;
- к конкретной сущности внутри модуля;
- к максимально атомарной сущности, если это имеет смысл для данного модуля.

Feedback не является Chat.

Feedback хранит:

- идентификатор;
- владельца/связанный объект;
- автора;
- текст;
- дату создания;
- дату изменения при необходимости;
- статус удаления;
- связанные Media, если они есть.

Для одной точки feedback допускается:

- до 500 символов текста;
- до 2 изображений;
- до 1 видео.

Тренер может оставить feedback самостоятельно, даже если клиент не оставлял собственный комментарий.

История feedback не должна теряться из-за изменения UI.

---

# 11. Редактирование

### Клиент

В `DRAFT` клиент может изменять отчет.

После `SUBMITTED` клиент не может изменять отправленную версию отчета.

### Тренер

Тренер не изменяет исходные данные клиента.

Он добавляет собственную обратную связь.

Каждый пользователь может редактировать и удалять собственную обратную связь.

Удаление feedback является мягким.

Если удалён feedback тренера, в истории сохраняется:

```text
Комментарий тренера удалён
```
# 12. Ownership

Владельцем отчета является клиент.

Тренер не становится владельцем отчета из-за наличия relationship или права `report.review`.

Авторство и ownership разделены:

- `owner_id` — клиент;
- `author_id` — пользователь, создавший конкретную запись или feedback.

Ownership не меняется при:

- смене тренера;
- архивировании relationship;
- реактивации relationship;
- изменении permissions.

Тренерские планы, цели и feedback сохраняют информацию об авторе.

Отчет остаётся частью истории пользователя независимо от текущего тренера.

# 13. Доступ после архивации relationship

Архивация relationship не удаляет:

- отчеты;
- feedback;
- media;
- историю.

После архивирования relationship тренер сохраняет доступ к данным периода своего сотрудничества в соответствии с правилами исторического доступа.

Новые данные клиента после завершения сотрудничества тренеру недоступны.

Новые действия, требующие активного сотрудничества, должны проходить отдельную permission-проверку.

Архивирование relationship не переносит ownership и не удаляет исторические данные.

Если исходная сущность, на которую ссылается отправленный отчет, была удалена после отправки, архивный отчет сохраняет соответствующее место и отображает маркер удаления.

Архивный отчет не должен терять структуру из-за удаления исходной сущности.

# 14. Связь с Chat

Chat не копирует содержимое отчета.

В сообщении может находиться ссылка на существующий Report object.

Схема:

```text
Chat Message
     ↓
Object Reference
     ↓
Report
```

При открытии ссылки пользователь получает просмотр существующего объекта.

---

# 15. Связь с Media

Report использует общую Media-модель.

Не создаётся отдельное файловое хранилище только для отчетов.

Схема:

```text
Report
  ↓
Media Link
  ↓
Media
  ↓
Private Object Storage
```

Это позволяет в будущем использовать одну систему хранения для:

- Chat;
- Reports;
- Training;
- Photos;
- других модулей.

---

# 16. Permissions MVP

Для отчетов используются как минимум:

```text
report.create
report.read_own
report.submit
report.review
report.feedback
```

Окончательное решение принимает Backend.

Frontend может скрывать недоступные действия, но не является механизмом безопасности.

---

# 17. Loading / Error / Empty

Интерфейс отчета должен иметь состояния:

- loading;
- empty;
- error;
- draft;
- submitted;
- reviewed.

Ошибки backend не должны приводить к молчаливому сбою.

Пользователь должен получать понятное состояние и возможность повторить действие, если это безопасно.

---

# 18. Уведомления

В MVP используются только in-app indicators.

Например:

- новый отчет ожидает проверки;
- тренер оставил feedback.

Push-уведомления и сложная notification-система в MVP не обязательны.

Email-уведомления могут быть добавлены позже через Backend Email Service.

---

# 19. История

История отчетов является постоянной частью пользовательских данных.

Окончание подписки, изменение тренера или архивирование relationship не должны автоматически удалять отчет.

Удаление пользовательских данных возможно только через отдельный предусмотренный процесс удаления аккаунта/данных и соответствующую политику хранения.

---

# 20. Backend API

Frontend работает с отчетами только через `reportService`.

Целевая схема:

```text
Report Page
    ↓
reportService
    ↓
apiClient
    ↓
Backend API
    ↓
Permission / Ownership / Relationship Check
    ↓
PostgreSQL
```

Прямой доступ frontend к PostgreSQL запрещён.

---

# 21. MVP Definition of Done

Модуль Reports считается готовым для MVP, когда:

- клиент может создать отчет;
- клиент может сохранить draft;
- клиент может отправить отчет;
- тренер может увидеть отправленный отчет;
- тренер может оставить feedback;
- клиент может увидеть feedback;
- report history сохраняется;
- связанные media сохраняются;
- приватные media выдаются через signed URLs;
- permissions проверяются на backend;
- Chat может ссылаться на Report;
- loading/error/empty состояния обработаны.

---

# 22. Что не входит в MVP

Не являются обязательными для первой версии:

- сложные шаблоны отчетов;
- автоматический анализ отчета AI;
- автоматическая оценка прогресса;
- push-уведомления;
- сложные recurring notification rules;
- публичные отчеты;
- групповые отчеты;
- несколько тренеров в одном отчете;
- автоматическая расшифровка видео/голоса;
- расширенная аналитика отчетов.

---

# 23. Связанные документы

Модуль Reports работает совместно с:

- AUTH_ARCHITECTURE.md;

- DATABASE_SCHEMA.md;
- MEDIA.md;

# Итог

Weekly Report является самостоятельным canonical object платформы.

Клиент владеет отчетом и его материалами.

Тренер получает доступ через Coach/Client Relationship.

Chat хранит только ссылку на отчет, а не копию его содержимого.

Структурированные данные хранятся в PostgreSQL.

Медиа хранятся в private Object Storage.

Все критические действия проверяются Backend Permission System.

История отчетов сохраняется постоянно и не удаляется автоматически.
